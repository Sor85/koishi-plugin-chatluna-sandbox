# 唤醒规则从被测响应插件的运行时读出，并随工具声明一起发布

**唤醒规则**由一个 module（`src/chatluna-wakeup.ts`）唯一持有：读被测响应插件的运行时配置、按会话派生当前生效的唤醒条件、把同一份事实渲染成一段可直接放进提示词的指引。三件事不拆开，因为拆开就会长出「结构化事实说 A、指引文案说 B」这种只有 AI 消费者能发现的漂移，而它发现的方式是等一条永远不会来的回复直到超时。

它要解决的是一个**沉默的失败**：外部测试控制器发一条 `send_message`，被测机器人不回复，控制器无从判断这是插件缺陷、是模型出错，还是这条消息根本没有唤醒它。而「怎样才算唤醒」完全不由沙盒决定——ChatLuna 主功能在群聊里看 @、引用、`botNames` 昵称与随机概率，私聊默认有问必答；chatluna-character 只在群聊里判定 @ 与引用，两处都看**伪装预设的 `nick_name`** 而不是插件配置里的机器人名，还会按累计消息条数、发言等待与群活跃度自己触发。两套口径没有一处重合。

**「谁在响应」本身是要先答出来的一条事实。** chatluna-character 的 `disableChatLuna` 默认开启，因此两个插件同时装上时默认只有它回复，ChatLuna 主功能被整条拦在 `chatluna/before-check-sender` 上；而它的私聊与群聊白名单模式默认都开启且名单默认为空，因此「装了 chatluna-character 却一条消息都不处理」是它的默认状态而不是异常状态。这两条默认值叠起来就是最常见的困惑形态：控制器照着 chatluna-character 的昵称去唤醒，实际回复它的是 ChatLuna 主功能，或者两个都不回复。答错这条，后面每一项唤醒条件都是错的。

**状态是四态而不是布尔。** `responds` 与 `suppressed`／`out-of-scope` 之外必须有 `conditional`：chatluna-character 的白名单按**会话键**（群聊是群号、私聊是发言者账号）判定，没指定会话时无从判定它收不收这条会话，把这一态压成两端都是替被测插件猜，而控制器据此写出的等待一定超时。同理，随机回复频率是 Koishi 计算属性时不静默当成 0——那会把「这个群其实开着随机回复」说成「不会随机回复」，而随机回复正是最难与缺陷区分的一种回复。不响应的插件也**不列**唤醒条件：那份清单会被读成「照着做就能唤醒」。

**抑制反过来不留余地：`disableChatLuna` 开着就按抑制成立作答。** 拦截器实际上还有两条放行名单，群聊那条更由被测插件按群里最近几条消息动态决定；沙盒刻意只取主干。复述那几层的代价是每条答案都要挂一句「要传 conversationId 才能判定」，连不带会话的通用规则都被它撑长，而 `disableChatLuna` 默认开启、放行名单默认为空，主干覆盖的正是几乎全部真实部署。代价写明：把某个会话加进 `whiteListDisableChatLuna` 之后沙盒仍然报「已被抑制」，那时以被测插件的实际行为为准。唯一保留的一层是白名单——会话不在 chatluna-character 的处理范围里时它连消息都收不到，也就不去拦；那一层不是「关于 `disableChatLuna` 的额外判定」，而是「谁在响应」本身，去掉它会让同一份答案自相矛盾。

**读运行时，不读配置文件，也不读预设文件。** 两份配置都从服务实例上现取（`chatluna` 的 `currentConfig`、`chatluna_character` 的 `_config`），昵称从被测插件自己的预设缓存 `preset.getPresetForCache(name, false)` 取。理由是要答的问题是「现在发一条消息会怎样」：配置页上的值与插件此刻在用的值可以不同（重载中、被别的插件改写过，切换默认预设正是写进 `currentConfig` 的），而从预设目录反推哪个文件对应哪个预设名会引入第二份解析——预设仓库（[ADR-0064](./0064-edit-upstream-presets-and-link-runtime-evidence.md)）解析的是模板与表达式，不是「这条会话此刻用哪个昵称」。`throwError` 显式传 `false`：上游默认在预设缺失时抛 ChatLunaError，而读不到昵称只该让指引少一句话。缺省值一律照抄上游 schema 默认值（私聊消息间隔 0、群聊 20、发言等待 10 秒、活跃度阈值 0.85），因为配置对象可以只带被改过的那几个键。

「怎么跨 loader group 取到被测插件的服务」搬进 `src/chatluna-runtime.ts` 由它唯一持有，对话线切换时重置 chatluna-character 上下文那条（[ADR-0080](./0080-follow-event-conversation-when-reading-history.md)）与本轮的唤醒规则都问它。两条形态各有理由且都不是防御性写法：走 `get(name)` 而不是属性访问，因为这两个服务不能进 `inject`——声明了它们会让被测插件每次重载都连带重建沙盒，内存模式下整份场景会跟着丢——而未声明的属性访问会被 Cordis 记一条注入告警；自己的上下文取不到时用提供方自己的上下文再取一次，因为被测插件可能装在隔离了服务映射的 loader group 里。

**发布面有三处，源头只有一个。** 新增只读工具 `get_wakeup_rules` 按会话精确作答；`chatluna-sandbox://guide` 带上同一份答案，因为工具清单只说「怎么调用工具」，而「消息要写成什么样机器人才会回复」是一次测试能不能开始的前提；`send_message` 的参数说明里带上通用指引，因为 MCP 客户端在连接时就会把 `tools/list` 交给模型，那是唯一不需要模型先想到要问的位置。三处都经 `describeTools` 或同一个读取口，因此不可能漂移，也自动对两种协议表述同时生效（[ADR-0081](./0081-serve-http-test-api-beside-mcp.md)）。

注入点**按 schema 形状选，不按工具名选**：带消息正文参数的工具就是「正文要写成什么才能唤醒机器人」的那一个。这与幂等窗口那处注入同一个手法，也必须如此——服务端源码里工具名不得与字符串字面量比较是一条架构守卫（[ADR-0086](./0086-own-tool-facts-in-one-registry-entry.md)），而给注册表条目加第五个治理标记只为一个工具服务，代价大于收益。今后新增带正文的工具会自动带上指引，这正是期望行为。

会话解析上，**会话实例与它的根会话得到同一份答案**。群聊取群号、私聊取会话里那位不是机器人的参与者，而实例继承根会话的参与者与群号（[ADR-0076](./0076-support-multiple-conversation-instances-per-contact.md)），因此实例与根会话必然同键——这与被测插件看不见实例这一级、同一时刻只持有一条对话线的上下文是同一件事，不是巧合。

刻意留在 Out of Scope 的有四处：**Koishi 全局 `nickname` 前缀**不计入条件——它经 `session.stripped.appel` 与 @ 等价，是 Koishi 层的事实而不是响应插件的配置，而沙盒给出的 @ 路径本来就能唤醒，穷举所有等价路径只会让指引变长；**两条放行名单与群聊那段按最近消息的动态判定**不复述，理由见上一段；**计算属性不求值**，沙盒没有 session 可用来解析；**WebQQ 不展示唤醒规则**，本轮的消费者是外部测试控制器，工作台上要不要有一处「当前谁在响应」是一次独立的界面判定。领域词汇新增两条：**响应插件**与**唤醒规则**。
