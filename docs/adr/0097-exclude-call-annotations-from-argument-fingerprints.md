# 调用标注参数不参与业务参数指纹

幂等键的重放判定与破坏性操作确认令牌的参数绑定共用同一个业务参数指纹，该指纹在求摘要前剥掉调用标注参数：测试关联标识（`testRunId`）与确认令牌本身（`confirmationToken`）。

标注参数的定义就是「不描述这次调用要做什么」。测试关联标识由工具注册表统一注入到全部工具的 schema 上，只写进测试调用记录，并且是 `list_test_call_records` 回溯同一轮编排的唯一维度——端点自己在鼓励每次调用都带上它。一个鼓励普遍携带的键参与业务判定，产出的是两条本该成功的路径静默失败：签发令牌时 `arguments` 里没有复述标注、实际调用带了它，确认被判成失败并报 `confirmation_required`；同一幂等键的两次重放各带一个标注值，第二次被判成 `idempotency_conflict`。两种失败的错误码都指向别处，消费者按错误码去查参数或去重取令牌，永远查不到真正的原因。

指纹只有一份而不是两处各自求摘要：确认令牌与幂等键对「同一份参数」的理解一旦分叉，同一次调用会在一条路径上被判成相同、在另一条上被判成不同。收成一处之后，「哪些键算业务参数」这个问题只有一个答案。

这确实收窄了 ADR-0023 里「令牌绑定操作参数」的范围：令牌不再覆盖请求的逐字全文，编排换一个标注值可以复用同一个令牌。这是可接受的，因为令牌要防的是「参数被改成删另一个实体」，而标注值改不了操作对象；令牌仍然绑定测试凭证、工具、全部业务参数与场景版本，且只能用一次。

反过来把标注参数排除在注入之外（让工具各自决定要不要 `testRunId`）解决不了问题：确认令牌的参数绑定是按「实际调用的全部参数」求摘要的，只要那个键出现在某次调用上，同一个坑就还在。
