# 数值参数类型不对显式失败，越界收敛

测试控制端点上的全部数值参数经同一个取值助手读取：类型不是有限数值时抛 `invalid_arguments`，取值超出声明的上下限时收敛到边界。两种非法输入分开处理，因为它们的失败形态不同。

类型不对此前经 `Number(...)` 变成 NaN，再被 `Math.min`/`Math.max` 原样放行——NaN 参与的比较全为 false。它不报错，只让调用静默退化成另一种行为：`limit` 变成 `slice(0, NaN)` 也就是零条会话，`timeoutSeconds` 变成 `setTimeout(NaN)` 也就是立刻超时，`settleSeconds` 变成「不等静默期」，`cursor.sequence` 变成「每个事件都匹配不上」，`expectedRevision` 变成「与任何版本都不相等」。前四个的观察结果与真实情况完全一样（这个操作者没有会话、机器人没有回复、机器人只回了一条、游标之后没有事件），消费者据此得出的是错的结论而不是一次可重试的失败；第五个报成 `revision_conflict`，把调用方推向「重读快照再重试」这条永远走不通的路。因此必须显式失败，与协议实现参数拒绝静默回落到默认值同一个理由。

越界不同：上下限已经写在 inputSchema 的 `minimum`／`maximum` 里，收敛之后消费者拿到的是一页真实数据加上续页信息，不会得出错的结论。这里收敛而不是拒绝，避免把一个可继续工作的调用变成失败——`limit: 10000` 的意图是「尽量多给」，服务端按上限给一页并附上续页游标正是它要的。

数值字符串（`'50'`）同样按类型不对拒绝，不做宽容转换：schema 声明的是 `number`，两种协议表述都走 JSON，数值在传输过程中不会退化成字符串。接受它等于让一个拼错类型的客户端一直拼错下去，而它下一次传的可能是 `'五十'`。

校验位置仍在工具执行体内部，不改「inputSchema 只当文档暴露、协议表述不做参数校验」这条既有决定：助手是执行体调用的，不是新增的一层校验中间件。
