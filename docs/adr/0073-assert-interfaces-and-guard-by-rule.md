# 断言 interface 而不是源码文本，架构守卫用规则制

测试的断言对象是从 interface 观察得到的外部行为，不是读进来的源码文本。源码断言看起来便宜，成本却在错误的地方发生：它在任何等价重构时变红，却对真实行为回归保持沉默——把三处相同的恢复赋值合并成一个函数、改变响应式引用的默认值写法、调整组件目录结构、更换图标，这些都会让它变红，而口径漂移它一条都抓不住。因此它是重构阻力而不是回归防线，模型请求工作台那一百零二条肯定式实现细节断言按此判据删除。判据是成本结构而不是断言形式。

三类源码文本断言是明确的例外。样式文本断言的断言对象本身就是样式源码，它不锁死实现写法，改一个变量名不会让它变红，它的问题是覆盖弱而不是有害。用户可见文案断言同理：在不引入组件挂载测试、jsdom 或 happy-dom 的前提下，它是唯一能守住界面文案不被误删的手段。否定式的已删除实现守卫是第二类例外，成本结构与肯定式细节断言相反——它只在有人把已经删掉的实现重新加回来时才变红，那正是需要的行为。架构守卫自身读取源码是第三类：它的断言对象本来就是源码结构，「客户端源码是否遵守某条规则」没有别的观察面，不属于被禁止的模式，不要把它当成同类问题一起删掉。

数量断言与源码文本断言是同一个错误的两种形态，都用一个廉价指标冒充行为验证。断言某个集合恰好有多少元素，只证明数量对得上，不证明其中任何一个元素能工作：MCP 工具覆盖那条工作里四十个工具有十五个从未被调用过，却被一处工具总数断言完整掩盖了很久。覆盖只能由逐个执行来证明。

架构守卫采用规则制而不是白名单制。白名单只约束名单内的文件，名单外默认豁免，规则随文件数增长自动失效，而失效是静默的——WebQQ 工作台那份七个文件的白名单外藏了九条真实违规，其中两条因为守卫不扫描 TypeScript 文件而连暴露机会都没有，还有一条只因为该文件里恰好没出现快照的类型名而被放过，规则靠拼写巧合成立。规则制反过来：谓词跑遍客户端全部源码，新增文件默认受约束，谓词描述被禁止的行为本身而不是它的某一种拼法。谓词的边界要按真实源码校准，宁可窄一点：完整快照规则只认属性形式的快照读取，因为放宽到裸标识符会把「把同名局部变量展开进搜索条件」误抓进来，误报会让豁免清单混进假债务。

已知违规登记为显式豁免，理由与负责消化它的后续工作均为必填，清单与守卫断言放在同一处，改动客户端代码的人立刻看到它。豁免不是放行而是有主的债务：有了负责人字段，它从白名单里的隐形放行变成一条可以被追踪和收敛的记录。逐条移除豁免后对应文件必须重新报错，这条断言保证规则真的在逐文件起作用，也保证清单里没有已经消化掉的陈旧条目。

## 规则的扫描根目录是规则自己的字段

守卫引擎的文件遍历、违规汇总、豁免匹配与三条元守卫断言只写一份，扫描根目录写在规则上：客户端源码规则与样式规则都扫 `client`，测试断言规则扫 `tests`。样式规则的根目录一度是 `client/styles`，区域样式表按能力归属散进各能力目录后（[ADR-0092](./0092-move-region-stylesheets-into-capability-directories.md)）它必须扩到 `client`——留在原地不会报错，只会静默缩到剩下的几张跨能力表。写死在引擎里的后果是每加一类扫描面就复制一份引擎——服务端与客户端已经各自复制了谓词类型、规则类型、豁免类型、文件遍历、违规汇总与三条元守卫断言，再加第三份是明知故犯。构建产物（`*.generated.css`）与类型声明文件不是源码，遍历时按后缀跳过。

## 组件测试文件不得出现裸的肯定式源码断言

这条判据本身此前只写在本记录里，靠人记账；现在由一条规则强制。规则按形状判定：先把测试文件里每个字符串变量绑到它读进来的那个文件（`.css` 是样式文本，其余是组件源码），派生变量按来源传递，再找 `expect(<组件源码变量>).toContain/toMatch(...)` 且不带 `not` 的落点。三类例外在形状上各自成立——否定式守卫带 `not`，样式文本断言的变量绑到 `.css`，架构守卫自身按 `*-architecture.test.ts` 这个文件名形状认出来。

用户可见文案是第四类例外，但它和被禁止的肯定式实现细节断言长得一模一样，规则无从按形状区分。因此给它一个显式辅助函数作为合法出口（`tests/helpers/user-facing-copy.ts` 的 `expectUserFacingCopy`）：把「这条断言保护的是文案」这个意图写进代码形状，规则因此能按形状判定，而不必维护一张断言级别的白名单。出口只限界面上真会被用户读到的字面文案；类名、属性名、类型声明、函数名与 CSS 选择器借它塞进来会让规则退化成一句空话。

### 逐条分类用的五类判据

治理一个测试文件时按这五类逐条判，判据是**成本结构**而不是断言形式：

1. **已有行为测试覆盖同一事实** —— 全删。同一件事有可执行的 interface 在断言了。
2. **样式文本** —— 全留（上面的第一类例外）。
3. **DOM 结构与元素顺序** —— 全留，含与样式选择器构成结构契约的类名、元素的先后顺序与嵌套关系。它们是结构事实，不锁死实现写法。
4. **实现细节契约** —— 删肯定式，留否定式（上面的第二类例外）。「接线」属于这一类的肯定式部分：哪个事件通向哪个处理器、哪个模块被真的接上。下沉后仍要保留接线断言时，必须在块注释里写明它保护的是接线而不是判定，以及少接一根线的表现形态。
5. **用户文案与展示语义** —— 全留，改由 `expectUserFacingCopy` 表达（上面的第四类例外）。

**别把「第 3 类」和「第三类例外」混为一谈。** 前者是这份分类里的 DOM 结构与元素顺序，后者是上一段的架构守卫自身读取源码；两者编号撞车，已经产出过一处误标的块注释。引用时写全称。

棘轮钉的是「未治理文件数只减不增」而不是断言总条数。按上面的五类判据，未治理文件里三分之二的断言本来就是合法的，钉总条数会把「治理完成」误导成「断言归零」，而归零会逼人删掉有架构决策依据的守卫。

已消化的文件不会从豁免清单里消失：它的组件行为下沉之后，剩下的第 2、3、5 类断言与第 4 类里的接线本来就该留，而规则无从按形状把它们和被禁止的实现细节断言区分开。因此清单分「已消化」与「未治理」两类登记，棘轮只数后者——把两类混在一个计数里，治理进度就永远收敛不到零。

## 只写在组件测试里的架构守卫要转成规则

一条架构决策若只由某个组件测试里的几条肯定式源码断言守着，它实际上只对那一个文件生效，而且断言的往往是另一个文件的源码文本。ADR 0060 与 ADR 0071 此前就是这个状态。正确形态是把决策的样式面转成对全仓样式表生效的规则（按选择器主语判定：一级区域与表头自身不得声明 `backdrop-filter`，模糊层必须落在无后代的 `::before` 上），把它的行为面下沉成带行为断言的模块，然后才删掉那些源码断言。顺序不可颠倒——这两条决策的失效形态都是「不会报错、只会静默错」，先删等于取消决策。
