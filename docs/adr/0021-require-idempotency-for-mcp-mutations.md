# MCP 状态修改必须幂等

改变模拟 QQ 环境或 AI 测试空间状态的 `interact` 与 `manage` 工具必须携带 `idempotencyKey`，服务端按测试凭证、工具名称和 Key 在当前运行纪元内缓存首次结果。相同参数的重试返回原结果，不重复修改模拟 QQ 环境；同一 Key 搭配不同参数时返回冲突。「相同参数」按业务参数指纹判定，调用标注参数不参与（见 ADR-0097）。

幂等缓存有界：首次结果的默认有效期为 30 分钟，且每个运行纪元默认最多保留 500 条，超出条数时淘汰**最早写入**的一条。淘汰按写入顺序而不是最近使用：有效期从首次写入起算，命中重放不延长留存期，若按最近使用刷新顺序，一条记录会活得比它承诺的窗口更久。超出有效期或被淘汰之后，同键重放**会重新执行操作**而不是返回首次结果——对 `send_message` 意味着重复发一条消息，对 `apply_environment_changes` 意味着重复应用变更（多半会因 `expectedRevision` 失败，但不保证）。外部测试控制器因此必须在窗口内重试，不能把幂等键当成长期去重手段。

这两个数值可以通过服务选项覆盖，因此携带 `idempotencyKey` 的工具描述由服务按**实际生效的配置**生成，而不是写死默认值：把默认值写进静态 schema 会让非默认部署向 AI 消费者发布一份错误的契约。消费者读 `tools/list` 拿到的窗口永远等于该实例真正执行的窗口。

上限是必要的而不是防御性的：每条缓存都持有结果的 `structuredClone`，`apply_environment_changes` 的结果里带完整场景快照，而纪元只在破坏性操作时轮换，因此不做破坏性操作的长跑测试会话原先会让这份缓存无界增长。取值理由：500 条与调用记录同一量级，在默认的每分钟 60 次状态修改上限下覆盖八分钟以上的满速修改；30 分钟远超幂等键真正服务的场景——响应在网络上丢失后的秒级重试，而单次调用最长也只有 120 秒的等待超时。两个取值都可以通过服务选项覆盖，与事件、调用记录、上传媒体三个缓冲区的做法一致。

`expectedRevision` 不能替代幂等键：它只能拒绝重复提交，响应在网络上丢失后重试会得到 `revision_conflict`，外部测试控制器无从判断上一次是否已经生效。

以下工具不在此列，各有更合适的机制：

- 事件等待工具（`wait_for_*`）不改变状态，按 ADR-0018 与命令分离；缓存首次结果会让重试拿不到新事件。
- `upload_media` 按内容寻址，`mediaId` 是正文摘要，同样的字节必然得到同一个 ID，天然幂等。
- `prepare_destructive_action` 只签发确认令牌，不改变领域状态，而且它本身就是破坏性操作的重试入口。
- 破坏性管理操作（`reset_scene`、`clear_scene`、`import_scene`、`delete_environment_entity`）由 ADR-0023 的一次性确认令牌覆盖。该令牌绑定测试凭证、工具、参数与场景版本且只能用一次，比缓存首次结果更严；ADR-0023 有意让这些操作无法盲目重试，重试必须重新取得令牌，因此不叠加幂等键。
