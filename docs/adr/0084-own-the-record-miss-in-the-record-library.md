# 证据记录库拥有自己的未命中判定，控制服务不转售

「这条证据记录在不在」由记录库自己判定。两个证据记录库（OneBot 调试记录与模型请求记录）各有一个「取不到就抛」的读取成员，抛的是领域错误，消息含记录标识；它与既有的「取不到返回空值」并存而不是替代它——后者服务于跨记录域遍历，遍历必须能区分「这个记录域里没有」与「这个记录域的持久化坏了」，用异常表达未命中会让一次真实故障被当成「这里没有」静默跳过。判定收进记录库之前，同一句中文提示有五处、两个错误类，其中未归属那一处抛的是裸 `Error` 而不是领域错误，与领域错误类存在的唯一理由（让测试控制端点把「领域说不」与「实现出错」分开）相矛盾；那个矛盾不是有人写错，是这句判定没有主人的必然结果。

单记录域的未命中归记录库，跨记录域的未命中归调用方。没有任何单个记录库知道「全部记录域都没有」，而记录域目录已经用返回空值表达查找未命中（见 ADR-0083），把跨域那句判定塞进记录库会重新把「这个域里没有」与「这个域坏了」混成一件事。因此这件事有两个持有者，这是判定而不是遗漏：文案同源、逐字相同，位置显式不同。

控制服务上只保留「把记录库交出去」这一个入口，两种证据各一个，形状相同——只返回字段，不带调用。九个替记录库说话的公开成员因此全部消失：七个原本是一行 `return this.<记录库>.<方法>(...)`，两个只多做一件事（把「记录不存在」写成一句中文抛出去）。其中一个成员全仓零调用，直接删除；追加记录那个成员的唯一消费方是仅在开发模式下生效的错误预览种子，改成直接写进记录库。两种证据对称处理而不是只治其中一种：收拢前一个记录库从不交出去、另一个整个交出去，这个差异不来自任何决定，只来自先后。

ChatLuna 的失败回填（解析上游错误、找到该会话最近一条失败记录、单行更新、把任务登记进更新跟踪）住在已经拥有 ChatLuna 错误解析与「最近一条失败记录」查找的那个 module，签名接收记录库。它不进记录库：记录库不该认识 ChatLuna 的错误格式，否则换掉记录存储要连带理解上游错误的形状。「ChatLuna 的错误回调是同步的，记录查找与单行更新只能在后台完成，收尾等待通过更新跟踪覆盖它」这条规则改坏了不会报错，只会在关机时静默丢掉一次归档，因此注释跟着逻辑一起走。

一条规则制守卫拦住「一行转售」这个形状重新长出来：公开成员体只有一句 `this.<字段>.<方法>(…)` 即报，且该字段的声明类型是另一个 module 的类。协作字段按同文件里的声明类型判定而不是按字段名列举，新增一个协作 module 时规则自动覆盖它；内置集合与值类型、数组类型与数组字面量、同文件里声明的类都不算——读自己的集合或本 module 自己的内部结构不是转售。裸 `return this.<字段>`（没有调用）不算，那正是本条决定想要的结果；只有一句但调用自由函数的成员也不算，那一句是本 module 自己的判断。规则跑遍服务端全部源码，与既有两条同形，不按文件名列白名单。

该规则的豁免按成员登记而不是按文件：它当前的两处豁免（ChatLuna 状态库的读写两侧各一个一行委托）同在一个文件里，沿用「文件 ＋ 规则」成对匹配会让同一文件长出第三个转售成员被静默放过。因此豁免可以带一个成员名，带了就只放行那一个成员；不带仍然按文件与规则匹配，前两条规则的豁免形状不变。「移除任一豁免后对应文件重新报错」这条元守卫继续成立，并对成员级豁免额外要求「暴露的只是它自己那一个成员」。

不改变 ADR-0002 的服务端状态所有权：状态仍然只有一个权威持有者，动的是 interface 的宽度。不改变 ADR-0027 对测试控制端点错误分类的口径，也不改变 ADR-0083 的任何既有决定——记录域的形状补充见该条。规则制守卫与「按 interface 而不是按实现写法断言」的判据见 ADR-0073。控制服务按六组职责在 implementation 里划内部 module 是另一条候选，本条决定刻意不碰它：那件事的爆炸半径与本轮差一个量级，混进来会让「interface 收窄是否纯结构性」无从证明。
