# 改变状态的工具返回发送前游标

`send_message`、`send_forward_message`、`perform_friend_action`、`perform_group_action` 在结果里同时给出 `cursorBefore`（进入执行体时的事件游标）与 `cursor`（操作完成后的事件游标）。等待被测机器人对这次操作的反应时传 `cursorBefore`。

这些工具都会等待被测机器人的同步处理完成才返回，因此机器人的回复、ChatLuna 状态变更与插件发起的 OneBot 调用可能在调用返回之前就已经进入事件流。只返回操作后的游标时，最自然的写法——把上一步返回的 `cursor` 传给 `wait_for_message`——必然错过这些事件，而错过的表现是 `matched: false`，与「机器人没有回复」完全一样。

正确做法此前是「先调 `get_server_info` 取一次游标，再发送，再用那个旧游标等待」。它可行，但只能靠文档传达：这套仪式此前写在四处散文里（两个发送工具的参数说明、测试指南里的两个等待示例），而任何一个消费者只要没读到那几段，就会写出那个必然错过的版本。返回值里多一个字段之后，正确写法变成「把上一步返回值里的字段传下去」——这是每个 API 消费者的默认动作，不需要先学。

命名成 `cursorBefore` 而不是 `previousCursor`：它回答的是「这次操作之前的位置」，而不是「上一次调用的游标」。两个字段并列返回而不是只返回发送前游标：操作后的游标仍然有用（不关心机器人反应、只想从当前位置继续等别的事件时用它），而且去掉它是一次破坏性变更。

四个工具都给而不是只给两个发送工具：关系操作同样可能触发机器人反应（戳一戳、审批入群申请之后机器人发公告），同样在执行体里 `await` 了领域操作，因此同一个坑一模一样。让四个工具在这件事上形状一致，消费者不必记住「哪些工具的返回值里有它」。
