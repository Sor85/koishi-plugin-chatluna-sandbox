# 按调用结果筛选证据记录用状态枚举

三族证据记录的查询参数用 `status` 枚举筛选结果，取值集合就是各自记录的状态词汇：OneBot 调试记录与测试调用记录是 `success`／`error`，模型请求记录多一个 `pending`。此前是 `errorsOnly` 布尔。

布尔只能表达「只要错的」。「只要成功的」表达不了，而它是真实需求——确认某一轮编排里没有失败调用要反过来数，确认某次交互真的成功落地要在成功记录里找。模型请求的 `pending` 更是布尔连边都碰不到：一个还没收到响应的请求既不是错也不是成功，它是排查「插件卡住了」时最该看的那一类。

取值集合直接取记录自己的状态类型，因此筛选参数与记录字段是同一份词汇，消费者读到 `status: 'error'` 的记录后可以原样把这个值传回去当筛选条件。这也让端点内部不再有两套说法：`wait_for_onebot_action` 早就用 `status` 枚举筛同一批 OneBot 调用记录，而列表工具用 `errorsOnly` 布尔，同一个领域概念在相邻两个工具上长着两个名字。

改动落在查询输入与持久化查询上，WebQQ 那三处筛选仍是「只看错误」复选框：复选框是布尔控件，这与端点参数是枚举不冲突，翻译发生在客户端的调用点（`status: errorsOnly ? 'error' : undefined`）。三个记录页此时只用得到枚举的一半，那是界面的取舍而不是查询层的限制。

同一轮里所有枚举参数（`order`、`direction`、`transport`、`scope`、事件类型）都改成取值集合之外显式失败。此前每处各写一句「是这个值就用它、否则 undefined」，于是拼错的取值静默变成「不筛选」或「用默认排序」；筛选参数被无声忽略最坏——`status: 'faild'` 会返回全部记录，而消费者以为自己拿到的只有失败记录。失败消息里带上取值集合，因此错误本身就是文档。
