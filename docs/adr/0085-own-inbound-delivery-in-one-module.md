# 入站投递是一道内部 seam，控制服务不再逐条组装事件

把「把一条已落库的消息投递给所有该收到它的虚拟 OneBot 机器人」收成一个内部 module（`src/inbound-delivery.ts`）。它对外只有两件事：把一个 OneBot 事件派发给一个机器人并记录它（消息、好友请求、好友通知、群请求、群通知、撤回通知六种事件都经它），以及把一条已落库的消息投递给所有该收到它的机器人（接收机器人推导、会话与 OneBot 事件字段构造、ChatLuna 角色上下文跟随、中间件等待与超时、入站事件会话的进出栈、投递记录）。协作者按最小结构化 interface 注入——按标识取运行时机器人与机器人档案、订阅中间件完成、写调试记录、写投递记录、跟随角色上下文、记日志——**不注入宿主 `Context`**，与 [ADR-0075](./0075-make-dom-touching-view-behaviour-testable-by-injection.md) 在客户端那侧同口径，服务端也已有记录域目录与模型请求采集器两个先例。

真正的收益不是少几份组装，而是三条此前只写在注释里的规则第一次成为可断言的事实，三条都改坏了不报错：等待被测插件中间件的十五秒超时（拿掉它会让 void 掉的投递 Promise 永久挂起，堆积监听器并拖垮运行时）、ChatLuna 角色上下文跟随失败只写日志不中断投递（改成抛出会让被测插件根本收不到消息，那比上下文不干净严重得多）、入站事件会话的进出栈（[ADR-0080](./0080-follow-event-conversation-when-reading-history.md) 的历史读取跟随与挂在机器人动作记录上的会话观察都依赖它，失败形态完全静默）。它们此前藏在一个三千行的控制服务里，要驱动必须先起一个真的 Koishi 运行时，因此至今零覆盖；现在四类接收机器人推导、超时、跟随失败与窗口进出栈都能不开运行时驱动，超时用测试运行器的假时钟推过去而不是换一个时钟（[ADR-0066](./0066-drive-domain-time-with-fake-timers.md)）。顺带被钉住的是一份还没漂移的重复：媒体那一路手搓的 raw message 与共用助手函数今天逐字相同，但没有任何东西保证它继续一致，现在它调同一个助手函数。

共用底座必须在这个 module 里，因为六种事件都用它，而它拥有调试记录的形状（[ADR-0048](./0048-standardize-onebot-action-records.md) 那份统一动作记录）。留在控制服务会让 module 反过来注入一个「怎么记录一次派发」的回调，等于把自己的核心职责外包出去。入站事件会话窗口反过来不在那份 interface 里：它是 module 之外的一个小值，由 module 进出栈、由机器人适配器读取，控制服务只负责把同一个实例交给两边。把读取塞进 module 的 interface 会在「派发一个事件」「投递一条消息」之外多出第三件；让机器人适配器转手控制服务再读一次则是一行转售，规则本来就拦它。

notice 与 request 那五个派发方法的**组装留在控制服务**，只有派发那一步改道。每一个都依赖场景状态（取用户、取群成员与角色、按角色挑收件人），每一个都带着自己那段保真度注释——例如戳一戳必须补上子类型与目标标识，缺了它「被戳后回复」这类插件的监听器永远不匹配。搬它们是另一个切片，硬搬会把场景查询拖进投递模块，而那正是这条 seam 想要挡在外面的东西。

一条守卫规则拦住第二份组装：组装入站消息事件字段的写法只允许出现在投递模块里，谓词按形状判定——事件类型与 raw message 出现在同一个对象字面量里——与既有那条「收发 Koishi RPC 的函数只允许出现在客户端端口适配器里」同形（[ADR-0073](./0073-assert-interfaces-and-guard-by-rule.md)）。它今天只命中投递模块；机器人适配器里那份读取方向的 `get_msg` 回执带 raw message 但不带事件类型，notice 与 request 那五份带事件类型但不带 raw message，两类都命不中，因此豁免清单不增一条。

本轮只收 implementation，一条既有决定都不推翻：[ADR-0076](./0076-support-multiple-conversation-instances-per-contact.md) 的写入偏离（原始 OneBot action 的回复仍然只落到根会话，沙盒不替插件归位）、ADR-0080 的读取跟随与会话观察、ADR-0048 的动作记录形状、[ADR-0002](./0002-server-owned-sandbox-state.md) 的服务端状态所有权都保持原样，被测插件收到的会话字段与 OneBot 载荷经三条发送路径的确定性基线比对逐字节相同。控制服务上八个发送成员一个不动：它们的差异不是冗余，而是「谁等待投递完成」（Console 要即时结果、外部测试控制器要等到同步回复进入发送前游标对应的事件流、机器人动作不能等否则向自身会话发送会成环）与「操作者是不是机器人」（机器人操作者必须走自身的真实 OneBot action，能力禁用与调试记录才与真实通道一致）两件事，前者被外部测试控制器的游标语义压着，后者被 ADR-0076 压着，收窄它们是另一次判定。同样留在下一次的还有入站与读回在媒体段字段上的既有差异：入站投递给插件的媒体段只有文件引用，共用助手函数在带媒体时产出的段还带地址与文件名。改它会改变被测插件收到的事件保真度，必须对着真实 OneBot 实现核过，因此和机器人适配器里那份读取方向的组装一起归「OneBot 事件构造的两个方向」——那份组装的输入是快照里的一条消息而不是一次发送描述，硬合会让一个 module 同时服务两个方向。
