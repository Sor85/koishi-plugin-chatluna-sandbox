# 用测试运行器的假时钟驱动领域时间，不注入时钟

沙盒控制服务中约二十六处时间来源——消息与通知的 `createdAt`、撤回时间、禁言截止时间、OneBot 事件的 `timestamp` 与 `time`、耗时测量的起止点——继续直接读取系统时钟，不引入可注入的时钟选项。需要控制领域时间的测试改用测试运行器的假时钟：`vi.useFakeTimers({ shouldAdvanceTime: true })` 配 `vi.setSystemTime()`。

这条决策来自一次探针验证，而不是推断。探针用假时钟在两个不同日期各发送一条消息，再按日历日筛选消息搜索结果，二十毫秒内通过；`shouldAdvanceTime` 是必需的，因为消息投递路径会等待 Koishi 的 middleware 事件，完全冻结的定时器会让该等待永久挂起。同一组探针还纠正了两个此前的推断：Koishi 即使没有注册用户中间件也会触发 middleware 事件，因此消息投递在正常路径上是毫秒级完成，硬编码的十五秒中间件超时不会被触及；只有在应用未启动的测试装配下才会走满该超时，那是装配缺陷而不是生产缺陷。

因此「控制服务缺少时间注入 seam」不是一个真实的结构问题。加入时钟选项要改动二十六处调用点、在服务选项上新增一个字段，换来的能力测试运行器已经免费提供；按删除测试判断，删掉那个选项后复杂度不会在调用方重现，它只是把系统时钟的读取搬了个家。仓库中已有先例可循——OneBot 调试记录的排序测试早就用 `vi.setSystemTime` 制造同毫秒与跨秒场景。

有一处测试债与时间无关，但常被误认为同一个问题：跨日历日的消息搜索测试目前先取场景快照、直接改写其中的消息创建时间，再通过整体替换场景写回。整体替换场景是为导入版本化场景设计的破坏性入口，它会递增修订号、清空机器人事件投递、清空 ChatLuna 对话状态并重新同步运行时机器人，所以任何跨日期搜索测试都无法同时验证投递记录或对话状态。这条债应当通过改用假时钟消除，而不是通过新增时钟选项。

耗时测量不适用假时钟：注入固定时钟会让持续时长恒为零，断言反而更不真实。超时时长是「等多久放弃」而不是「现在几点」，若将来需要在测试中缩短某个超时，应当像数据库就绪超时那样单独增加一个时长选项，而不是纳入时钟。
