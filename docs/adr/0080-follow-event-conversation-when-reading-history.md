# 历史读取跟随事件来源会话，并在对话线切换时重置被测插件上下文

原始 OneBot 历史查询按触发它的入站事件来源会话作答。这取代 [ADR-0076](./0076-support-multiple-conversation-instances-per-contact.md) 里「原始 OneBot action 保持只能寻址根会话」在**读取方向**上的部分——写入方向不变，那一段原文不改写。ADR-0076 的理由（真实 QQ 的 action 表面没有「会话」这一级，替插件猜测归位会让沙盒行为与真实环境分叉）对写入仍然成立，对读取不成立，区别在于结果的可见性：一次回复落到根会话是测试者在界面上看得见的事实，看见之后可以据此断言被测插件的真实行为；一次历史查询读到什么没人看得见，它会直接变成模型输入。照字面把 `get_friend_msg_history` 与 `get_group_msg_history` 答成根会话，插件在会话实例里就读到另一条对话线的历史，随后拿着它去请求模型，而 WebQQ 上这条实例仍然只显示用户刚发的那一句——分支测试因此不成立，且失败形态完全静默。跟随只在「来源会话正好是所寻址根会话的实例」时发生：插件主动查另一个联系人的历史是它自己的选择，跟着改会让沙盒答非所问。跟随本身与写入偏离同口径，作为一条会话观察挂在机器人动作记录上，是可断言的证据而不是警告日志。

按账号或群号归档对话上下文的被测插件，由沙盒在对话线切换时替它重置。会话实例只在 Koishi channel ID 这一维上与根会话不同，因此沙盒自己的状态（ChatLuna 对话状态的组合键、模型请求记录的会话归属）天然按实例分叉，但第三方插件不一定看 channel ID：chatluna-character 把消息缓冲、状态与历史回填全部按 `private:<账号>` 或 `group:<群号>` 归档，一个根会话与它的全部实例在那里塌成同一份上下文，新建实例后发的第一条消息会带着上一条对话线的历史进模型。沙盒没有办法让第三方插件同时持有多份上下文，能做的只有在切换时把它那份清掉，让它按沙盒的历史查询重新回填——上一段的读取跟随正是这次回填能读对的前提。重置只在「同一个会话键上一次派发的会话与本次不同」时发生，因此同一条对话线里连续发消息不会把上下文清掉；本进程第一次为某个键派发时也不重置，那一刻插件那份上下文还没被别的对话线污染过，而重置会在插件里写下一条历史截断时间，之后它再也回填不出这条对话线自己的历史。

被测插件按服务名现取，不进 `inject`。声明进 `inject` 会让被测插件每次重载都连带重建沙盒控制服务，内存模式下整份场景跟着丢；而未声明的属性访问会被 Cordis 记一条注入告警，因此走 `ctx.get(name)`，并在自己的上下文取不到时遍历插件注册表用提供方的上下文再取一次（chatluna-usage 已经踩过服务映射被 loader group 隔离这个坑）。重置失败只写日志：最坏结果是这一轮带上另一条对话线的历史，而中断投递会让被测插件根本收不到消息，那比上下文不干净严重得多。

这条决策换不回「两条对话线各自留住自己的上下文」。chatluna-character 的清空动作会写下历史截断时间并据此过滤回填结果，所以切回另一条对话线时它同样从零开始，而不是恢复那条线之前累积的上下文。沙盒选择「每条对话线从它自己的历史开始」而不是「带着另一条对话线的历史继续」，因为后者会让分支测试给出错误结论，前者只是让上下文短一些且有据可查。真正的修法在被测插件那一侧——把 channel ID 并进它的会话键；本仓库不替它做，也不为此伪造参与者账号或群号。
