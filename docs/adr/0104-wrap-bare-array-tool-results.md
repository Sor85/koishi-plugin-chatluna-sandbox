# 裸数组结果包一层

`list_test_spaces`、`list_pending_requests`、`get_capability_matrix` 三个工具的结果从裸数组改成 `{ items: [...] }`。这是全仓库唯一三个返回裸数组的工具，其余三十八个本来就是对象。

MCP 协议要求 `structuredContent` 必须是对象，因此传输层只在工具结果是普通对象时附上它，数组与标量只落进 `content[0].text` 里的一段 JSON 字符串。同一个工具在 HTTP 表述下返回的是真正的 JSON 数组。于是 MCP 客户端对这三个工具必须改走「解析文本」的路径，而对其余工具可以直接读结构化内容。词汇表说两种表述「落到同一次工具调用上的权限、配额、幂等与记录完全相同」——这处差异不在那四项里，但它同样是消费者要为「换一种表述」付的代价，而且不是协议翻译的必然结果：结果形状是我们自己定的。

第二个代价是加不了字段。裸数组上没有地方放容量摘要、续页信息或来源标注，因此这三个工具今后要加任何东西都是破坏性变更。包一层之后加字段是兼容的。

集合键取 `items`，与四个 list 工具收敛后的集合键同名（ADR-0103），端点上因此只剩一个集合键。

包装只加在工具这一侧。`readCapabilityMatrix` 同时被 `chatluna-sandbox://capabilities/napcat` 与 `.../llbot` 两条只读资源复用，而资源正文本来就是文本序列化、不受 `structuredContent` 的约束；跟着包会让已经在读资源的消费者白改一次，因此两条资源保持返回裸数组。

`jsonContent` 的判定不改。它对协议的理解是对的，问题在结果形状而不在它；判定留着是因为它仍然是正确的防线，而不是因为还有工具要走它的 else 分支。

这是一次破坏性返回变更，与 ADR-0103、ADR-0105 同批发生。受影响的既有断言逐处改成读 `items`，不加兼容层。
