# 关系操作的规则由一个 module 唯一持有，两条操作通道退成 adapter

「谁能对谁做什么、做完之后场景变成什么样、派发哪一条群通知」收成一份规则（`src/relationship-actions.ts`），两条**操作通道**都问它：普通用户的交互直接调它，虚拟 OneBot 机器人经自身 OneBot action 落到同一份规则上。写这条 ADR 之前退群、改群名、设管理员、踢人、改群名片这五个动作在控制服务里是**两份逐字重复**——同样的角色判定、同样的状态变更、同样的通知时序，差异只有返回值形状与通知里操作者标识的取值来源；申请审批同样有两份。转让群主、设专属头衔、禁言三个动作**已经共用**一个私有方法，因此这条路在那个文件里已经走过三次，本轮把它走完，并把它搬到一个能被守卫钉住的位置。

真正的收益不是少五份拷贝，而是「两条通道的规则会不会漂移」第一次有了红灯。它此前的失败形态是**从 WebQQ 操作正常、机器人操作却不对**：两条路都通，只是规则不一样，没有任何东西会报错。而且它已经漂移过四次——入群申请被拒时两条通道各说一句不同的话、好友申请找不到时的措辞不同、批准好友申请时设置备注只有机器人通道支持、用户通道对群邀请多一条守卫。四处里前两处是文案、后两处是能力与守卫，本轮全部**原样保留**，但它们证明漂移不是假设。第五处经核查**不是漂移**：机器人通道按 OneBot 的子类型语义查找申请（调用方必须传子类型，传错就当找不到），用户通道没有这个参数——两个通道的**输入不同**，不是同一规则的两种写法，因此不动它，也免得下一轮有人把它当债务去修。

**拒绝以可辨识原因表达，文案归通道。** 规则不写中文，只回答「不行，因为什么」；两条通道各自把同一个原因渲染成自己的措辞。这不是新写法：共用消息能力规则已经这么做，控制服务里三个渲染函数把同一个拒绝原因渲染成撤回、贴表情、回复三套文案（[ADR-0078](./0078-share-one-message-capability-rule.md)）。收益是入群申请审批那两句**已有断言**的文案逐字保留（用户「只有群主或管理员可以处理入群申请」、机器人「机器人没有审批入群申请的权限」），而角色判定只剩一份。传字符串也能做到，但那会让规则收一个只为拼文案存在的参数。八个群动作的措辞在两条通道上今天逐字相同，因此它们共用一份动作名表与一个渲染函数——把动作名再抄一遍等于把刚消掉的重复换个位置放回来；文案真正不同的那一处不在那张表里，由两条通道各自在自己的入口上渲染。

**申请审批只共用尾巴。** 共用的是「摘掉申请、批准则加成员或加好友、否则提交场景变更」；前置判定各留在自己通道——谁有权处理、能不能代机器人处理、按什么条件查找申请。这正是两条通道**应该**不同的地方，把它们参数化会让通道差异从两段可读的代码变成一组开关，读的人每次都要回头查那个开关传了什么。备注因此留在机器人 adapter：好友那条尾巴收一个「批准后、提交之前对新建立的好友关系做一次补充」的回调，而不是收一个 `remark` 参数——给用户通道加那个参数是新功能而不是重构，而把备注写在尾巴之后会让场景变更监听器先收到一份没有备注的快照。用户通道对好友申请与群邀请那两条「机器人的决定必须由机器人自己作出」的守卫同样留在 adapter：它们表达的正是操作通道这条领域约束（[ADR-0008](./0008-require-bot-approval-for-relationships.md)、[ADR-0039](./0039-use-a-unified-current-operator-in-webqq.md)），不是同一条规则的两种写法。

协作者按最小结构化 interface 注入，**不注入宿主类型**，与入站投递模块同口径（[ADR-0085](./0085-own-inbound-delivery-in-one-module.md)）；分三类：提交一次场景变更（含把成员从群里摘掉这种连带清理）、派发一条群通知、申请与好友关系集合的写入。module **不持有第二份沙盒场景**，只接收群对象与群成员的引用并就地改写它们，[ADR-0002](./0002-server-owned-sandbox-state.md) 的服务端状态所有权因此不动。它也没有「操作者是不是机器人」这一维：机器人仍然只能经自身 OneBot action 执行这些操作，受启用状态、实现配置与能力覆盖约束，通道差异表达在 adapter 里而不是表达绕道（[ADR-0076](./0076-support-multiple-conversation-instances-per-contact.md)）。控制服务上机器人通道那四个落地成员的 interface 一个未改——它们是 OneBot action 的落地点，返回 OneBot 回执形状，收窄它们是另一次判定。

要 module 而不是继续用私有方法，依据是守卫。仓库既有的架构守卫都按「写法形状 ＋ 持有者文件」判定（[ADR-0073](./0073-assert-interfaces-and-guard-by-rule.md)）；规则留在控制服务的私有方法里，持有者就是控制服务整个文件，而违规也在同一个文件里——文件级持有者判定会把整个文件放行，规则等于不存在。因此新增的规则是：**群成员角色比较只允许出现在关系规则模块里**。谓词按标识符名收窄，与工具名那条同一个手法（[ADR-0086](./0086-own-tool-facts-in-one-registry-entry.md)）：只认 `actor`／`target`／`operator` 这三个名字上的角色字段与字面量比较，相等、不等与字面量写在左边三种写法都算。两处合法命中因此天然避开——场景校验里判断群里有没有群主用的是解构出的裸 `role` 与 `member.role`，机器人适配器把角色渲染成中文名用的也是 `member.role`。真正命中的只剩共用消息能力规则里那道撤回阶梯，它按**文件**登记为有主豁免，负责人指向 ADR-0078：那道阶梯回答「一条消息能不能被撤回」，与关系规则那道「一个成员能对另一个成员做什么」在那条 ADR 里已经判定各自成立、不合并；把它搬进关系规则模块会让服务端与客户端共用的纯函数模块反过来依赖关系规则。

净新增测试 seam 为零，这是有意的。两条操作通道各自的既有 seam 就是这一族的全部测试面，而且它们恰好是**真实通道**：群权限那份与好友关系那份驱动用户通道，OneBot 桥接那份与实现配置那份驱动机器人自身的 action。两份都一字不改地继续通过——它们不是同一条断言的两份拷贝，而是「每条通道都真的经过了那份规则」这条接线的两侧证据，因此不能用一份 module 断言替掉。拒绝原因联合也不写形状断言：那是肯定式实现细节断言，等价重构时变红，它由两条通道渲染出的具体文案从外部证明。行为没变由基线证明——八个群动作、两类申请审批与两类邀请审批在两条通道上各跑一遍，含全部拒绝分支，执行前后的完整场景快照摘要、逐叶子差异、派发出去的每一个标准事件与原始 OneBot 载荷逐字节相同。

本轮只收 implementation，一条既有决定都不推翻。领域词汇不需要新词：「操作通道」已在册且定义准确，正是这个 module 的名字来源。刻意留在 Out of Scope 的有五处：统一那两处拒绝文案（两处都有断言，统一它们要改断言，而改断言正是最容易把真红当假红顺手改掉的动作）、给用户通道加备注、把邀请守卫下沉进规则、让两条通道按同一条件查找申请、以及按剩下几组职责继续划控制服务内部 module（场景写入与保留窗口、头像与媒体、发送时序、公共 notice 派发）。
