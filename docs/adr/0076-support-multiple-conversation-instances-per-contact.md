# 同一联系人下支持多个会话实例

会话实例是一等会话，不是界面上的一个分栏。在实例里发消息时，插件收到的 Koishi channel ID 就是实例 ID，因此 ChatLuna 对话状态的组合键（机器人参与者 ID 加会话 ID）与模型请求记录的会话归属自动按实例分叉，两条对话线的上下文互不污染——这正是这次改动的全部价值：复盘一次长对话时，用户可以从中间某条消息往下换一种问法，而原始记录一条不动。代价是分支要复制分叉点之前的消息，场景消息保留窗口的预算因此按分支数被摊薄；把分支改成只记分叉点、读取时拼接根会话前缀是独立一轮工作，它会改动消息存储与消息历史分页的验证面。实例的参与者对与群号一律从根会话读而不复制，可见性也完全继承根会话，因此实例不引入所有权或创建者维度。

会话实例移出根会话集合，成为沙盒场景里的独立集合。这是本决策里最主要的一条：把实例压进同一个会话类型、用一个可缺省的父会话字段区分，会让全仓库十余处按参与者对或群号解析会话的实现对实例视而不见——OneBot 私聊与群消息发送、消息历史、转发读取、戳一戳都会拼回根会话的规范 ID，好友动作、群动作、关系目录与客户端可见会话投影都会取第一个匹配，而机器人的最近联系人列表反过来会把每个实例当成一个独立联系人；这些漂移全部是静默的，没有任何一处会报错。拆成两个集合之后，那十余处遍历默认只看到根会话，不需要记住任何新事实；确实需要全部会话的少数路径（消息搜索、保留窗口裁剪、场景导出、场景校验）显式合并两个集合。谁是根会话、某个 ID 指向根还是实例、某个操作者能看到哪些会话、一对参与者的根会话在哪，连同实例集合的创建与删除，全部收进会话解析模块，并由一条架构守卫规则钉住：除该模块外，服务端源码不得直接读写会话集合与实例集合。

原始 OneBot action 保持只能寻址根会话。真实 QQ 的 action 表面没有「会话」这一级，沙盒不按「最近一次事件」或异步上下文替插件把回复归位到实例——那会让沙盒行为与真实环境分叉，而分叉过的沙盒证明不了任何事情。标准 Koishi 发送路径按 channel ID 解析会话，实例天然可达，回复落在用户发消息的那个实例里；插件改用原始 action 时回复落到根会话，沙盒在 OneBot 调试记录上留下一条「回复偏离了事件来源会话」的观察结果，包含事件来源会话与实际落点。它是可断言的证据而不是警告日志：外部测试控制器与用户因此都能把被测插件的这个真实行为写成断言，而不是怀疑沙盒出错。归因窗口限定在「机器人正在处理某条入站消息事件」这段时间内，派发之后异步发出的 action 不被归因，这是有意的下限——沙盒只观察它能确证的那一段。
