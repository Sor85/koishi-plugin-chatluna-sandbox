# 按能力拆分客户端 RPC 端口，而不是喂一个大工作区端口

客户端每一类 Console RPC 能力有自己的端口三件套：类型化 interface、Koishi 适配器、内存假实现，三者按 [ADR-0090](./0090-group-source-files-by-capability.md) 落在能力目录里，文件名分别是 `port.ts`、`koishi-port.ts`、`fake-port.ts`。工作区端口继续拥有模拟 QQ 环境的场景读写，测试空间生命周期与 MCP 管理面各自独立成端口。判据是「输入里有没有对方的概念」：工作区端口读写单个空间内部的场景状态，测试空间端口只管空间自身的存在与归属，MCP 管理面的凭证、能力目录与服务器活动根本不经过场景，把它们塞进工作区端口只会让一个 interface 承担互不相关的变更原因。代价是调用方要认识多个 seam，换来的是每个假实现只覆盖自己那一类能力——手写假端口的体积不随能力总数增长，这是继续喂大端口时最先失控的东西。

架构守卫因此按命名约定判定适配器层而不是列举文件名：能力目录下的 `koishi-port.ts` 自动被认作合法的 RPC 持有者，其余任何客户端文件出现 `send` 或 `receive` 都算违规。这比原来「只允许一个具体文件」弱一档，但仍是规则制——新增适配器不需要改守卫，新增其他文件默认受约束，而白名单做不到后者。

显式定域优先于隐式当前工作区定域。工作区端口适配器按当前活动空间给请求补 `spaceId`，但调用方已经指名 `spaceId` 时不得被覆盖：AI 测试空间总览要在一屏里绘制主环境与任意测试空间的缩略图，它需要按显式空间读头像媒体，而隐式定域按定义只能表达「当前那一个」。这条规则统一作用于全部端口方法，顺带修掉了 OneBot 调试记录读取里的同一个潜在缺陷——那里的输入类型早就允许显式 `spaceId`，却会被隐式定域静默盖掉。

跨空间视图模型由唯一同时握有全部空间的模块交出。机器人目录跨主环境与全部测试空间，环境目录的用户与群组取当前工作区而机器人跨全部空间；这两份目录都落在 AI 测试空间外壳里，因为它是唯一持有主环境快照、当前工作区快照与测试空间列表的地方。装配层不做派生，UI 组件收目录而不是完整快照，ADR-0040 里「UI 模块不得访问完整 snapshot」这条至此没有例外。合成一份目录也消掉了一处口径分叉：环境管理页此前只解析主环境机器人的头像，测试空间的机器人头像没走解析。

四道记录域能力随后也各自成端口：OneBot 调试记录、模型请求记录、预设文件、测试调用记录。工作区端口留下的是**场景消息读写、环境与关系操作、场景变更广播**——环境与关系不拆成第五道，它返回的是同一份工作区状态，与消息读写共享场景这个概念，拆开只会得到两个都返回工作区状态的端口。判据因此是两条而不是一条：既有的「输入里有没有对方的概念」，再加上**适配器要不要注入当前观察空间**。第二条把四道拆法完全确定下来：模型请求的分类由调用方显式给出（未归属分类根本没有空间标识），预设文件是全局 ChatLuna 资源，测试调用记录跨主环境与全部空间共享（筛选里的空间标识是记录字段而不是定域），三者的适配器都不注入；调试记录那道则注入，它的工厂与工作区端口的工厂收同一个「解析当前空间标识」的实参，并共用同一份隐式定域实现——「显式定域优先」是一条规则而不是两条，抄成两份之后其中一份被改动不会有任何红灯。定域发生在适配器往请求里注入的那一步，不是 interface 上的概念，因此它不构成与工作区端口「共享概念」，不影响判据。

装配侧因此少了一份宽端口。页面此前构造两份工作区端口，一份跟随当前活动空间、一份不定域；不定域那份唯一的消费方是 AI 测试空间总览的缩略图，它必须能越过隐式定域读任意空间的头像媒体。拆完之后它只需要场景那一道，从 38 个成员降到 21 个，这是拆分的自然结果而不是另一处改动。三道不定域的记录域端口不需要第二份实例——它们的适配器根本不注入空间标识，构造一次就够。

**不按成员数或文件大小设守卫。** 拆分依据是能力归属，一条尺寸规则会逼出为了达标而做的拆分，与上面两条判据相反。既有那条「收发 Koishi RPC 的函数只允许出现在客户端端口适配器里」按 `koishi-port.ts` 判定持有者，新增适配器自动落在模式内，不需要为拆分新增任何规则。

端口三件套的文件名后来去掉了能力前缀：能力标识由所在目录承担（`client/<能力>/koishi-port.ts`），文件名里再写一遍是同一个事实的第二份声明，改目录不改文件名就会分叉。守卫的判定形状因此从 `koishi-<能力>-port.ts` 收窄成 `koishi-port.ts`——仍是规则制，且比原来更严：原模式会把任意 `koishi-任意词-port.ts` 认作合法 RPC 持有者，收窄后只有能力目录里那一个约定名算。一条断言钉住每个持有 RPC 的能力目录都齐备这三个文件、且不存在带能力前缀的旧写法。
