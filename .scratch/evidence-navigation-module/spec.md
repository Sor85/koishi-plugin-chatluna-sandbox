# 证据导航统一 module 规格

Status: resolved

## Problem Statement

从预设工作台跳到模型请求变量、从聊天消息跳到模型请求、从轨迹账本跳到检查器再返回——这三条跨视图往返目前没有任何一个 module 拥有「完整往返」这一个概念。它被切成四个 module、六个散落各处的一次性触发编号,以及工作台与轨迹视图里手写的镜像状态。

用户能观察到的直接后果是一条缺陷:从预设工作台跳到模型请求变量后,左侧模型请求列表没有高亮选中行;如果目标记录超出列表首屏分页,列表里根本找不到它。详情面板和文本定位都正常,只有列表不对。从聊天消息进入的那条路径没有这个问题——它设置了列表选择保护,而预设那条路径没有。两条路径逐字重复了十四行进入逻辑,唯独这一处不对称。

维护者面对的是另一组问题。同一件事的编号发在三个不同层级:预设原点恢复的类型声明在 module 里,编号却由工作台 shell 用第二个计数器补上;详情内定位有两个互不知情的计数器喂同一个被观察的字段,撞号只是被中间一拍空值侥幸挡住;返回是否可用这个事实要在工作台 shell 里手工镜像进三处响应式引用,漏一处就静默失同步。四个 module 各有自己的测试文件,而「完整往返」这件事只有跨越它们才能断言,于是接线层——包括上面那条缺陷——一行测试都没有。

架构决策记录 0062 曾经把分散在三处的定位计数器收敛为 module 内部的一个,并把理由写进了决策。预设导航上线后,计数器又长回六个。

## Solution

建立一个反应式的证据导航 module,让它拥有跨视图往返的全部决策。

进入模型请求视图的意图统一为一个类型两种形态:必含空间归属与记录标识,可选携带证据定位段。携带证据段时进入到达闸门——只有目标详情标识匹配、轨迹处于单请求模式、且该记录确实在轨迹内,才交出定位请求并给出正在定位的进行态文案;不携带证据段时意图在打开记录后立即消费。原先两条路径各自决定筛选重置、页签、请求范围构造与三次读取,现在共用同一份进入状态,「一条有保护一条没有」在结构上不再可能出现。

module 独家发出四个语义互不重叠的一次性触发编号:打开某条记录、在已打开详情内定位到某条证据、恢复工作台内视图快照、恢复预设工作台原点。它们不合并成一个,因为四个消费者是不同组件、在不同时机等待不同的事;但详情内定位的三个来源——预设跳转、轨迹账本选中行、组成分段点击——全部从同一个发号源取号,撞号因此在结构上不可能。

module 以响应式引用暴露状态,工作台 shell 不再手工镜像返回是否可用。筛选、页签、选中记录与状态文案继续由视图持有,module 只交出该进入什么状态的数据。唯一移交的视图侧时序是「本次筛选变化不清空导航选中」这个一次性令牌:它与统一进入状态绑定,消费即失效,原先用来对齐两个 module 的那次帧后回调随之删除。

## User Stories

1. As a 模型请求复盘人员, I want 从预设工作台跳到模型请求变量后左侧列表高亮目标记录, so that 我知道当前详情对应列表里的哪一条
2. As a 模型请求复盘人员, I want 目标记录超出列表首屏分页时仍出现在列表里, so that 我能在左侧继续切换到相邻请求
3. As a 模型请求复盘人员, I want 从聊天消息进入模型请求时列表行为与从预设进入完全一致, so that 我不需要记住两条入口的差别
4. As a 模型请求复盘人员, I want 从预设工作台跳转后详情自动切到分析页签, so that 我不必手动找到证据所在的视图
5. As a 模型请求复盘人员, I want 跳转过程中看到正在定位的进行态提示, so that 我知道页面正在等待详情与轨迹到达
6. As a 模型请求复盘人员, I want 定位成功后提示变为已定位, so that 我确认高亮的文本就是预设表达式的展开结果
7. As a 模型请求复盘人员, I want 定位失败时得到明确说明而不是停在进行态, so that 我知道请求已打开但精确文本无法标记
8. As a 模型请求复盘人员, I want 从聊天消息进入模型请求时不显示定位提示, so that 界面不暗示还有一步没完成
9. As a 模型请求复盘人员, I want 只有目标详情与轨迹都到达后才开始定位, so that 定位不会作用在上一条记录上
10. As a 模型请求复盘人员, I want 轨迹处于会话模式时不误触发单请求定位, so that 跨请求聚合视图不会跳到错误的证据
11. As a 模型请求复盘人员, I want 返回预设工作台时列表滚动位置被恢复, so that 我回到原来正在读的那个预设文档
12. As a 模型请求复盘人员, I want 返回预设工作台时搜索词被恢复, so that 我不需要重新输入筛选条件
13. As a 模型请求复盘人员, I want 返回预设工作台时源码编辑器滚动位置被恢复, so that 我回到原来正在看的那一行表达式
14. As a 模型请求复盘人员, I want 从轨迹账本进入检查器后可以返回轨迹, so that 我能继续按顺序检查其他行
15. As a 模型请求复盘人员, I want 返回轨迹时原选中行被恢复, so that 我知道刚才看到哪一行
16. As a 模型请求复盘人员, I want 返回轨迹时账本滚动位置被恢复, so that 长轨迹不会回到顶部
17. As a 模型请求复盘人员, I want 返回轨迹时详情面板滚动位置被恢复, so that 右侧不会停在顶部
18. As a 模型请求复盘人员, I want 返回轨迹时页签与轨迹模式被恢复, so that 视图状态与离开时一致
19. As a 模型请求复盘人员, I want 跨请求返回时等目标详情真正到达后才恢复视图, so that 中途的详情变更不会把恢复消费在错误的记录上
20. As a 模型请求复盘人员, I want 同时可从轨迹和预设返回时返回按钮指向最近一次离开的位置, so that 返回行为符合我的直觉
21. As a 模型请求复盘人员, I want 点击轨迹账本行触发的定位与预设跳转触发的定位互不干扰, so that 两种操作不会互相吞掉
22. As a 模型请求复盘人员, I want 点击请求组成分段触发的定位正常生效, so that 组成图仍然是可点击的导航入口
23. As a 模型请求复盘人员, I want 连续多次跳转每次都真的重新定位, so that 重复点击同一个表达式不会静默失效
24. As a 模型请求复盘人员, I want 自动刷新期间导航状态不被打断, so that 进行中的请求刷新不会取消我正在进行的跳转
25. As a 模型请求复盘人员, I want 用户主动点选其他请求时取消待处理的跳转, so that 我的操作优先于自动跳转
26. As a 模型请求复盘人员, I want 切换到其他视图后再回来不残留上次的跳转意图, so that 旧意图不会突然生效
27. As a 预设编辑者, I want 从预设表达式跳转再返回后仍能继续编辑, so that 复盘不打断我的编辑流程
28. As a 维护者, I want 跨视图往返由一个 module 拥有, so that 时序缺陷集中在一处而不是分散在四个 module 与两个视图里
29. As a 维护者, I want 进入模型请求视图的逻辑只有一份, so that 新增入口不需要复制十四行并记得带上列表选择保护
30. As a 维护者, I want 进入模型请求视图必然带上列表选择保护, so that 预设路径那类漏掉保护的缺陷在结构上不可能再出现
31. As a 维护者, I want 每个一次性触发编号由拥有该决策的 module 自己发出, so that 不再有类型声明在一处而编号补在另一处的反常
32. As a 维护者, I want 详情内定位的三个来源共用同一个发号源, so that 两个互不知情的计数器撞号的风险被结构性消除
33. As a 维护者, I want 四个编号语义互不重叠, so that 每个消费者不必判断这一次轮不轮到自己
34. As a 维护者, I want 返回是否可用作为响应式事实暴露, so that 工作台 shell 不再手工镜像它并可能漏掉一处
35. As a 维护者, I want 视图状态的赋值继续留在视图里, so that module 不需要 adapter 也不碰 DOM
36. As a 维护者, I want 一次性令牌与统一进入状态绑定, so that 它不再需要靠帧后回调与另一个 module 对齐
37. As a 维护者, I want 模型请求列表选择 module 只保留普通选择与跨页补入, so that 它的 interface 不再混装导航令牌
38. As a 维护者, I want 四个旧 module 的测试合并为一个, so that 完整往返这件事第一次有地方断言
39. As a 维护者, I want 往返 module 不依赖 DOM 与帧时序原语, so that 它可以在没有浏览器环境的测试里被完整驱动
40. As a 维护者, I want 证据导航与证据定位的分工被记录下来, so that 下一次架构评审不会把两者的形状差异当成不一致来修

## Implementation Decisions

### module 边界

新建证据导航 module,取代原先的预设证据导航、预设导航协调器、证据返回栈与模型请求导航四个 module。它拥有:

- 意图发布与消费
- 到达闸门
- 返回栈
- 预设原点快照与恢复
- 「本次筛选变化不清空导航选中」一次性令牌
- 「该进入什么视图状态」这份数据

它不拥有筛选、页签、选中记录与状态文案本身——那些继续由视图以响应式引用持有,由视图在应用进入状态时写入并发起读取。这条分工沿用架构决策记录 0062 对展开状态的处理:出错的始终是时序与保护,不是赋值。

### 意图形态

一个意图类型两种形态。必含字段是空间归属与记录标识;可选字段是证据定位段,含证据标识与可选的文本范围。

携带证据段时走到达闸门,闸门三个条件全部满足才交出定位请求:目标详情标识与意图记录标识相同、轨迹处于单请求模式、该记录在轨迹记录集合内。闸门只交出一次,已交出后不重复。不携带证据段时意图在打开记录后立即消费。

进行态文案由是否携带证据段决定:携带时显示正在定位,不携带时为空。

### 四个一次性触发编号

module 独家发出四个编号,视图与工作台 shell 不再持有任何计数器:

- 打开某条记录
- 在已打开详情内定位到某条证据
- 恢复工作台内视图快照
- 恢复预设工作台原点

不合并成一个。四个消费者是不同组件、在不同时机等待不同的事:工作台内恢复必须等目标详情按记录身份到达,预设原点恢复在视图切换后立即生效。合并会迫使两个组件观察同一个编号并各自判断这一次轮不到自己。

详情内定位的三个来源——预设跳转、轨迹账本选中行、请求组成分段点击——全部从同一个发号源取号。原先外部来源旁路了视图本地计数器,两个互不知情的计数器喂同一个被观察字段,撞号只被中间一拍空值侥幸挡住。

预设原点恢复的编号由 module 的返回动作自己发出,不再由工作台 shell 用第二个计数器补上。

### 反应式形状

module 以响应式引用与计算属性暴露状态,包含待处理意图、定位请求、两种恢复快照与返回是否可用。这与架构决策记录 0062 让证据定位保持纯数据加 adapter 的选择相反,理由是两者面对的外界不同:定位唯一关心的事实是目标最终停在哪个滚动位置,那需要真实布局,因此必须能被数字化假 adapter 驱动;导航一行 DOM、一个帧时序原语都不碰,反应式暴露后工作台 shell 不再需要把返回是否可用手工镜像进三处引用。

### 列表选择保护

一次性令牌从模型请求列表选择状态移交给导航 module,并与统一进入状态绑定:进入状态本身声明这是一次导航选中,令牌随之生效,被筛选变化消费一次后失效。视图的筛选侦听器在清空选中前先向导航 module 询问。

原先用来对齐两个 module 的帧后回调、列表选择状态上的令牌字段,以及释放令牌的函数,一并删除。模型请求列表选择 module 收窄为普通列表选择与「用权威详情补入超出首屏分页的目标记录」两件事。

### 缺陷修复

从预设工作台进入模型请求的路径原先只设置选中记录,没有取得列表选择保护,也没有登记跨页补入所需的导航记录标识。两条路径都会把筛选分类从默认值改为按空间,必然触发筛选侦听器清空选中。统一进入状态后两条路径取得完全相同的保护。

### 领域词汇与架构决策

新增「证据导航」词条,并收紧「证据定位」词条——后者原文包含「在返回时恢复原视图与滚动位置」,那部分已移交导航。两个词条互列避免用词。

新增架构决策记录,说明证据导航与证据定位的分工、四个编号各自的语义与不合并的理由、以及为什么导航 module 反应式而定位 module 坚持纯数据加 adapter。架构决策记录 0062 本身不修改。

## Testing Decisions

### 什么算好测试

只断言从 module interface 观察得到的外部行为:给定一次跳转、一次详情到达、一次筛选变化、一次返回,module 交出什么意图、什么定位请求、什么恢复快照、哪个编号递增了。不断言内部调用次数,不断言源码文本。

### 主 seam

新建的证据导航 module。候选的全部可断言行为都在这里:意图两种形态、闸门三个条件、返回栈按记录身份消费、原点快照自带编号、令牌与进入状态绑定、四个编号各自单调。

seam 净变化为四减到一:四个旧 module 的 seam 消失,新增一个。

Prior art:现有工作区控制模块测试——三十个行为测试打在同样形状的响应式组合式 module 上,是仓库里质量最高的客户端测试。四个旧测试文件的断言整体迁入新测试文件。

### 关键新回归

新回归**不是**「令牌规则是否生效」——那已有四个既有用例覆盖。新回归是「进入模型请求视图必然带上保护」:两条路径共用同一份进入状态后,断言两者交出的进入状态在保护标记上完全一致,使一条有保护一条没有在结构上不可能。这才是原先漏掉的那一层。

### 辅 seam

模型请求列表选择 module。interface 收窄后,既有四个令牌用例中规则部分迁往导航 module,跨页补入部分留下。

### 不新建的 seam

进入状态被视图正确应用、四个编号的消费者真的动了,没有 seam。依架构决策记录 0062 不引入 jsdom、happy-dom 或组件挂载测试,由浏览器手工验证承担。

### 验收

单元测试、类型检查与构建全绿,外加三条路径各走一遍浏览器:

- 预设工作台到模型请求变量再返回,含列表高亮、超出首屏分页的目标记录补入、返回后列表滚动、搜索词与源码编辑器滚动恢复
- 聊天消息到模型请求,含列表高亮与跨页补入
- 轨迹账本到检查器再返回,含选中行、账本滚动、详情滚动与页签恢复

第四个编号——详情内定位——走的是架构决策记录 0062 既有的浏览器验证路径,不重复。

## Out of Scope

- 证据定位 module 本身。它的 adapter 十八个成员中有十个只是响应式引用搬运,seam 偏宽,属于另一条候选。
- 模型请求工作台里其余的响应式镜像与加载状态包装。它们与导航无关。
- 模型请求对话视图内部消息计数与工具计数口径不一致。
- 共享模型证据投影的边缘问题,包括概览格计数、预设表达式观察值与按记录身份的记忆化。
- 视图状态赋值搬进 module。明确不做,由架构决策记录 0062 的分工排除。
- 引入 jsdom、happy-dom 或组件挂载测试。
- 导航相关的界面文案、图标与布局调整。进行态与已定位文案沿用现有措辞。
- 浏览器历史与地址栏集成。证据导航不是页面路由。

## Further Notes

- 本规格取代的四个 module 共约二百零八行,对应测试共约二百二十四行。合并后的 module 预期不会显著更小——收益不在行数,而在于「完整往返」第一次有唯一拥有者与唯一测试面。
- 已核实的缺陷是从代码读出的,未在浏览器复现。复现需要一条预设表达式恰好匹配到超出首屏分页的模型请求。验收阶段的第一条浏览器路径同时承担复现与验证。
- 架构决策记录 0062 记录过同一类收敛——三个分散的定位计数器合并为 module 内部的一个。本规格是把同一条纪律用在后来新增的预设导航上,而不是推翻它。
- 领域词汇与架构决策记录的改动已经先行落地,与本规格同批提交:两者互相引用,分开提交会让其中一半悬空。
- 分支与提交:依仓库规则不自行创建分支、不自行提交。
