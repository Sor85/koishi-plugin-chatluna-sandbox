# 01 — 建立证据导航 module 并统一进入模型请求视图的路径

**What to build:** 从预设工作台跳到模型请求变量后,左侧模型请求列表正确高亮目标记录;目标记录超出列表首屏分页时,被权威详情补入列表。这条已核实的缺陷因此修好,而且是结构性修好——从聊天消息进入与从预设工作台进入共用同一份进入状态,不可能再出现一条路径有列表选择保护、另一条没有。

新建证据导航 module,取代预设证据导航、预设导航协调器与模型请求导航三个 module。它拥有跨视图往返的意图发布与消费、到达闸门、预设工作台原点快照与恢复,以及「本次筛选变化不清空导航选中」这个一次性令牌。进入模型请求视图的意图统一为一个类型两种形态:必含空间归属与记录标识,可选携带证据定位段;携带时走到达闸门并显示正在定位的进行态,不携带时打开记录后立即消费。

module 以响应式引用暴露状态,工作台 shell 不再手工把返回是否可用镜像进多处引用。筛选、页签、选中记录与状态文案继续由视图持有,module 只交出「该进入什么状态」的数据,由视图写入并发起读取。

三个一次性触发编号归入 module:打开某条记录、在已打开详情内定位到某条证据、恢复预设工作台原点。轨迹视图原本持有的本地定位编号消失——详情内定位的三个来源（预设跳转、轨迹账本选中行、请求组成分段点击）从同一个发号源取号,两个互不知情的计数器喂同一个被观察字段的撞号风险因此在结构上消除。预设原点恢复的编号由 module 的返回动作自己发出,不再由工作台 shell 用第二个计数器补上。

工作台内视图返回栈本票不动,它的编号是唯一残留的外部计数器,由下一票收走。

## 实现记录

- 实现落点：`client/webqq/evidence-navigation.ts`（`createEvidenceNavigation()`，反应式 module）。
- 进入状态 `ModelRequestEntryState` 由 `enterFromMessage` / `enterFromPreset` 共同产出，视图侧 `applyEntryState()` 是唯一应用点。
- `applyEntry(seq, filtersChanged)` 的第二个参数是视图唯一知道而 module 不知道的事实：进入状态写入筛选后筛选值是否真的变了。没变时 Vue 侦听器不会触发，令牌必须当场失效，否则会挡掉下一次用户主动改筛选的清空。
- 闸门那一次定位写入 `locateRequest`，账本与分段的定位只取号、由发起它们的视图自己持有；两者因此不会互相吞掉。
- 浏览器验证（Chrome，`http://127.0.0.1:5140/chatluna-sandbox`）：
  - 用 `git stash` 取 HEAD 基线复现缺陷：预设跳转后 `is-selected` 与 `aria-current="true"` 均为 0；恢复改动后两者都为 1。
  - 正序排列使目标记录（2026-08-25 07:24:39）落在首屏 50 条之外，跳转后它被权威详情补入列表首位并高亮，可继续点选相邻请求。
  - 从聊天消息右键「跳转到对应请求」进入：列表同样高亮，无定位提示文案，无返回按钮。
  - 手动改排序时选中被正常清空，证明令牌只挡住导航那一次。
