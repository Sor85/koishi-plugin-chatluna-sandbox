# 插件装配只写一份，端点可用性变成一个值

Status: ready-for-agent

## Problem Statement

测试控制端点起不来的时候，插件走的是一份复制品。

插件入口里，构造 MCP 服务与监听器这一段包在 `try` 里，`catch` 里又抄了一整套装配：注册 Console、注册启动钩子、注册关机收尾。两份唯一的实质差别是给 Console 注册时传不传 MCP 服务、以及有没有那一次启动与停止。十五行重复。

这份重复已经长出差异了：关机收尾那一段解释「Koishi 的 dispose 不可等待，收尾写入的失败只能进日志而不是被静默丢弃」的注释只存在于主路径那一份，降级那一份没有。注释记的是一条改坏了不报错的规则，而它今天只保护两份拷贝里的一份。

降级这条路从来没有人跑过：插件入口没有任何测试，也没有手工验证的记录。而它实际存在的理由只有一处——构造 MCP 服务时建数据目录或读凭证文件失败。监听器的构造函数是纯字段赋值，抛不出东西。

还有一个隐患。Console 注册也在 `try` 里面。它抛出的话，`catch` 会用「测试控制端点初始化失败」这句与事实不符的文案记日志，然后**再注册一遍** Console 入口与全部监听器。

往装配里加一件「启动时要做的事」或「关机时要收尾的事」，今天要写两遍。漏掉降级那一份不会报错。

## Solution

先把端点求出来，再单路装配一次。

端点是否可用变成一个可空值：拿到了就带着 MCP 服务与监听器，没拿到就是空。装配代码只有一份，Console 注册照旧按「有没有 MCP 服务」传参，启动与关机各多一次可空调用。

部署者看到的东西不变：端点起不来时 WebQQ 照常可用，两种失败（构造失败与监听失败）各自的日志文案不变。沙盒用户看不到任何变化。

治理之后，加一件启动或收尾的事只写一次；两份拷贝之间悄悄长出差异的可能性归零；降级与主路径跑的是同一段代码。

## User Stories

1. As a 部署者, I want 测试控制端点起不来时 WebQQ 仍然完整可用, so that 一个可选能力的故障不会带走主功能
2. As a 部署者, I want 端点构造失败与监听启动失败各有自己的日志文案, so that 我知道是数据目录的问题还是端口的问题
3. As a 部署者, I want 数据目录建不出来或凭证文件读不动时插件不整体崩掉, so that 我能先用起来再排查
4. As a 部署者, I want 两种协议都没启用时端点既不占端口也不报错, so that 不用这个能力的人不必配置它
5. As a 部署者, I want 非回环地址缺 TLS 时照常启动并持续告警, so that 局域网调试仍有路可走而风险有人告诉我
6. As a 部署者, I want 降级路径与主路径是同一段装配代码, so that 我在降级下遇到的问题不会是主路径没有的问题
7. As a 沙盒用户, I want 端点无论起没起，WebQQ 的界面与功能一字不变, so that 我不必关心服务端的可选能力
8. As a 沙盒用户, I want 开发模式下的 ChatLuna 错误预览记录照旧生成, so that 我在开发环境里仍看得到那批样例
9. As a 沙盒用户, I want 关机时未归属模型请求的收尾写入照旧完成, so that 关一次插件不会丢掉刚采集到的记录
10. As a 插件维护者, I want 装配只有一份, so that 改它的时候不必记得还有第二处
11. As a 插件维护者, I want 加一件「启动时要做的事」只写一次, so that 不会漏掉降级分支
12. As a 插件维护者, I want 加一件「关机时要收尾的事」只写一次, so that 收尾在两条路上必然一致
13. As a 插件维护者, I want 端点可用性是一个值而不是两条代码路径, so that 差异由数据表达而不是由控制流表达
14. As a 插件维护者, I want 「只有 MCP 服务、没有监听器」这个不可能的状态不可表达, so that 读装配代码时不必判断它会不会发生
15. As a 插件维护者, I want 那两行关于关机不可等待的注释只存在一份并且必然生效, so that 它保护的规则不再只覆盖两份拷贝里的一份
16. As a 插件维护者, I want Console 注册不会因为端点构造失败而跑第二遍, so that 入口与监听器不会被注册两次
17. As a 插件维护者, I want 两种降级模式仍然是两条各自的日志, so that 收拢不把两件不同的事合成一件
18. As a 插件维护者, I want 降级路径被真的跑过一次, so that 一段从未执行过的代码不再只靠阅读来相信
19. As a 插件维护者, I want 两份装配的逐行差异清单作为证据留下, so that 「差异只有三项」不是一句口头承诺
20. As a 插件维护者, I want 不为这次收拢新增测试 seam, so that 不引入在等价重构时变红、在真实回归时沉默的断言
21. As a 插件维护者, I want 不加一条判不准的守卫规则, so that 守卫的信号不被稀释
22. As a 插件维护者, I want 装配之外一行不改, so that 这次收拢是否纯结构性可以被证明

## Implementation Decisions

### 端点可用性是一个可空值

- 「造端点」这件事求值一次，成功时得到一个同时带着 MCP 服务与监听器的值，失败时得到空。
- 不拆成两个各自可空的值：那会让「只有 MCP 服务、没有监听器」这个不可能的状态变得可表达，而它们要么一起有要么一起没有。
- 不做「什么都不做的空端点」：那要实现两个空方法并把 MCP 服务造出来，而 Console 注册恰恰需要「没有就是空」这个语义——空对象在那里表达不出来，只会退化成再加一个字段说明自己是空的。
- 可空值不需要额外判空。监听器的启动在两种协议都没启用时自己就返回，停止在没有服务器时自己就返回，因此调用点只需要一次可选调用。

### `try` 只包住两次构造

- Console 注册、启动钩子注册、关机钩子注册移到 `try` 之外单路执行。
- 这不只是整齐。今天 Console 注册在 `try` 里面，它抛出会导致降级分支用与事实不符的文案记日志并把 Console 入口与监听器注册第二遍。收窄范围顺手消掉这一处。

### 一处明示的偏离

- 收窄之后，Console 注册抛出会直接冒出插件的 apply，而今天会被记成「测试控制端点初始化失败」并触发一次重复注册。
- 这是本轮**唯一**一处行为可能变化的地方，作为明示的偏离登记，不混进「纯结构性」。判断依据是今天那个行为本身不成立：文案与事实不符，且重复注册会让 Console 入口出现两份。

### 两种降级模式各自保留

- 端点**构造**失败：完全没有 MCP 服务，Console 注册时不传它，日志是「测试控制端点初始化失败；WebQQ 仍可继续使用」。
- 端点**启动**失败：MCP 服务仍然注册给 Console，只有监听器没起来，日志是「测试控制端点监听器启动失败；WebQQ 仍可继续使用」。
- 这是两件不同的事，收拢时各自的文案与可观察结果一字不变。不合并。

### 装配之外一律不动

- MCP 服务与监听器自身的 interface、配置项的形状、非回环缺 TLS 时照常启动并持续告警这条既有决定、逐字段构造传输配置这个刻意的写法，全部原样保留。
- 记录域目录的装配、预设服务的装配、模型请求采集器的安装都在 `try` 之前，本轮一行不碰。

## Testing Decisions

好的测试断言外部可观察的行为，而不是实现写法。本仓库的判据已经写下来了：肯定式实现细节断言在等价重构时变红、在真实回归时沉默。

**净新增 seam 数：零。**

### 为什么不给装配建测试面

- 装配的 seam 是插件的 apply，驱动它需要一个完整的 Koishi Context。仓库里没有这类测试，代价与收益不成比例。
- 把「造端点，失败就返回空」提成一个可测的函数看着像个便宜的 seam，但它要吃 Context 与整份配置，能断言的只有「构造失败时返回空并写了一条日志」——这正是 `try/catch` 字面上写着的东西，是典型的实现细节断言。
- 本轮真正的收益是 locality：装配只有一份。它由「差异清单」证明，而不是由断言证明。

### 证明手段

- **逐行差异清单。** 列出主路径与降级路径两份装配的全部差异，证明差异集合恰好等于三项——Console 注册的 MCP 服务实参、一次启动、一次停止——外加两行只存在于主路径的注释。这是本轮的主要证据。
- **完整测试、类型检查与构建通过。**
- **真跑两次。** 按项目重启规则完整重启一次开发环境，确认端点起来了、Console 注册了、WebQQ 可用；再把数据目录改成不可写强制走一次降级，确认日志文案与 WebQQ 仍可用。降级这一路今天从来没有人跑过，这是它第一次被执行。
- 验收后清理临时改动，把数据目录恢复原状。

## Out of Scope

- **给这个形状加守卫规则。** 「`try` 与 `catch` 各抄一份装配」没有可判定的形状，硬写只会得到一条判不准的正则；而把两份守卫引擎收成一份是另一条正在排队的候选，往里塞一条判不准的规则会拖累它。
- **写 ADR。** 本轮没有建立也没有推翻任何约束，只是把一份拷贝删掉。
- **端点自身的行为。** 门禁、配额、协议判定、TLS 处理一律不动。
- **配置项的形状。** 展示分组与监听器接口的对接写法是刻意的，原样保留。
- **`try` 之前那一大段装配的收拢。** 记录域目录、预设服务、模型请求采集器、用量关联都留在原处。
- **界面、文案、样式与交互的任何调整。** 除上面那一处明示偏离外没有行为变化。

## Further Notes

- 最值得做的不是少十五行，而是「两份之间悄悄长出差异」这件事已经发生过一次：关机收尾那两行注释只保护了两份拷贝里的一份。它不会报错，只会在某次真实的关机里静默丢掉一次写入失败的日志。
- 顺带被处理掉的是一个从未被触发过的隐患：Console 注册在 `try` 里面，它抛出会导致重复注册。收窄 `try` 的范围不是为了整齐，是为了这个。
- 这一轮不需要基线比对——装配代码没有输出，也没有测试。证据换成两份拷贝的逐行差异清单加上一次真实的降级执行。这与前几轮的手法不同，但性质相同：都是把「没变」从口头承诺变成可检查的东西。
- 降级路径的第一次真实执行本身就是本轮的一项收益。它今天只靠阅读来相信。
- 领域词汇不需要新词：「测试控制端点」「记录域」都已在册。
