# 预设目录读取放大规格

Status: resolved

## Problem Statement

打开预设工作台时,每个预设文档都被完整读取两次、被解析三次。

按目录读取的方法内部对每个 YAML 文件调用一次单文件读取,拿到完整的预设文档——正文与解析结果都在手上——然后只摘出五个元数据字段返回,把正文与解析结果丢掉。预设服务收到这份摘要后,立刻按文件名对同一批文件再读一遍。因此 N 个预设文档意味着 2N 次文件正文读取,以及 2N 次带源码位置映射的语法树解析,而后者要为每个模板表达式建立字符偏移,不是廉价操作。

第三次解析来自展示名称。服务层在呈现预设文档时,又用普通 YAML 解析把同一份正文解析一遍,只为取出核心预设的第一个关键词或角色预设的名称。而完整的语法树此刻已经在手上。

被丢弃的那个中间类型是这条链上最刺眼的一环:预设摘要是预设文档的真子集——后者直接继承前者——它存在的唯一理由是「按目录列举时返回轻量结果」,而它唯一的业务消费者拿到它之后做的第一件事就是重读同一批文件。轻量这个理由从未成立过。

维护者由此面对两条读取路径:一条按目录、一条按文件名,而前者内部调用后者。想知道"打开预设页会发生多少次磁盘读取"必须同时读懂两个方法和它们之间的摘要类型。

## Solution

让预设目录只被读取一次,并让展示名称成为解析产物而不是第三次解析的结果。

按目录读取的方法直接返回完整预设文档,预设服务不再重读。方法随之改名为「读取全部」——原来的名字暗示轻量列举,与它实际做的事不符:它一直都在读取并解析全部内容。文件正文读取与语法树解析因此各从 2N 降到 N。

预设摘要类型删除,它的字段合进预设文档。一个没有消费者的中间类型比没有类型更容易误导:留着它,读者会以为仍然存在一条轻量读取路径。

展示名称成为文档解析的产物,与模板字段、表达式、诊断并列。核心预设的第一个关键词与角色预设的名称都是 YAML 字段,读出来就是解析行为;完整语法树已经在手上,不需要再跑一遍普通解析。第三次解析因此消失。

读取保持串行,遇到不安全文件时继续跳过而不是让整个目录读取失败。这条容错行为不变。

防御性拷贝不动。呈现预设文档时的三处结构化克隆是为了防止调用方改写内部状态,减少它需要先论证返回值不会被改写,风险与收益不成比例。

## User Stories

1. As a 预设编辑者, I want 打开预设工作台时每个预设文档只被读取一次, so that 预设数量增长时打开成本不会翻倍
2. As a 预设编辑者, I want 展示名称与改动前完全一致, so that 我在列表里认得出每个预设
3. As a 预设编辑者, I want 预设列表的排序与改动前完全一致, so that 我熟悉的位置不会变
4. As a 预设编辑者, I want 没有展示名称的预设仍然按文件名排在正确位置, so that 缺少关键词或名称的预设不会跑到列表意外的地方
5. As a 预设编辑者, I want 核心预设的展示名称仍然取第一个关键词, so that 与 ChatLuna 的呈现保持一致
6. As a 预设编辑者, I want 角色预设的展示名称仍然取名称字段, so that 与 ChatLuna 的呈现保持一致
7. As a 预设编辑者, I want YAML 有语法错误的预设仍然出现在列表里, so that 我能打开它并修复
8. As a 预设编辑者, I want YAML 有语法错误的预设不显示展示名称, so that 我不会看到从损坏内容里猜出来的名字
9. As a 预设编辑者, I want 目录里存在符号链接或非常规文件时预设列表仍然可用, so that 一个异常文件不会让整页打不开
10. As a 预设编辑者, I want 模板字段、表达式与诊断在列表与详情里保持不变, so that 表达式定位与编辑体验不受影响
11. As a 预设编辑者, I want 预设的修订标识、大小与修改时间保持不变, so that 并发保护与冲突提示仍然准确
12. As a 预设编辑者, I want 打开单个预设文档的行为不变, so that 从列表进入编辑器的路径不受影响
13. As a 预设编辑者, I want 新建、保存、重命名与删除预设的行为不变, so that 本次改动只影响读取
14. As a 维护者, I want 预设仓储只有一条读取路径的实现, so that 想知道打开预设页会产生多少次磁盘读取时只需读一个方法
15. As a 维护者, I want 按目录读取的方法名说明它读取完整内容, so that 调用方不会误以为它是轻量列举
16. As a 维护者, I want 没有消费者的中间摘要类型被删除, so that 读者不会以为还存在一条轻量路径
17. As a 维护者, I want 展示名称与模板字段、表达式、诊断同属解析产物, so that 从 YAML 内容派生的事实都由同一次解析交出
18. As a 维护者, I want 同一份 YAML 不再被解析三次, so that 新增解析需求时不会又长出第四次
19. As a 维护者, I want 展示名称在解析失败时的判定与文档诊断一致, so that 不存在两套"解析失败"的口径
20. As a 维护者, I want 每个预设文档只读一次这条不变式有测试守住, so that 将来有人重新引入重读时测试会变红
21. As a 维护者, I want 语法树解析次数也被断言, so that 有人绕开解析产物又加一次解析时测试会变红
22. As a 维护者, I want 不安全文件的跳过容错保持不变, so that 现有的健壮性不因本次改动退化
23. As a 维护者, I want 读取保持串行, so that 跳过容错的实现不必改成结果过滤
24. As a 维护者, I want 防御性拷贝不被本次改动触及, so that 返回值的可变性安全假设不变
25. As a 外部调用方, I want 预设目录读取的结果内容与改动前一致, so that 我不需要适配任何形状变化

## Implementation Decisions

### 仓储读取 interface

按目录读取的方法返回完整预设文档数组,并改名为「读取全部」。它不再内部调用单文件读取后丢弃结果,而是直接产出完整文档。

预设摘要类型删除,五个元数据字段合进预设文档。删除它的理由是它已无消费者:它存在的唯一目的是让按目录读取返回轻量结果,而唯一的业务消费者拿到后立刻重读同一批文件。

单文件读取方法保持不变,它仍是从列表进入编辑器时的读取路径。

### 预设服务

目录读取直接消费仓储交出的完整文档,不再按文件名重读。排序逻辑不变,仍按文档种类、展示名称、文件名依次比较。

### 展示名称

展示名称成为文档解析的产物,与模板字段、表达式、诊断并列。核心预设取第一个关键词,角色预设取名称字段,规则不变。

服务层不再独立跑普通 YAML 解析。

「解析失败时没有展示名称」这条判定必须与文档诊断保持一致的结论:现在它用普通解析的错误集合判断,改后要以文档解析的诊断为依据,不能出现"文档有诊断但展示名称仍被解析出来"或反之的情形。

### 保持不变的部分

- 读取保持串行。改并发要把不安全文件的跳过容错从异常捕获改为结果过滤,那是独立的性能决策,有实测需求时再提。
- 遇到不安全文件时跳过该文件、不让整个目录读取失败。
- 呈现预设文档时的三处防御性结构化克隆。减少它需要论证返回值不会被调用方改写。
- 新建、保存、重命名、删除四条变更路径,以及它们的并发保护与确认要求。

### 不做事前性能实测

本规格的依据是结构性重复——同一个文件读两次、同一份 YAML 解析三次——而不是实测耗时。次数是比耗时更稳定的指标:若实测只快了几毫秒就得出"不该修"的结论,那个结论是错的,因为收益在于读取路径只有一处、以及消灭一个立刻被丢弃的中间类型。

## Testing Decisions

### 什么算好测试

只断言从仓储与服务 interface 观察得到的事实。

读取次数属于 interface 而不是实现细节:按深模块词汇,interface 包含类型签名之外的不变式、错误模式与**性能特征**,「对每个预设文档只读取一次」正是性能特征。因此在测试中监视文件系统读取、断言 N 个预设文档恰好触发 N 次读取,断言的对象是 interface 的承诺,而监视只是手段。

不断言服务内部调用了仓储的哪个方法,也不断言源码文本。

### 主 seam

预设仓储的读取入口。返回完整文档、摘要类型消失、展示名称就位、不安全文件被跳过,都从这里观察。

Prior art:现有预设仓储测试已有并发、符号链接与 inode 替换用例,依赖真实文件系统。本规格沿用同一套装配,不引入内存文件系统——那些用例要验证的正是真实文件系统语义,无法替代。

### 辅 seam

预设服务的目录读取。展示名称、排序、以及"有语法错误的预设仍在列表里但没有展示名称"从这里观察。

### 次数断言

- N 个预设文档的目录读取恰好触发 N 次文件正文读取
- 同一次目录读取中,带源码位置映射的语法树解析恰好运行 N 次
- 目录读取过程中不再运行普通 YAML 解析

### 不测什么

具体耗时。次数已经覆盖本规格的全部承诺,而耗时受磁盘与环境影响,断言它会产生不稳定测试。

### 验收

单元测试、类型检查与构建全绿。

改动了服务端代码,浏览器验证前必须完整重启一次项目:确认旧进程与相关子进程已退出、监听端口已释放,重启后确认只有一个实例且加载的是当前构建产物。

浏览器验证:打开预设工作台,确认核心预设与角色预设的展示名称、列表排序与改动前一致,并确认一个没有展示名称的预设仍排在正确位置。排序**依赖**展示名称,派生偏差会表现为顺序变化而不是名字错误,这是单测不一定覆盖到的形态。

## Out of Scope

- 减少呈现预设文档时的防御性结构化克隆。当前是每个预设两次加每个表达式一次;真要优化应换成一次整体拷贝,且需先论证可变性安全。单列。
- 把目录读取改成并发。它会让不安全文件的跳过容错变绕,属独立性能决策。
- 引入可注入的文件读取器或内存文件系统。现有并发、符号链接与 inode 用例必须用真实文件系统。
- 预设文档解析本身的性能,包括源码位置映射的建立方式。
- 表达式词法分析在文档解析与证据匹配两处的重复实现。那是另一条摩擦点,涉及表达式序号契约,单列。
- 新增架构决策记录或领域词汇。本规格是内部实现收敛,没有跨模块的边界决策。
- 预设工作台的界面、文案与交互调整。

## Further Notes

- 架构评审对这条摩擦点的描述里有一处数字需要修正:结构化克隆不是无条件的 3N,而是 2N 加表达式总数——每个预设两次固定拷贝,再对每个表达式各一次。只有在每个预设恰好一个表达式时才等于 3N。若评审指的是静态调用点数量,那仍是三处。
- 现状是「N 次串行读取加 N 次并发读取」:按目录读取内部是串行循环,而服务层的第二次读取用并发。合并后保持串行,因此次数减半,但省掉的那一半原本是并发的。这是本规格明确接受的取舍。
- 预设仓储是本次架构评审中 depth 与 leverage 评价最高的两个 module 之一,它的并发与符号链接处理有 11 个真实用例。本规格不触碰那部分。
- 分支与提交:依仓库规则不自行创建分支、不自行提交。
