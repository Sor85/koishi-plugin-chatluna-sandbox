# 01 — 工具清单断言与 HTTP 错误信封

**What to build:** 端点提供哪些工具、每个工具属于哪个能力范围,成为测试直接陈述的事实。工具被误删、被误加、被改名、能力范围写错四种情况都会让测试变红——现在只有工具总数变化才会红。

三处断言工具总数的用例换成完整工具清单断言,内容包括每个工具的名字与能力范围,数量因此隐含。现有那份只列出部分工具名的清单合并进来,不再单独存在。清单断言同时是自文档化的:读测试就能看到测试控制端点提供哪些工具。

同时让 HTTP 传输层第一次真正调用一次工具。现有 HTTP 测试建立了真实 MCP 客户端,但只列举工具与资源,因此错误信封整体零断言;生成信封时读取的场景版本方法,唯一调用者就是这个未被验证的信封。本票经真实客户端调用一个超出凭证能力范围的工具,断言错误标记为真,且错误码、消息、追踪标识与场景版本就位。

重试等待时间不在本票内验证。它需要构造限流场景,属于凭证配额那条工作已经承诺的判据;本票验证信封的结构,那条验证限流的语义。

## Comments

完整工具清单写在 `tests/helpers/mcp-tool-catalogue.ts`，由测试侧独立书写而不从实现导入——从实现导入只能证明「实现等于自己」。三处数量断言换成对该清单的整体断言：

- `tests/mcp-service.test.ts` 能力目录用例断言名字与能力范围逐条一致
- `tests/mcp-service.test.ts` 按权限发现用例改为断言清单里 read 条目的子集，原先那份十条工具名清单不再单独存在
- `tests/console-mcp-call-records.test.ts` Console 能力目录同样断言完整清单
- `tests/mcp-http.test.ts` 传输层 `tools/list` 不携带能力范围，按名字与顺序比对完整清单

已实测把 `export_scene` 改名为 `export_scene_v2` 且能力范围从 read 改成 manage 后，上述四处断言全部变红，随后还原。

HTTP 错误信封用例经真实 MCP 客户端以只读凭证调用 `create_test_space`，断言 `isError` 为真，且信封携带 `permission_denied`、消息、`retryable`、`revision` 与 可对应到沙盒侧记录的 `traceId`；`revision` 由 `service.getRevision()` 读取，该方法此前唯一调用者就是这个未被验证的信封。`retryAfterMs` 按规格不在本票断言，只断言权限错误信封里不存在该字段。

### 发现并修复的缺陷（一条）

追踪标识此前对应不上任何记录。`src/mcp/server.ts` 生成信封时写的是当场 `randomUUID()`，而测试调用记录里根本没有 traceId 字段，两侧没有任何共同标识——User Story 22 的「我能把一次失败与沙盒侧记录对应起来」在实现上不成立。第一版用例只断言了 traceId 的 UUID 形状，那正是本规格拒绝的「字符串存在性冒充覆盖」，因此该缺陷差点被这张票自己掩盖过去。

改动的行为：`callTool` 捕获错误后把刚写下的测试调用记录 ID 回填到错误对象上（`SandboxMcpError.traceId`），传输层信封改为优先携带该 ID，仅在凭证校验阶段（还没有记录可指）退回随机标识。信封字段名与形状不变，变的是 traceId 的取值语义——它现在是可用于 `get_mcp_call_record` 的记录 ID。

用例相应改为断言对应关系本身：拿信封里的 traceId 调 `get_mcp_call_record`，断言取回的正是这次失败的记录（`tool`、`status: 'error'`、`errorCode`）。已实测把服务端改回 `randomUUID()` 后该断言变红（`record_not_found`），随后还原。
