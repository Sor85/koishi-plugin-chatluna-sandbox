# 03 — 交互类两个工具

**What to build:** 执行群操作与等待 ChatLuna 状态两个工具被真正调用。

执行群操作覆盖入群、邀请、退群、群管理与戳一戳。它属于交互能力范围,走机器人动作或用户交互的领域路径,因此要断言的不只是调用成功,还有操作确实改变了模拟 QQ 环境的相应事实,以及权限不足时被明确拒绝。

等待 ChatLuna 状态从事件游标开始等待,匹配到状态后返回。现有 ChatLuna 状态测试已有驱动状态广播的辅助函数,可直接复用来触发状态。要断言的是:从游标之前的旧状态不会被误认为当前结果、匹配条件生效、超时时返回未匹配而不是抛错。

调用全部经测试控制服务的工具调用入口。等待类工具在该入口上走独立的频率与并发分类,这条分类因此也被覆盖。

## Comments

两个工具的用例都在 `tests/mcp-tool-coverage.test.ts`，经 `service.callTool` 调用，并在已启动的 Koishi App 上运行，因此群通知与 ChatLuna 事件走真实事件流。

`perform_group_action` 断言的是模拟 QQ 环境的事实变化，而不是返回值形状：入群与邀请各产出对应子类型的待处理申请且申请人未直接入群、群主设置管理员后成员角色真的变成 admin、退群后成员从群里消失、戳一戳在群会话里留下 `event.type` 为 `poke` 的消息。越权路径断言普通成员设置管理员被拒，且领域层抛出的普通 `Error` 确实被归一为 `domain_error`——这条归一化行为只有经工具调用入口才测得到。

`wait_for_chatluna_state` 的实测语义与票面表述有一处需要澄清：该工具匹配的是 `control.getChatLunaStates()` 的当前状态，游标只用于校验 epoch，并不作为「只看游标之后的状态」的过滤条件。因此「游标之前的旧状态不会被误认为当前结果」按可观察行为断言为：本轮思考结束（thinking 落回 false）之后再等待 `thinking:true` 必须超时，历史上出现过的 thinking=true 不会被当成当前匹配。同一用例还覆盖会话过滤生效、超时返回 `{matched:false, reason:'timeout'}` 而不是抛错，以及过期 epoch 游标被 `cursor_expired` 拒绝。

状态广播辅助函数按判据要求真正复用：`emit` 与 Session 工厂从 `tests/chatluna-state.test.ts` 提取到 `tests/helpers/chatluna-state-broadcast.ts`，两个文件共用同一份实现，而不是各写一份。

未发现本票范围内的生产缺陷。
