# MCP 工具覆盖规格

Status: ready-for-agent

## Problem Statement

测试控制端点对外提供四十个工具,其中十五个从未被任何测试调用过。它们不是内部实现,而是外部测试控制器要依赖的对外契约。

覆盖缺口被一层数量断言掩盖了。三处测试断言工具总数为四十,这让工具清单看起来已被验证,实际上数量断言只在工具增删时变红——工具改名、语义变更、能力范围写错都不会红。其中五个未覆盖工具还出现在一份工具名清单断言里,那让它们看起来比其余十个更安全,而清单只证明名字存在。

未覆盖的十五个工具里,真正的风险在它们的领域约束上。重新激活 AI 测试空间只允许作用于已完成或失败的空间;标记失败只允许作用于运行中的空间;更微妙的是重新激活的身份归属——代码注释明确写着 WebQQ 重新激活代表用户接管,而测试控制端点重新激活必须归还原 AI 控制者,两条入口不能共用隐式默认身份。那条注释显然是修过缺陷留下的说明,却没有任何测试守住它。三个破坏性场景操作按既有决策必须先取得确认令牌,这条保障同样零验证。

HTTP 传输层的情况更彻底:没有任何测试经 HTTP 真正调用过工具。现有 HTTP 测试建立了真实客户端,但只列出工具与资源。因此错误信封——包含错误标记、错误码、消息、可重试标记、恢复建议、细节、重试等待时间、场景版本与追踪标识——整体零断言,而生成该信封时读取的场景版本方法,唯一调用者就是这个未被验证的信封。

## Solution

让十五个未覆盖工具各自被真正调用,并验证它们的领域约束;让 HTTP 传输层的错误信封第一次被断言;把三处数量断言换成完整工具清单断言。

工具调用全部经测试控制服务的工具调用入口,而不是下降到各自的领域服务。那个入口同时涵盖凭证校验、能力范围检查、限流分类、并发包装、幂等与调用记录;绕过它就测不到测试控制端点自己的错误归一化——任何非结构化错误都会被归一为领域错误码。

验证不止于「工具能调用成功」。只断言调用成功是最弱的覆盖形式,它比数量断言强不了多少,而本规格正是在修那类伪覆盖。因此空间生命周期的状态前提、重新激活的身份归属、破坏性操作的确认令牌保障都要一并断言。

数量断言换成完整清单断言,同时覆盖工具名与能力范围,一次抓住误删、误加、改名与能力范围写错四种情况,并且自文档化——读测试就能看到端点提供哪些工具。现有那份部分工具名清单合并进来。

HTTP 层验证信封结构:经真实客户端调用一个超出凭证能力范围的工具,断言错误标记为真且错误码、消息、追踪标识与场景版本就位。重试等待时间不在本规格内验证,它属于凭证配额那条工作——本规格验证信封的结构,那条验证限流的语义,两者不重复构造并发与限流场景。

补测试过程中发现的生产缺陷在本规格内修复,但每个修复单独记录改了什么行为。这些工具从未被调用过,存在真实缺陷的可能性不低;而对外契约的变更不能悄悄发生。

## User Stories

1. As a 外部测试控制器, I want 分页列出当前操作者可见会话的工具被验证过, so that 我依赖它编排测试时不必担心它从未运行
2. As a 外部测试控制器, I want 读取单个会话及其消息的工具被验证过, so that 我能确信返回的消息集合符合可见性规则
3. As a 外部测试控制器, I want 列出待处理好友与群申请的工具被验证过, so that 我能可靠地驱动关系申请测试
4. As a 外部测试控制器, I want 读取实现配置能力覆盖的工具被验证过, so that 我能据此判断某个 action 是否应当可用
5. As a 外部测试控制器, I want 导出版本化场景的工具被验证过, so that 我能把场景带到别处复现
6. As a 外部测试控制器, I want 执行群操作的工具被验证过, so that 入群、邀请、退群、管理与戳一戳都可依赖
7. As a 外部测试控制器, I want 等待 ChatLuna 状态的工具被验证过, so that 我能在状态到达后再继续断言
8. As a 外部测试控制器, I want 标记测试空间失败的工具被验证过, so that 失败路径与完成路径同样可靠
9. As a 外部测试控制器, I want 标记失败只作用于运行中的空间, so that 我不会误把一个已完成的空间改写成失败
10. As a 外部测试控制器, I want 重新激活测试空间的工具被验证过, so that 我能继续一个已经收尾的测试
11. As a 外部测试控制器, I want 重新激活只作用于已完成或失败的空间, so that 对运行中空间的误调用会被明确拒绝
12. As a 外部测试控制器, I want 经测试控制端点重新激活后控制权归还给我而不是变成用户接管, so that 我能立即继续修改场景
13. As a 外部测试控制器, I want 删除测试空间的工具被验证过, so that 我在明确需要清理时可以依赖它
14. As a 外部测试控制器, I want 删除后的空间不再出现在空间列表里, so that 我不会对已删除的空间继续发起调用
15. As a 外部测试控制器, I want 恢复初始场景的工具被验证过, so that 我能把环境还原到已知起点
16. As a 外部测试控制器, I want 清空场景的工具被验证过, so that 我能从空环境开始搭建测试条件
17. As a 外部测试控制器, I want 导入版本化场景的工具被验证过, so that 我能重放一个导出的场景
18. As a 外部测试控制器, I want 三个破坏性场景操作在没有确认令牌时被拒绝, so that 我不会因为一次误调用丢掉整个环境
19. As a 外部测试控制器, I want 清理 OneBot 调试记录的工具被验证过, so that 我能在测试之间重置证据
20. As a 外部测试控制器, I want 清理测试调用记录的工具被验证过, so that 我能控制记录的观察范围
21. As a 外部测试控制器, I want 超出凭证能力范围的调用在 HTTP 层返回结构化错误, so that 我的客户端能按错误码分支处理
22. As a 外部测试控制器, I want HTTP 层错误携带追踪标识, so that 我能把一次失败与沙盒侧记录对应起来
23. As a 外部测试控制器, I want HTTP 层错误携带当前场景版本, so that 我知道失败发生时环境处于哪个版本
24. As a 外部测试控制器, I want 工具清单的变更会让测试变红, so that 端点提供的能力不会在我不知情时改变
25. As a 维护者, I want 每个对外工具都至少被真正调用过一次, so that 不存在只被数量断言掩盖的工具
26. As a 维护者, I want 工具清单断言覆盖工具名与能力范围, so that 改名与能力范围写错都会被抓住
27. As a 维护者, I want 数量断言不再单独承担工具清单的验证职责, so that 它不会让缺口看起来已被覆盖
28. As a 维护者, I want 工具调用测试经测试控制服务的调用入口, so that 凭证校验、能力范围、限流分类、幂等与调用记录一并被覆盖
29. As a 维护者, I want 测试控制端点自己的错误归一化被覆盖, so that 非结构化错误确实被归一为领域错误码
30. As a 维护者, I want 空间生命周期的状态前提被断言, so that 那些约束不会在后续重构中被抹平
31. As a 维护者, I want 重新激活两条入口的身份差异被断言, so that 那条只写在注释里的规则获得测试保护
32. As a 维护者, I want 破坏性操作的确认令牌保障被断言, so that 既有决策的核心保障不再只存在于实现里
33. As a 维护者, I want HTTP 传输层至少有一次真正的工具调用, so that 该分支不再零覆盖
34. As a 维护者, I want 生成错误信封时读取的场景版本方法有测试经过, so that 它不再是一个零验证的调用
35. As a 维护者, I want 补测试过程中发现的缺陷被逐条记录, so that 这张票不会悄悄变成改行为的票
36. As a 维护者, I want 重试等待时间的验证留给凭证配额那条工作, so that 两处不重复构造限流场景

## Implementation Decisions

### 测试入口

工具调用全部经测试控制服务的工具调用入口。不下降到测试空间服务、控制服务或调试记录存储各自的方法——那样测的是领域服务而不是测试控制端点的工具,会漏掉能力范围检查、限流分类、并发包装、幂等处理、调用记录写入,以及非结构化错误被归一为领域错误码这条行为。

### 十五个工具按性质分组

- 读取类五个:分页列出可见会话、读取单个会话、列出待处理申请、读取能力覆盖矩阵、导出版本化场景
- 交互类两个:执行群操作、等待 ChatLuna 状态
- 空间生命周期三个:标记失败、重新激活、删除
- 破坏性场景操作三个:恢复初始场景、清空场景、导入场景
- 清理类两个:清理 OneBot 调试记录、清理测试调用记录

已核实三处让成本低于预期:标记失败与已被覆盖的标记完成共用同一实现,只差一个失败标记参数;三个破坏性场景操作共用同一个破坏性执行包装;三个空间生命周期工具共用同一个幂等包装。也已核实十五个工具全部有分派分支,不存在定义了但未实现的情况。

### 一并验证的领域约束

- 标记失败只允许作用于运行中的空间
- 重新激活只允许作用于已完成或失败的空间
- 经测试控制端点重新激活后控制权归还原 AI 控制者,而不是变成用户接管;这条区别目前只写在实现注释里
- 三个破坏性场景操作在缺少确认令牌时被拒绝
- 删除后的空间不再出现在空间列表里

删除测试空间那条「除非用户明确要求,否则测试完成后应默认保留」的说明**不纳入验证**。核实后它是写在工具描述里给外部测试控制器的指引,代码没有任何强制,调用即删除。它是文档性约定而不是可执行约束;断言描述文本包含该约定属于伪覆盖,正是相关工作正在消灭的模式。若认为删除应当需要显式确认,那是对外契约的行为变更,应单独提出并先判断它是否属于既有决策意义上的破坏性操作。

### 工具清单断言

三处数量断言换成完整工具清单断言,内容包括每个工具的名字与能力范围。数量因此隐含。现有那份部分工具名清单合并进来,不再单独存在。

清单断言同时抓住四种情况:工具被误删、被误加、被改名、能力范围写错。它也是自文档化的——读测试就能看到端点提供哪些工具。

### HTTP 层错误信封

经真实 MCP 客户端调用一个超出凭证能力范围的工具,断言错误标记为真,且错误码、消息、追踪标识与场景版本就位。场景版本是信封无条件包含的字段,因此一种错误即可覆盖它。

重试等待时间不在本规格内验证。它需要构造限流场景,而那属于凭证配额那条工作已经承诺的判据。本规格验证信封的结构,那条验证限流的语义。

### 发现生产缺陷时

在本规格内修复,但每个修复单独记录改了什么行为。这些工具从未被调用过,缺陷可能性不低;而对外契约的变更不能悄悄发生。

### 文档

不新增架构决策记录。本规格立的纪律是「数量断言不构成覆盖」,它与「源码文本不构成行为验证」是同一个错误的两种形态,应并入架构守卫那条工作尚未落地的决策记录,而不是独占一条。需要在那条工作的第一张票上增加一条判据。

领域词汇不变。

## Testing Decisions

### 什么算好测试

只断言从工具调用入口观察得到的外部行为:给定凭证与参数,工具返回什么、拒绝什么、错误码是什么、场景状态如何变化。不断言内部调用了哪个领域服务方法,也不断言工具描述文本。

尤其不接受以数量或字符串存在性冒充覆盖。工具总数为四十不证明四十个工具可用;工具名出现在某个清单里不证明它被调用过;描述文本包含某条约定不证明该约定被强制。

### 主 seam

测试控制服务的工具调用入口。它是覆盖本规格全部行为的最高既有 seam。不新增 seam。

Prior art:现有测试控制服务测试已经通过该入口调用工具并断言结果与权限拒绝。

### 辅 seam

HTTP 传输层的真实 MCP 客户端。现有 HTTP 测试已经建立真实客户端并调用过工具列举与资源列举,本规格加入第一次真正的工具调用。不新增 seam。

### 其他 prior art

- 等待 ChatLuna 状态:现有 ChatLuna 状态测试已有驱动状态广播的辅助函数,可直接复用
- 破坏性操作两步确认:现有测试控制服务测试已经取得过一次确认令牌
- 幂等:现有测试已经覆盖同一幂等键重复调用的行为

### 验收

单元测试、类型检查与构建全绿。

不做浏览器验证,除非某个缺陷修复触及 WebQQ 可见的空间控制状态——重新激活的身份归属正是这类,若修复改变了它,需要在 WebQQ 的 AI 测试空间总览上确认状态显示正确。

## Out of Scope

- 凭证配额的频率与并发行为,包括重试等待时间的取值。归凭证配额那条工作。
- 给删除测试空间增加显式确认参数。那是对外契约的行为变更。
- HTTP 层成功路径的信封。本规格只验证错误信封结构。
- 覆盖其余二十五个已被调用过的工具的额外场景。本规格只补零覆盖的十五个。
- 测试控制 API 版本递增。本规格不改变对外形状,除非某个缺陷修复必须改,那时依未发布阶段策略直接变更。
- 新增架构决策记录。相关纪律并入架构守卫那条工作的决策记录。
- 领域词汇调整。

## Further Notes

- 十五个未覆盖工具中,前五个读取类工具出现在一份工具名清单断言里。这比完全不出现更危险:清单让它们看起来已被覆盖,而清单只证明名字存在。
- 重新激活的身份归属那条规则只存在于实现注释里。注释的措辞表明它来自一次真实缺陷的修复,而修复没有留下测试。这是本规格最值得补的一条。
- 已核实生成错误信封时读取的场景版本方法,唯一调用者就是该信封;因此在 HTTP 层补一次错误调用,同时也让那个方法第一次被测试经过。
- 分支与提交:依仓库规则不自行创建分支、不自行提交。
