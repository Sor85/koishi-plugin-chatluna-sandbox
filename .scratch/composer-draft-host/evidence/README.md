# 证据：发送控件的 DOM 快照与光标快照

`caret-snapshot.mjs` 与 `compare.mjs` 是本 feature 的确定性回归脚本，逐票各跑一次。
运行环境是仓库外的完整 Koishi 开发环境（`http://127.0.0.1:5140/chatluna-sandbox`），
脚本依赖 Playwright，放在仓库外的临时目录里跑（`node caret.mjs <输出>`；`BROWSER=firefox` 切引擎）。

## 为什么要读光标

DOM 快照证明可见部分不变，但**光标位置在 DOM 快照里看不见**，而本 feature 一半的行为就是
光标落在哪。因此每个采样点同时读 `Selection` 的 anchorNode 与 anchorOffset：落在编辑器的第几个
子节点、节点类型、节点文本与偏移。

## 确定性

固定入口、按名字选会话（不按序号，避免会话排序变化）、固定操作序列、固定等待；全程不发送消息，
结束时切回私聊把草稿清空，因此可以反复运行、反复比对。

## 采样点

票 01 与票 02 用 15 个采样点：

群会话空态 → 点入输入框 → 输入两个字符 → 输入 `@` 打开候选 → 方向键移动候选 →
Enter 选中候选 → 退格一次 → 退格两次 → 左移一次 → 左移两次 → 右移一次 →
组字中「中文」 → 上屏后「中文」 → Escape → 切换会话后清空。

票 03 在 Escape 之后补 4 个：

选择两个附件（一张图 ＋ 一个多点文件名）→ 移除一个附件 → 粘贴一张图 → 发送后。

退格接管那次改动再补 4 个（脚本里的当前版本共 23 个），专为「提及夹在两段文本之间」这个形态——
前 15 个采样点里的提及都在末尾，删错光标看不出来：

第二次选中候选 → 提及后再输入正文 → 光标移回提及右边 → 两段文本之间的提及退格。

输入法那两个采样点派发 `compositionstart` ＋ `insertCompositionText` ＋ `compositionend`，
而不是用普通输入接口——普通接口走不到组字路径。

## 基线取法

- 票 01、票 02：`git stash push -u` 把工作区回到基线，等开发环境的 Vite 重新提供旧源码
  （用 `curl` 确认服务端返回的模块里已经没有新符号），跑同一个脚本，然后 `git stash pop`。
- 票 03 与退格接管：采样点变了，因此把基线整体切到 feature 动手前的提交
  （`git checkout e9ab03e`）重跑一次全部采样点，再切回来。

## 退格接管之后的两处 Selection 变化（不是行为变化）

可见部分（`editorHtml`、规范化后的整段 DOM、占位文案可见性、`data-empty`、发送按钮禁用态、
控件宽度、候选菜单）在 23 个采样点上两个引擎都逐字一致。变化只在 `Selection` 的内部表示：

| 引擎 | 采样点 | 基线 | 当前 |
| --- | --- | --- | --- |
| Firefox | 退格两次 | `DIV`, offset 1 | `#text`, offset 3 |
| Chromium | 两段文本之间的提及退格，及其后 6 个 | 锚点节点文本 `你好  `，offset 4 | 锚点节点文本 `你好   在吗`，offset 4 |

Firefox 那处是同一个视觉位置的两种坐标写法。Chromium 那处是节点切分不同：基线由浏览器删掉
芯片后留下两个相邻文本节点，当前实现按草稿重新渲染成一个合并节点；偏移两边都是 4，
也就是提及原来的位置。

## 顺带测出的浏览器口径差异（不是回归）

- 提及芯片在两个引擎里都是原子的：治理前一次退格删掉整块，从不留下半截 `@张` 文本。
  这条规则治理前由 `contentEditable = 'false'` 提供，现在由草稿宿主接管，两个引擎口径一致。
- 同一个视觉位置在两个引擎里的 `Selection` 写法可以不同（见上表 Firefox 那一行）。

## 脚本本身的一处限制

「粘贴一张图」这个采样点靠 `new ClipboardEvent('paste', { clipboardData })` 派发。
Firefox 不接受构造参数里的 `clipboardData`，因此那一步在 Firefox 里是空操作（附件数不变）。
基线与当前两次运行用的是同一份脚本，因此这个采样点在 Firefox 里仍然可比——它只是覆盖不到
粘贴路径。粘贴入口的行为由 `composer-attachments.test.ts` 的两条断言执行。
