# 发送控件的草稿宿主与发送编排下沉成模块

Status: ready-for-agent

## Problem Statement

WebQQ 工作台的发送控件里，最容易坏的那部分行为没有任何断言。

纯粹的 token 计算早就下沉了——插入提及、退格合并、判空、序列化都住在一个八十行的模块里，测得很足。但真正会出问题的不是 token 怎么算，而是**怎么把它和 contenteditable 对上**：从子节点遍历回读出草稿、把草稿渲染成节点、把光标放到第几个 token 的第几个偏移、输入法未上屏时不许读回、input 事件早于 Selection 更新时要等一拍。这两百多行全留在组件里，一条行为断言都没有。

它们的失效形态都是静默的。光标跳到开头、退格删掉半个提及、中文输入法上屏后前一个字符消失、方向键穿过提及时卡住——都不报错，只能靠人在界面上敲出来。而这个仓库没有组件挂载测试，所以唯一的「验证」手段是把组件源码读进来断言里面出现了某一行文本。发送控件的测试文件今天有六十三条这样的断言，它们在守卫的豁免清单里挂着，负责人一栏写的就是这一轮。

同一段脚本里还有三块同样没有断言的行为：附件采集（粘贴与选择两条入口、文件名拆分、base64 读取）、发送编排（单请求锁、错误文案、发完清草稿与附件并把焦点还回输入框），以及输入法状态在四处参与判定却不属于任何模块。

## Solution

把草稿与编辑器之间的桥接、提及菜单、附件采集与发送编排下沉成可以单独问的模块，光标与输入法的时序第一次成为可断言的事实。

用户看不到任何变化。输入、提及、退格、输入法上屏、附件、发送、焦点还原全部与今天一字不差。

治理之后，改发送控件的人能从测试里读出「输入法未上屏时不许读回草稿」这类规则，而不是从一句注释里；光标错位这类回归会在测试里当场报出来，而不是等用户敲出来。发送控件那条豁免随之消化。

## User Stories

1. As a 沙盒用户, I want 在输入框里打字、换行与删除的行为和今天一字不差, so that 一次结构性下沉不需要我重新适应输入
2. As a 沙盒用户, I want 输入 @ 后候选菜单照旧弹出与过滤, so that 提及某个参与者的操作不变
3. As a 沙盒用户, I want 方向键在候选菜单里上下移动、Enter 选中、Esc 关闭, so that 我不必改用鼠标
4. As a 沙盒用户, I want 候选菜单关着时 Enter 仍然是发送, so that 我的发送习惯不变
5. As a 沙盒用户, I want 选中一个候选项后光标落在提及之后而不是跳走, so that 我能接着往下打字
6. As a 沙盒用户, I want 退格删到提及边界时整块删掉而不是删掉半个, so that 我不会留下一截残缺的提及
7. As a 沙盒用户, I want 用中文输入法打字时未上屏的拼音不被当成正文读回, so that 上屏后不丢字也不重字
8. As a 沙盒用户, I want 输入法组字期间按 Enter 不触发发送, so that 我不会把拼音发出去
9. As a 沙盒用户, I want 输入一个字符后光标停在这个字符之后, so that 我不必每打一个字就重新点一次输入框
10. As a 沙盒用户, I want 从别处点「提及某人」后提及被插进当前光标处, so that 我不必自己找位置
11. As a 沙盒用户, I want 切换会话后输入框被清空, so that 上一条会话的草稿不会误发到这一条
12. As a 沙盒用户, I want 粘贴一张图片时它被当成附件而不是正文, so that 我不必先存盘再选文件
13. As a 沙盒用户, I want 选择文件与粘贴两条入口的附件表现一致, so that 我不必记住哪条路能用
14. As a 沙盒用户, I want 附件名很长时仍能看清扩展名, so that 我知道自己选对了文件
15. As a 沙盒用户, I want 移除单个附件与清空全部附件的行为不变, so that 我能改主意
16. As a 沙盒用户, I want 发送过程中按钮不接受第二次点击, so that 同一条消息不会被发两遍
17. As a 沙盒用户, I want 发送失败时看到错误文案而输入内容不丢, so that 我可以修一下重发
18. As a 沙盒用户, I want 发送成功后草稿与附件一起清空, so that 下一条消息从干净状态开始
19. As a 沙盒用户, I want 发送完焦点回到输入框, so that 我能连续发几条而不必重新点
20. As a 沙盒用户, I want 发送期间我切走了会话，焦点就不要被抢回来, so that 我在别处的操作不被打断
21. As a 插件维护者, I want 「从子节点遍历回读出草稿」有断言, so that 改动渲染结构时立刻看到红灯
22. As a 插件维护者, I want 「把光标放到第几个 token 的第几个偏移」有断言, so that 光标错位不再靠人敲出来
23. As a 插件维护者, I want 「input 事件早于 Selection 更新，必须等一拍再读回」这条时序能被驱动, so that 它不再只是一句注释
24. As a 插件维护者, I want 「输入法未上屏时不读回草稿、不发送、不开菜单」三条各有断言, so that 输入法相关的回归能被测出来
25. As a 插件维护者, I want 「这次按键有没有被候选菜单消费」由一个模块回答, so that Enter 到底发送还是选中不再由组件自己判
26. As a 插件维护者, I want 退格跨提及整块删除有断言, so that 这条判定不再只存在于实现里
27. As a 插件维护者, I want 附件采集的两条入口与 base64 读取能不起组件就驱动, so that 粘贴图片这类路径不必靠界面验证
28. As a 插件维护者, I want 发送编排的锁、错误文案与动作顺序有断言, so that 「发两遍」或「清空了却没还焦点」能被测出来
29. As a 插件维护者, I want 焦点该不该还回去仍由既有的焦点模块判定, so that 一份已经验证过的判定不被重新埋起来
30. As a 插件维护者, I want 光标位置在真实浏览器里被读出来比对, so that 「界面没变」不包含「光标悄悄变了」
31. As a 插件维护者, I want 组件的 props、emits、事件名与载荷一律不动, so that 下沉是否纯结构性可以被证明
32. As a 插件维护者, I want 发送控件那条守卫豁免被消化, so that 账本上少一条债务而不是多一条

## Implementation Decisions

### 四组行为，两个新模块

- **草稿宿主**拥有草稿与 contenteditable 之间的双向转换、光标读写、输入法状态、以及提及菜单。草稿与菜单必须同处一个模块：每次输入都要重算菜单、方向键要被路由给菜单、选中候选项又要写回草稿并移动光标——拆开会让两者之间的 interface 宽到没有意义。
- **附件采集**拥有粘贴与选择两条入口、文件名与扩展名的拆分、附件列表的增删清空、以及把文件读成 base64。它与草稿无关，与发送编排只有「发送时取文件列表」一条边。
- **发送编排**拥有单请求锁、错误文案与动作顺序：锁住、序列化、外发、无论成败都解锁、请焦点模块判断该不该还焦点、清草稿与附件。它只经三件窄接口使用草稿宿主——取序列化后的正文、清空、请求聚焦。
- 已有的纯 token 模块、焦点判定模块与提及文案模块都不动，新模块建立在它们之上。

### 注入形状按子问题分成两种

沿用已经落地的两种做法，不新造第三种：

- 带副作用、有时序的宿主操作走 adapter 接口：读回节点、渲染节点、读光标、写光标、等下一拍。测试用造假宿主驱动。
- 纯判定吃朴素结构：这次按键该做什么、退格该删到哪、菜单该不该开、候选该怎么过滤。这些不经过假宿主也能测，让它们经过只是白付成本。
- 一律不注入 DOM 类型，注入最小结构接口。

### 时序与输入法成为可断言的事实

- 「input 事件有时早于 Selection 更新，必须等一拍再读回草稿」今天是一句注释加一次 `nextTick`。下一拍经 adapter 注入，测试因此能驱动「input 已触发、Selection 尚未更新」这个中间态，断言草稿没有被过早读回。
- 输入法状态成为草稿宿主的一部分，而不是模板上两个内联赋值加四处散落的判定。三条规则各有断言：组字期间不读回草稿、不触发发送、不开候选菜单。

### 按键归属

- 草稿宿主回答「这次按键有没有被候选菜单消费」，组件只在未被消费时才走发送。菜单的打开状态住在草稿宿主里，让它回答是最短的路；让发送编排反过来去问菜单是否打开，会把好不容易切窄的那条边又拉宽。
- Enter、方向键与 Esc 三者的分流因此集中在一处，而不是散在模板事件绑定与两个处理函数之间。

### 焦点判定不动

- 「发送成功或失败后，仅在原会话、原操作者、原输入控件仍有效时才恢复焦点」已经是一个有断言的模块。发送编排调用它，不吸收它——吸收等于把一份已验证的判定重新埋起来。

### 组件的 interface 一律不动

- props、emits、事件名与载荷逐字不变。这不只是为了少改调用方：DOM 快照比对的前提就是界面不变，interface 同时在动，纯结构性就无从证明。

### 两张票

- 第一张是草稿宿主与提及菜单，含把那一条与用户切换栈有关的断言挪进它自己的测试文件——它本来就该在那儿。
- 第二张是附件采集与发送编排，阻塞于第一张：发送编排要经草稿宿主的接口取正文与清空，并行做会让同一段代码写两遍，也会让快照差异无法归因。

## Testing Decisions

好的测试断言外部可观察的行为，而不是实现写法。这个仓库已经把判据写下来了：肯定式实现细节断言在等价重构时变红、在真实回归时沉默。本规格不新增任何一条这样的断言。

**净 seam 数：新增三个模块 seam，去掉零个。** 目的就是让今天不可观察的行为变得可观察，seam 增加是意图而非代价。

### 主测试面：三个新模块自身的 interface

- 纯判定部分直接以普通单元测试驱动：按键分流、退格边界、菜单开合与过滤、文件名拆分、附件增删。
- 带副作用的部分用造假宿主驱动：读回、渲染、光标读写、等下一拍。先例是既有的滚动恢复模块（`measure` / `scrollTo` / `nextTick` / `frame` 四个方法的 adapter，测试逐帧驱动）与消息列表跟随控制器（帧调度与下一拍全部注入，五个用例逐帧驱动状态机）。
- 纯判定与朴素结构那一路的先例是指针分流模块：一个函数负责把 DOM 读数取成朴素结构，另外几个纯函数只吃结构。

### 复用的既有 seam

纯 token 计算、焦点判定与提及文案三个模块保持原样，新模块建立在它们之上，它们各自的测试一条不改。

### 纯结构性的证明：DOM 快照加光标快照

- DOM 快照证明可见部分不变，做法与上一轮相同。
- **但光标位置在 DOM 快照里看不见**，而这一轮一半的行为就是光标落在哪。因此另加一份 Playwright 交互脚本，在真实浏览器里读 `Selection` 的 anchorNode 与 offset，覆盖：输入一个字符后的落点、退格删掉整块提及后的落点、方向键穿过提及、选中候选项后的落点、以及中文输入法上屏。
- 输入法那一条必须派发 `insertCompositionText` 而不是用普通输入接口，否则走不到组字路径。
- 每张票各跑一次，不最后统一跑：快照差异只会告诉你哪里变了，不会告诉你是哪次改动干的。
- 浏览器会话与工具生成的临时目录按仓库规则在验收后清理；基线快照作为票的证据留在本 feature 目录下，不进仓库源码。

### 断言处置

- 逐条分类沿用仓库既定的五类与判据，分类表落盘在本 feature 目录，实施前核对断言总数与分类时一致，**先删除再拆分用例**——先拆会让行号整体位移，表随即失效。
- 删补不一对一，但凡一条断言确实声称保护某个用户可见行为，必须先有下沉后的行为断言接上才允许删。
- 保留的样式文本、DOM 结构与用户文案断言按主题归入现有用例，上方块注释注明类别与依据；用户可见文案改由既有的显式辅助函数表达。
- 七个用例里只拆那个三十一条混了三个主题的（回复上下文、附件浮层、内联提及），其余六个都在十三条以内且主题单一，重拆只会制造无意义的 diff。
- 落地后消化发送控件那条守卫豁免。

### 别处变红的处置

逐条区分真红与假红——函数改名导致的跟着改标识符是假红，行为口径或成本结构变化导致的是真红，停下来查——并在票的 Comments 里逐条记处置。

## Out of Scope

- **用户切换栈**。它是发送控件脚本里另一大块——头像组的排序、折叠与展开的度量、布局动画、悬停与聚焦态、以及在其中创建普通用户和机器人。它与草稿、光标、发送毫无关系，自己就有二十来个函数加一套布局动画，并且守卫豁免清单里有它自己的条目与负责人。本轮只顺手把一条落错文件的断言挪回去。
- **布局观察**。`ResizeObserver` 驱动的紧凑模式与把发送区高度外发给消息列表做内边距。紧凑模式直接喂用户切换栈的度量，纳入等于把那个候选拽进来一半。
- **引入 jsdom、happy-dom 或组件挂载测试**。这是一条已经记录在案的决定，本轮不重开。
- **组件 interface 的调整**。props、emits、事件名与载荷一律不动；想调整是另一件事。
- **纯转发管道与薄状态**。把环境管理事件原样转出去这类一行函数，跑删除测试不集中复杂度，只搬家。
- **界面、文案、样式与交互的任何调整**。本轮没有行为变化，一处例外都没有。
- **提及候选的来源与过滤口径**。候选列表由上层模型给出，本轮只搬运「菜单什么时候开、按键怎么路由」，不改谁能被提及。
- **附件的上传与媒体存储**。本轮只到「读成 base64 交给外发事件」为止，服务端那一侧不动。
- **源码断言归零**。样式文本、DOM 结构与用户文案三类按仓库判据合法保留。

## Further Notes

- 这一轮是上一轮明确留下的续篇：守卫豁免清单里发送控件那条的负责人一栏写的就是本轮，理由是「该文件断言的组件行为尚未下沉，这些断言是它当前行为的唯一记录，在对应 interface 抽出来之前删掉是净损失」。顺序因此必须是先抽 interface 再删断言。
- 最值得做的不是删掉多少条断言，而是四条今天只写在注释里或散在模板绑定上的规则第一次成为可断言的事实：input 早于 Selection 更新要等一拍、输入法组字期间不许读回草稿、退格到提及边界要整块删、Enter 到底是发送还是选中候选。这四条改坏了都不报错，只会让用户觉得「输入框有点怪」。
- 与上一轮最大的差别是证明手段多了一层。上一轮验证的是渲染结果，DOM 快照够用；这一轮一半的行为是光标位置，快照里完全看不见，因此必须在真实浏览器里读 `Selection`。这层基建与上一轮共用，只是脚本多读一个快照。
- 两张票各跑一次完整测试、类型检查与构建，外加一次 DOM 快照与一次光标快照比对。完整 Koishi 开发环境在插件仓库之外，起环境时要按路径清理旧进程与 worker，不是零成本——仍然每张都跑。
- 发送控件测试文件现有六十三条肯定式断言，其中只有一条与用户切换栈有关；用户栈自己的测试文件有十九条，留给它自己的候选。分类基数按五类口径重新统计，不要沿用「肯定式条数」这个数字当作可删量。
