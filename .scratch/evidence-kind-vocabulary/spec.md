# 证据种类词汇统一规格

Status: ready-for-agent

## Problem Statement

同一份证据分类目前被七套互不相关的词汇描述,四张标签表在同一屏上给出同一种证据的三种说法。

在模型请求轨迹视图里,一条工具定义证据同时出现在四个位置:证据种类过滤开关显示 `TOOL DEFS`,轨迹账本的种类列显示 `TOOL DEFS`,请求组成图的图例与分段显示 `Tool Defs`,而嵌在检查器里的分析导航分组显示 `Tool`。两处都没有排版层面的大小写转换,这三种写法是硬编码在字符串里直接呈现给用户的。

比大小写更实质的是粒度不一致。分析导航把工具合并成一个分组;组成图合并成两档,把工具调用与工具结果算作一类;过滤开关与轨迹账本分成三档。用户要在三种粒度之间自己建立映射,才能确认这四处说的是同一件事。分析导航的标签表内部还中英混杂:同一张表里前五项是英文,响应那一项是中文。

维护者面对的是七套词汇:共享模型证据投影内部有消息角色与响应事件种类两套;服务端轨迹派生有轨迹行种类加工具事件副字段、以及请求组成种类两套;客户端有分析导航分组键加条目种类、证据过滤种类、对话卡片角色三套。新增一个视图就会长出第八套,而客户端的证据过滤模块里三个函数的全部工作就是在这些词汇之间做翻译。

同一病因还产生了一处用户可见的缺陷:模型请求变量的搜索在左侧导航与右侧卡片使用两套搜索文本。导航项的搜索文本在变量状态不是已观察时包含状态说明文案,而右侧卡片的判定在同样情况下用空字符串。因此搜索「歧义」这类状态文案时,左侧导航项会命中并保持高亮,右侧对应卡片却被置灰且不会展开——同一个查询词,导航说有、正文说没有。

## Solution

建立一个证据种类 module,让它成为证据分类与其展示标签的唯一拥有者。

基础证据种类取最细的一档,共八种:系统消息、用户消息、助手消息、模型请求变量、工具定义、工具调用、工具结果、模型响应。它们与领域词汇表中的词条一一对应。

标签提供两个变体,按排版语境区分:徽标语境用全大写,标题与图例语境用词首大写。这保留了现有的排版惯例——账本种类列与过滤开关是徽标,组成图图例与导航分组标题是标题——同时消灭了同一种证据在两种语境下叫法不一致的问题。分析导航那张表里的中文响应改为英文。

粒度差异保留,但改为显式的具名聚合。组成图把工具调用与工具结果聚合为工具交互,因为它按字符占比统计而这两者在请求消息里成对出现;分析导航把三种工具证据聚合为一个工具分组,因为分组标题下要挂多个条目。这些聚合从基础种类派生并显式声明,因此「组成图把工具调用与工具结果算作一类」这条规则第一次成为可以断言的事实——它现在只存在于一个条件分支里。

七套词汇收敛为一套基础词汇加一套具名聚合,另有两套留在投影内部不对外。轨迹行的种类从「种类加工具事件副字段」两维压成一维基础种类,取标签因此从两个参数变成一个。客户端证据过滤模块里三个纯翻译函数随之删除。

变量搜索改用导航项已经算好的搜索文本作为唯一来源,右侧卡片不再自己重算一遍。

## User Stories

1. As a 模型请求复盘人员, I want 轨迹视图同屏各处对同一种证据使用一致的说法, so that 我不必在三种写法之间自己建立映射
2. As a 模型请求复盘人员, I want 徽标语境的证据种类统一为全大写, so that 账本种类列与过滤开关读起来是同一套词
3. As a 模型请求复盘人员, I want 标题语境的证据种类统一为词首大写, so that 组成图图例与导航分组标题读起来是同一套词
4. As a 模型请求复盘人员, I want 分析导航的响应分组显示英文, so that 同一张导航里不再中英混杂
5. As a 模型请求复盘人员, I want 组成图把工具调用与工具结果合并统计的规则保持不变, so that 请求体占比图仍然按成对出现的交互汇总字符数
6. As a 模型请求复盘人员, I want 分析导航仍把三种工具证据收在一个工具分组下, so that 导航层级不会因为词汇统一而变平
7. As a 模型请求复盘人员, I want 过滤开关仍然分别提供工具定义、工具调用与工具结果三档, so that 我能单独隐藏其中某一类
8. As a 模型请求复盘人员, I want 轨迹账本的种类列显示与过滤开关完全相同的标签, so that 我知道勾掉哪个开关会隐藏哪些行
9. As a 模型请求复盘人员, I want 请求边界行继续显示为请求而不被当作一种证据, so that 隐藏全部证据种类后我仍能看出有哪些请求
10. As a 模型请求复盘人员, I want 搜索模型请求变量的状态文案时导航项与右侧卡片同时命中, so that 我不会以为某个变量既存在又不存在
11. As a 模型请求复盘人员, I want 搜索已观察变量的展开值时导航与卡片行为一致, so that 搜索结果可信
12. As a 模型请求复盘人员, I want 搜索不命中的变量在导航与卡片两侧同时被置灰, so that 视觉反馈不矛盾
13. As a 模型请求复盘人员, I want 证据种类的配色与图标保持现状, so that 本次改动不影响我已经熟悉的视觉识别
14. As a 模型请求复盘人员, I want 按种类过滤的行为完全不变, so that 我的筛选习惯不受影响
15. As a 模型请求复盘人员, I want 模型响应分组的过滤行为保持现状, so that 隐藏助手消息不会连带隐藏响应分组
16. As a 外部测试控制器, I want 模型请求轨迹的行种类是一个扁平取值, so that 我不必读取工具事件副字段才能判断这一行是定义、调用还是结果
17. As a 外部测试控制器, I want 轨迹行种类的取值与领域词汇表的证据词条对应, so that 断言可以直接引用领域概念
18. As a 外部测试控制器, I want 请求组成项的种类明确标记为聚合结果, so that 我知道工具交互合并了哪两种基础证据
19. As a 维护者, I want 证据分类与其展示标签由一个 module 拥有, so that 新增视图不会长出第八套词汇
20. As a 维护者, I want 基础证据种类只有一处定义, so that 增删一种证据只改一个地方

27. As a 维护者, I want 分析导航分组键与条目种类被删除, so that 客户端不再有第二套分类
28. As a 维护者, I want 对话卡片角色被删除, so that 客户端不再有第三套分类
29. As a 维护者, I want 投影内部的消息角色与响应事件种类保持不变, so that 协议识别的职责不被本次改动侵入
30. As a 维护者, I want 变量搜索文本只有一处派生, so that 导航与卡片不可能再产生两套口径
31. As a 维护者, I want 证据种类 module 可在服务端与浏览器同时运行, so that 服务端轨迹派生与客户端视图共用同一实现
32. As a 维护者, I want 证据种类 module 不依赖 Node、Koishi、Vue 或 DOM, so that 它不会破坏任何一侧的构建
33. As a 维护者, I want 证据种类进入领域词汇表, so that 它不是一个只存在于代码里的概念
34. As a 维护者, I want 证据种类与共享模型证据投影的边界被记录下来, so that 将来没人把展示标签塞进投影
35. As a 维护者, I want 过滤开关不暴露模型响应种类这件事被明确记录, so that 它被识别为一个显式缺口而不是遗漏
36. As a 维护者, I want 现有的证据身份与定位行为完全不受影响, so that 跨视图定位不需要重新验证

## Implementation Decisions

### 证据种类 module

新建证据种类 module,位于服务端目录,是浏览器安全的纯 module——不依赖 Node、Koishi、Vue 或 DOM,服务端轨迹派生与客户端视图共用同一实现。这与共享模型证据投影同一形状。

它拥有三件事:基础证据种类的全集、每种证据的两个标签变体、以及若干具名聚合。

### 基础证据种类

八种,取最细一档:系统消息、用户消息、助手消息、模型请求变量、工具定义、工具调用、工具结果、模型响应。它们与领域词汇表的词条一一对应。

模型响应纳入基础词汇的理由:它在领域词汇表里与请求消息、工具定义并列,确实是一类证据。把它排除会让 module 覆盖不全,下一个视图仍要自己定义响应的标签。

请求边界行不纳入。它是「一次模型请求从这里开始」的结构标记,不是证据。现有测试已经把这条区分钉住:隐藏全部证据种类后仍能看出有哪些请求。

### 两个标签变体

徽标语境用全大写,标题与图例语境用词首大写。两者在 module 里成对声明,不会漂移。

这保留现有排版惯例:轨迹账本种类列与过滤开关是徽标(有背景色、内边距与固定高度),组成图图例与分析导航分组标题是标题。大小写差异因此是有依据的排版区分,而不是不一致。

分析导航标签表里的中文响应改为英文,与同表其余项一致。

### 具名聚合

两个聚合,从基础种类派生并显式声明:

- 工具交互:工具调用加工具结果。组成图使用,因为它按字符占比统计,而这两者在请求消息里成对出现,合并统计才有意义。
- 工具分组:工具定义加工具调用加工具结果。分析导航使用,因为分组标题下要挂多个条目。

聚合显式化后,「组成图把工具调用与工具结果算作一类」这条规则第一次可以断言;它目前只存在于一个条件分支里,没有任何测试。

### 每个视图取什么

基础词汇是证据种类的全集;每个视图按需要取子集或聚合,这是显式选择:

- 过滤开关:取八种中的七种,不暴露模型响应。因此模型响应分组的现有过滤行为完全不变——它的理由从「响应分组没有单一角色」变成「过滤开关不暴露响应种类」,更准确,而钉住该行为的现有测试仍然有效。
- 轨迹账本:取全部八种的徽标标签,外加视图特有的请求边界行标签。
- 组成图:取工具交互聚合后的五档,用标题标签。
- 分析导航:取工具分组聚合后的六档,用标题标签。

### 词汇收敛

七套收敛为一套基础词汇加一套具名聚合,另有两套留在投影内部:

- 证据过滤种类提升为基础词汇本身,并补上模型响应。
- 轨迹行种类与工具事件副字段压成一维基础种类,副字段删除。取标签从两个参数变成一个。
- 请求组成种类保留,但声明为从基础种类聚合而来。
- 分析导航分组键与条目种类删除,改用基础种类加工具分组聚合。
- 对话卡片角色删除,改用基础种类。
- 投影内部的消息角色与响应事件种类保持不变。它们描述协议识别结果,属于共享模型证据投影的职责,本次改动不侵入。

客户端证据过滤模块里三个纯翻译函数删除:轨迹行到过滤种类、消息角色到过滤种类、导航条目到过滤种类。基础种类统一后不再需要翻译。

### 对外形状变更

模型请求轨迹的行种类压平、工具事件副字段删除,这是 Console RPC 与测试控制端点可见的形状变更。依未发布阶段兼容策略直接变更,不加兼容层、不并行两套字段、不递增测试控制 API 版本。

### 变量搜索修复

删除分析视图里自己重算的变量搜索判定,改用导航项已经算好的搜索文本作为唯一来源。修复后搜索变量状态说明文案时,左侧导航项与右侧卡片同时命中或同时不命中。

分析视图里那份与导航侧文案不同的变量状态标签同时删除,改用导航侧那一份。

### 文档

领域词汇表新增证据种类词条,说明它是最细档的证据分类、拥有聚合关系、以及它与原始模型证据的区别——后者是数据,前者是分类。

新增一条架构决策记录,内容包括:证据分类与展示标签由独立 module 拥有而不进共享模型证据投影,因为投影只理解协议结构而标签是展示概念;聚合关系为何显式声明;两个标签变体为何按排版语境区分而不是统一成一种。共享模型证据投影那条决策不修改。

## Testing Decisions

### 什么算好测试

只断言从 interface 观察得到的外部行为:给定一种基础证据种类,module 交出哪两个标签;给定一个聚合,它包含哪些基础种类;给定一条轨迹行,它的种类是什么。不断言实现内部有几张表、用了什么数据结构,也不断言源码文本。

### 主 seam

新建的证据种类 module。本规格的核心事实都能从这里观察:八种基础种类的全集、每种的两个标签变体、两个聚合各自包含哪些基础种类。

新增 seam 数为一。它取代的不是别的 seam,而是四张分散的标签表与三个翻译函数——那些是同一 module 内的实现细节,不是 seam。

Prior art:共享模型证据投影是同一形状的既有 module——服务端目录里的浏览器安全纯 module,被服务端与客户端共同消费。

### 新获得的可断言事实

聚合关系。目前「组成图把工具调用与工具结果算作一类」只存在于一个条件分支里,没有测试。聚合具名后应当断言:工具交互聚合恰好包含工具调用与工具结果两种;工具分组聚合恰好包含三种工具证据;两个聚合的成员不重复也不遗漏。

### 既有 seam 的调整

- 服务端轨迹派生:行种类压平后,现有断言从「种类加工具事件副字段」两个字段改为断言一个扁平种类。该测试文件已经逐行断言过全部行种类,改断言即可。
- 客户端证据过滤:九个现有用例中三个是测翻译函数的,函数删除后这些断言改为「基础种类可直接用于过滤判定」。其余六个用例——包括请求边界行不参与过滤、响应分组不被助手种类过滤掉、切换过滤成员返回新集合——全部保持不变。
- 客户端分析导航:分组键与条目种类删除后,相关断言改用基础种类与工具分组聚合。
- 变量搜索:导航项搜索文本已有测试覆盖,删除右侧重算后无需新增断言,但应补一条回归——变量状态不是已观察时,搜索状态说明文案在导航与卡片两侧结论一致。

### 不测什么

标签在界面上的实际排版效果。四处标签是否真的同屏一致、大小写在具体元素上如何呈现,属于布局事实,由浏览器验证承担。依既有决策不引入组件挂载测试。

### 验收

单元测试、类型检查与构建全绿。

改动了服务端类型与 Console RPC 形状,浏览器验证前必须完整重启一次项目:先确认旧进程与相关子进程已退出、监听端口已释放,重启后确认只有一个实例且加载的是当前构建产物。

浏览器验证三件事:

- 打开模型请求轨迹视图,确认过滤开关、账本种类列、组成图图例、分析导航分组四处对同一种工具证据的说法一致——徽标处全大写、标题处词首大写、粒度对应关系清楚
- 分析导航的响应分组显示英文
- 搜索一个状态不是已观察的模型请求变量的状态说明文案,确认左侧导航项与右侧卡片同时命中;再搜索一个不存在的词,确认两侧同时置灰

## Out of Scope

- 让过滤开关支持过滤模型响应。基础词汇纳入模型响应后这一步在技术上变得可行,但暴露一个新的过滤档位是功能新增,现有过滤行为在本规格内保持不变。单列。
- 共享模型证据投影按记录身份的记忆化。一次自动刷新周期同一条记录被投影多次,其中轨迹派生内部就重复三次输入完全相同的投影;那是另一条候选,与词汇无关。
- 证据种类的配色与图标。它们目前已经共用一套角色色,本规格不动。
- 证据定位与证据导航的任何行为。本规格只改分类词汇与标签,不触碰定位与往返。
- 模型请求对话视图内部消息计数与工具计数口径不一致。
- 引入组件挂载测试、jsdom 或 happy-dom。
- 轨迹视图的布局、图标与交互调整。

## Further Notes

- 本规格纠正了架构评审对这条摩擦点的两处描述。评审说是六套词汇,实际是七套——漏了对话卡片角色。评审把问题归因为「同屏三种写法」,但核实后大小写差异有排版语境依据,真正站不住的是粒度不一致与同表中英混杂。
- 大小写按语境保留而不是统一成一种,是明确决策而非妥协:徽标全大写、标题词首大写是常规排版惯例,统一成一种反而会让其中一处显得突兀。
- 三种粒度各有功能依据,已逐一核实:过滤开关需要三档因为用户要分别过滤;账本行需要三档因为每行是一条证据;组成图合并工具交互因为按字符占比统计且两者成对出现;导航分组需要容器因为标题下挂多个条目。因此「粒度统一到一档」是功能退化,本规格改为「多档粒度从同一词汇派生且聚合显式」。
- 变量状态标签目前有两份不同文案,一份短句一份长句。这印证了导航侧与卡片侧各自演化过,也是本规格把它们收敛到一处的直接理由。
- 分支与提交:依仓库规则不自行创建分支、不自行提交。
