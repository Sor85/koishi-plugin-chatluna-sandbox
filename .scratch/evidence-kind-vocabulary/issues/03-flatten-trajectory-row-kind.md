# 03 — 服务端轨迹派生改用基础证据种类

**What to build:** 外部测试控制器读取模型请求轨迹时,行种类是一个扁平取值,不必再读工具事件副字段才能判断这一行是工具定义、工具调用还是工具结果。

轨迹行的种类目前由两个字段共同表达:一个粗粒度种类加一个可选的工具事件副字段。判断一行到底是哪种工具证据必须同时读两个字段,取展示标签也因此需要两个参数。改为一维基础证据种类后副字段删除,取标签只需一个参数。

请求组成项的种类保留现有的五档,但显式声明为从基础证据种类聚合而来——其中工具交互聚合了工具调用与工具结果。组成图按字符占比统计,这两者在请求消息里成对出现,合并统计才有意义,因此聚合必须在服务端完成,不能下推给视图。

这是 Console RPC 与测试控制端点可见的形状变更。依未发布阶段兼容策略直接变更,不加兼容层、不并行两套字段、不递增测试控制 API 版本。

请求边界行继续作为视图特有的行类型存在,不并入基础证据种类。现有测试已经钉住这条区分:隐藏全部证据种类后仍能看出有哪些请求。

**Blocked by:** 01 — 建立证据种类 module

**Status:** ready-for-agent

- [ ] 轨迹行的种类是一维基础证据种类,工具事件副字段删除
- [ ] 工具定义、工具调用、工具结果三种行各自有独立的扁平取值
- [ ] 请求边界行仍然是视图特有的行类型,不属于基础证据种类
- [ ] 请求组成项的种类显式声明为从基础证据种类聚合而来
- [ ] 请求组成图的字符占比统计结果与改动前完全一致,工具交互仍合并工具调用与工具结果
- [ ] 会话模式轨迹的聚合、排序与请求边界行为不变
- [ ] 证据身份与跨视图定位行为不受影响
- [ ] 现有轨迹测试中逐行断言行种类的部分改为断言一个扁平种类
- [ ] Console RPC 与测试控制端点的形状变更不加兼容层、不递增测试控制 API 版本
- [ ] 单元测试、类型检查与构建全绿
