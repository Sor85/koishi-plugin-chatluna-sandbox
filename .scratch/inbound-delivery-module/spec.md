# 入站投递收成一个内部 module

Status: ready-for-agent

## Problem Statement

发文字、发图片、发合并转发这三条路，各自组装一份几乎相同的投递数据，然后交给同一个派发函数。修好一条不代表另两条也修好了。

组装其实有四份，第四份在机器人适配器里——插件用 `get_msg` 读回一条消息时又组装了一遍同一个五元组。它和入站投递在媒体段上口径不同：投递给插件的媒体段只有文件引用，读回时的媒体段还带着地址与文件名。

媒体那一路的 raw message 是手搓的，另两路调共用的助手函数。逐段核过之后两者结果**逐字相同**——这是一份还没漂移的重复，没有任何东西保证它继续一致。

真正的问题是投递里有三条改坏了不报错的规则，今天全部零覆盖：

- **等待被测插件的 middleware 有 15 秒超时。** 注释写着「无超时会让 void 掉的投递 Promise 永久挂起，堆积监听器并拖垮运行时」。整个测试目录里这个时长零出现。
- **ChatLuna 角色上下文跟随失败只写日志、不中断投递。** 注释写着「中断投递会让被测插件根本收不到消息，那比上下文不干净严重得多」。投递路径上的「失败不中断」没有断言。
- **入站事件会话的进出栈。** ADR-0080 的历史读取跟随与挂在机器人动作记录上的会话观察都依赖它。取当前入站事件会话这件事在测试目录里零出现。

这三条都在一个 3117 行的控制服务里，要驱动它们得先起一个真的 Koishi 运行时。

## Solution

把「把一条已落库的消息投递给所有该收到它的机器人」收成一个内部 module。

用户看不到任何变化。三条发送路径的行为、投递给插件的事件字段、调试记录、投递记录、会话观察、等 delivery 的入口对时序的保证，全部与今天一字不差。

治理之后：投递规则集中一处，给投递加一种能力时三条路自动都有；那三条今天只靠注释保护的规则第一次有红灯；排查「插件到底收到事件了吗」只看一处。

## User Stories

1. As a 沙盒用户, I want 发文字、发图片、发合并转发三条路的投递行为真正一致, so that 修好一条不必再去验另两条
2. As a 沙盒用户, I want 被测插件的中间件长时间不结束时投递仍然收尾, so that 界面不会永远等在发送中
3. As a 沙盒用户, I want ChatLuna 角色上下文重置失败时插件仍然收到消息, so that 一次上下文不干净不会变成一次收不到消息
4. As a 沙盒用户, I want 群消息投递给所有该收的机器人、停用的不收, so that 多机器人场景下的投递范围符合预期
5. As a 沙盒用户, I want 机器人发群消息时不投递给自己, so that 不会形成自我调用环
6. As a 沙盒用户, I want 私聊只投递给对端机器人, so that 用户之间的私聊不产生机器人事件
7. As a 沙盒用户, I want 一条群消息复用同一个消息标识派发给多个机器人, so that 历史里仍然只有一条消息
8. As a 沙盒用户, I want 插件在会话实例里读历史时仍然跟随事件来源会话, so that 分支测试仍然成立
9. As a 沙盒用户, I want 机器人动作记录上的会话观察一字不变, so that 我据以断言插件真实行为的证据不变
10. As a 沙盒用户, I want 每次事件派发照旧在调试记录里留一条, so that 我仍能看到插件收到了什么
11. As a 沙盒用户, I want 事件派发失败照旧记一条错误记录并抛出, so that 失败不被吞掉
12. As a 沙盒用户, I want 投递记录（谁收到了哪条消息）一字不变, so that 投递范围仍然可查
13. As a 沙盒用户, I want 界面、文案与交互没有任何变化, so that 一次结构性收拢不占用我的验收时间
14. As a 外部测试控制器使用者, I want 等 delivery 的入口仍然保证同步回复已进入发送前游标对应的事件流, so that 我的编排脚本的时序假设不变
15. As a 外部测试控制器使用者, I want 合并转发的机器人操作者仍然走自身的真实 OneBot action, so that 能力禁用与调试记录仍与真实通道一致
16. As a 插件维护者, I want 投递规则集中在一个 module 里, so that 读它不必在三条发送路径之间比对
17. As a 插件维护者, I want 给投递加一种能力时三条路自动都有, so that 不会出现只加了一条路的情况
18. As a 插件维护者, I want 中间件等待的超时有断言, so that 拿掉它导致的永久挂起能被测出来
19. As a 插件维护者, I want 「ChatLuna 跟随失败不中断投递」有断言, so that 有人把它改成抛出时会变红
20. As a 插件维护者, I want 入站事件会话的进出栈有断言, so that 历史读取跟随所依赖的东西不再只靠记得
21. As a 插件维护者, I want 接收机器人的推导可以不开 Koishi 运行时就驱动, so that 四种情形各写一条断言的成本很低
22. As a 插件维护者, I want 媒体那一路不再手搓 raw message, so that 两份表达不会哪天悄悄分叉
23. As a 插件维护者, I want 入站与读回在媒体段上的既有差异被记下来而不是被顺手改掉, so that 保真度的改动有它自己的决定与验证
24. As a 插件维护者, I want notice 与 request 各自那段保真度注释一行不动, so that 「缺了这个字段插件的监听器永远不匹配」这类规则不在搬迁中丢掉
25. As a 插件维护者, I want 调试记录的形状不变, so that ADR-0048 记的那份统一动作记录不受影响
26. As a 插件维护者, I want 一条规则拦住第二份入站消息事件组装, so that 四份组装不会变成五份
27. As a 插件维护者, I want 那条规则零豁免, so that 它是一条无例外的不变量
28. As a 插件维护者, I want 八个发送成员一个不动, so that 「谁等 delivery」这件事留给它自己那条候选去决定
29. As a 插件维护者, I want 被测插件收到的事件在收拢前后逐字节相同, so that 「行为没变」不是一句口头承诺
30. As a 插件维护者, I want 客户端一行不改并且可以用 diff 证明, so that 这一轮不需要开浏览器
31. As a 插件维护者, I want ADR-0076 的写入偏离与 ADR-0080 的读取跟随一条不被动, so that 收拢不夹带语义变化
32. As a 插件维护者, I want 这道 seam 被写进 ADR, so that 下一个人知道事件组装该住在哪里

## Implementation Decisions

### 只收 implementation，发送 interface 一个键不动

- 控制服务上的八个发送成员全部保留。报告里那条「六个成员降到三个」不成立：核过之后七个各有真实消费方，唯一没有 src 消费方的那个媒体等待版本有十五处测试在用。
- 八个入口的差异不是冗余，是两件事——**谁等待投递完成**（Console 要即时结果、外部测试控制器要等到同步回复进入事件流、机器人动作不能等否则向自身会话发送会成环）与**操作者是不是机器人**（机器人操作者必须走自身的真实 OneBot action，才能让能力禁用与调试记录与真实通道一致）。
- 前者被外部测试控制器的游标语义压着，后者被 ADR-0076 的写入偏离口径压着。收窄它们是「发送时序」那条候选要先做的决定，不是这一轮的机械迁移。

### 投递 module 的形状与注入

- 工厂函数，返回一份窄 interface。协作者按**最小结构化 interface 注入**：按标识取运行时机器人、订阅中间件完成、写一条投递记录、记日志。**不注入宿主 `Context`**。
- 这与 ADR-0075 在客户端那侧同口径（注入最小结构化 interface，绝不注入宿主类型），服务端也已有两个先例：记录域目录是工厂函数吃注入的协作者，模型请求采集器是工厂函数吃注入的钩子并交回一个卸载函数。
- 中间件等待的超时用注入的计时能力表达，因此它第一次能被假计时器驱动。ADR-0066 已经有「用假计时器驱动领域时间」这条决定，直接沿用。

### module 对外只有两件事

- **把一个 OneBot 事件派发给一个机器人并记录它**：派发、写一条调试记录、失败时记错误记录并原样抛出。六种事件（消息、好友请求、好友通知、群请求、群通知、撤回通知）都经它。
- **把一条已落库的消息投递给所有该收到它的机器人**：接收机器人推导、会话与 OneBot 事件字段构造、ChatLuna 角色上下文跟随、中间件等待与超时、入站事件会话的进出栈、投递记录。
- 共用底座必须进 module：六种事件都用它，而它拥有调试记录的形状。留在控制服务会让 module 反过来注入一个「怎么记录一次派发」的回调——那是把自己的核心职责外包出去。

### notice 与 request 的组装留在控制服务

- 五个 notice／request 派发方法各自组装完事件字段之后调 module 的第一件事。它们不搬：每一个都依赖场景状态（取用户、取群成员与角色、按角色挑收件人），每一个都带着自己那段保真度注释——例如戳一戳必须补上子类型与目标标识，缺了它「被戳后回复」这类插件的监听器永远不匹配。
- 搬它们是另一个切片。本轮它们一行不改，只是派发那一步改道。

### 组装统一到「已经一致」为止

- 媒体那一路手搓的 raw message 改成调共用助手函数。两者结果逐字相同（回复段、媒体段、文本段三段都对得上），因此这是纯结构性的一步，顺带消掉一份没有任何东西保证同步的重复。
- **媒体段的字段口径不动。** 入站投递给插件的媒体段只有文件引用，而共用助手函数在带媒体时产出的段还带地址与文件名。改它会改变被测插件收到的事件保真度，属于另一件事，必须单独决定并对着真实 OneBot 实现核过。

### 读取方向不收

- 机器人适配器里那份 `get_msg`／历史事件组装本轮不动。ADR-0080 明确把读与写分开处理，它的输入是快照里的一条消息而不是一次发送描述。硬合会让一个 module 同时服务两个方向，而两个方向的媒体段口径今天就不一样。
- 它与上面那条保真度差异一起归「OneBot 事件构造的两个方向」候选。

### 守卫零豁免

- 新增一条规则：组装入站消息事件字段的写法只允许出现在投递 module 里。谓词按形状判定——**事件类型与 raw message 出现在同一个对象字面量里**——与既有那条「收发 Koishi RPC 的函数只允许出现在客户端端口适配器里」同形。
- 核过之后这条规则今天只命中控制服务那一处，迁完后只命中投递 module。机器人适配器那份读取方向的组装带 raw message 但**不带事件类型**，命不中，因此不需要豁免。规则落地后豁免清单不增一条。

### ADR

- 写一条：入站投递是一道内部 seam，控制服务不再逐条组装事件；共用底座拥有调试记录的形状；notice 与 request 的组装留在控制服务及其理由。
- 明确写清保住什么：ADR-0076 的写入偏离（机器人动作只寻址根会话）、ADR-0080 的读取跟随与会话观察、ADR-0048 的统一动作记录形状、ADR-0002 的服务端状态所有权。本轮只收 implementation，一条都不推翻。

## Testing Decisions

好的测试断言外部可观察的行为，而不是实现写法。本仓库的判据已经写下来了：肯定式实现细节断言在等价重构时变红、在真实回归时沉默。本规格不新增任何一条这样的断言。

**净新增 seam 数：一个。** 目的是让三条今天只靠注释保护的规则变得可驱动。没有这个 seam，要碰它们必须先起一个真的 Koishi 运行时，因此它们至今零覆盖。

### 主测试面

- **投递 module 自身的 interface（新增 seam）**。协作者按注入取得，因此接收机器人推导、中间件超时、跟随失败、入站事件会话这四件事都能不开运行时驱动。先例是记录域目录与模型请求采集器的测试——两者都是工厂函数吃注入的协作者。
- **消息投递那一族的既有 seam（回归网）**。已有一个测试文件用真 `App` 驱动六个用例，覆盖接收机器人推导的结果：私聊只投给对端机器人、用户之间私聊不产生投递、群消息投给所有机器人成员而历史只存一份、机器人发群消息时排除自己。**这六个用例一字不改地继续通过**，是这一族的回归网。
- **调试记录与会话观察的既有 seam**。事件派发的记录形状、机器人动作记录上的会话观察都已有断言，一字不改地继续通过。
- **服务端架构守卫（既有 seam）**。新规则与它的正反自测在这里。

### 要补的断言

三条静默规则各一条，都是「改坏了不报错」的类型：

- 中间件迟迟不结束时，把假计时器推到超时点之后，投递照常结束且监听器被解除。
- ChatLuna 角色上下文跟随抛错时，投递仍然完成，插件仍然收到事件，只多一条日志。
- 入站事件会话在投递期间可见、投递结束后弹出；嵌套投递时后进先出。

外加接收机器人推导的四种情形直接在 module 的 interface 上驱动：私聊对端是启用的机器人、对端是停用的机器人、群里有多个机器人成员、操作者自己是机器人时被排除。既有那六个用例仍然从真 `App` 那一侧覆盖同样的事实，两者不互相替代——一个证明推导本身，一个证明接线。

### 纯结构性的证明

- **stash 基线比对被测插件收到的事件本身。** 一份确定性脚本让三条发送路径各跑一次，导出插件收到的会话字段与 OneBot 载荷的完整 JSON，逐字节相同。投递的产物就是那个事件，这比比对任何页面输出都贴切。
- **完整测试、类型检查与构建通过。**
- **`git diff --stat` 里没有客户端路径**，作为一条验收项。本轮客户端一行不改。
- 每张票各跑一次。基线作为票的证据留在本 feature 目录下。

### 别处变红的处置

改控制服务会让读它源码或按私有方法名断言的测试变红。逐条区分真红与假红——标识符变化跟着改是假红，行为口径或成本结构变化是真红，停下来查——并在票的 Comments 里逐条记处置。**不重判前几轮已经判定保留的断言。**

## Out of Scope

- **收窄八个发送成员。** 「谁等待投递完成」被外部测试控制器的游标语义压着，「操作者是不是机器人」被 ADR-0076 压着。归「发送时序」候选。
- **统一入站与读回的媒体段字段口径。** 那会改变被测插件收到的事件保真度，需要对着真实 OneBot 实现核过。归「OneBot 事件构造的两个方向」候选，和读取方向那份组装一起。
- **搬迁 notice 与 request 的组装。** 五个方法各自依赖场景状态并带着自己的保真度注释，是另一个切片。
- **按剩下五组职责继续划控制服务内部 module。** 场景写入与保留窗口、头像与媒体、群权限、关系申请、公共 notice 派发本轮不动。本轮是那条候选里最大的一块，做完之后按剩余行数重新估，不开一张「六组一起划」的大票。
- **界面、文案、样式与交互的任何调整。** 本轮没有行为变化，一处例外都没有。
- **引入组件挂载测试。** 已记录在案的决定。

## Further Notes

- 最值得做的不是少三份组装，而是三条今天只写在注释里的规则第一次成为可断言的事实。三条都改坏了不报错：一条表现为投递 Promise 永久挂起并堆积监听器，一条表现为被测插件根本收不到消息，一条表现为插件在会话实例里读到另一条对话线的历史然后拿它去请求模型——最后这条 ADR-0080 用一整段描述过它的失败形态「完全静默」。
- 顺带被钉住的是一份还没漂移的重复：媒体那路手搓的 raw message 与共用助手函数今天逐字相同，但没有任何东西保证它继续一致。这一类「还没坏」的重复比已经坏掉的更值得处理，因为它不会自己暴露。
- 本轮明确**不**碰的那两处差异（入站与读回的媒体段口径、八个发送入口的时序分工）都不是遗漏，是各自需要自己的决定与自己的验证。把它们写进 Out of Scope 而不是留在代码里当谜题。
- 与前几轮的差别是基线比对的对象变了：前几轮比页面输出或模块模型，这一轮比**被测插件收到的事件**。这是本 feature 唯一的对外事实，也是唯一值得逐字节比对的东西。
- 领域词汇不需要新词：「入站事件」「投递记录」「会话观察」「机器人动作记录」都已在册，实施时核一遍即可。
