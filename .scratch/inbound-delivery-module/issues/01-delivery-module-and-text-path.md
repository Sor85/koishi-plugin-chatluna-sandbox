# 01 — 入站投递成为一个 module，文字发送这一路走它

**What to build:** 用户在 WebQQ 里发一句话，被测插件收到的事件与今天逐字节相同——但这次投递是由一个能单独驱动的 module 完成的，而三条今天只写在注释里的规则第一次有了红灯。

module 对外只有两件事：**把一个 OneBot 事件派发给一个机器人并记录它**（六种事件都经它——消息、好友请求、好友通知、群请求、群通知、撤回通知），以及**把一条已落库的消息投递给所有该收到它的机器人**（接收机器人推导、会话与事件字段构造、ChatLuna 角色上下文跟随、中间件等待与超时、入站事件会话的进出栈、投递记录）。

共用底座必须进 module，因为六种事件都用它、而它拥有调试记录的形状；留在控制服务会让 module 反过来注入一个「怎么记录一次派发」的回调，等于把自己的核心职责外包出去。五个 notice／request 派发方法**一行不改**，只是派发那一步改道——它们各自那段保真度注释（例如戳一戳必须补上子类型与目标标识，缺了它「被戳后回复」这类插件的监听器永远不匹配）原样留在控制服务里。

协作者按最小结构化 interface 注入，**不注入宿主 `Context`**，因此那三条规则第一次能不开 Koishi 运行时就驱动：中间件迟迟不结束时投递照常收尾、跟随失败时插件仍然收到消息、入站事件会话进得去也出得来。

转发与媒体两路本轮不动，两族会暂时一新一旧。用户看不到任何变化。

**Blocked by:** None — can start immediately.

## Comments

**文字这一路无法单独迁移，三条路一起过去了。** 票面写着「转发与媒体两路本轮不动，两族会暂时一新一旧」，但三条发送路径原先已经共用同一个投递入口（`dispatchMessageToBots`），各自不同的只是消息正文的组装（文字段／媒体段／转发段）。把那个入口改道到新 module，三条路同时就走上了新 module；要造出「一新一旧」必须先把入口复制成两份，那正好是本轮要消掉的东西。因此票 02 剩下的实际工作是媒体那路的 raw message 统一、守卫规则与 ADR。

**入站事件会话窗口做成 module 之外的一个小值。** 票面要求「module 对外只有两件事」，而机器人适配器要读这个窗口。三种写法里：（一）把读取加进 module 的 interface，会多出第三件；（二）控制服务开一个 `getInboundEventConversationId` 转手，那是一行转售，既有那条守卫规则本来就拦它，而票 02 要求豁免清单不增一条；（三）窗口是投递模块文件里的一个小值，由投递模块进出栈、由机器人适配器读取，控制服务只把同一个实例交给两边。选（三）。`SandboxBot` 因此多一个构造参数，`control.getInboundEventConversationId` 删除——它在 src 里只有那两个调用点，测试目录零出现，也不在 Console RPC 契约里。窗口的进出栈与后进先出因此能直接驱动，不是靠一个假的协作者转述。

**中间件超时沿用假计时器，不做成注入项。** 规格里「用注入的计时能力表达」与紧接着的「ADR-0066 已有『用假计时器驱动领域时间』这条决定，直接沿用」是两种写法；票面验收项写的是「假计时器推过超时点」，因此取后者：超时时长是一个导出常量（`INBOUND_MIDDLEWARE_TIMEOUT_MS`），照旧用运行时时钟，测试用 `vi.useFakeTimers()` 推过去。ADR-0066 明确说过超时时长不属于时钟注入。

**三条静默规则各自的红灯经变异验证。** 逐条把实现改坏后重跑：拿掉 `setTimeout` → 超时那条用例挂在五秒测试超时上变红；把跟随的 `catch` 改成 `finally`（异常继续传播）→ 跟随那条变红；窗口不出栈 → 会话那四条加投递失败那条共五条变红。改回后 19 条全绿。

**别处变红：零条。** 全量 180 个测试文件、1656 条断言一次通过，没有一条需要区分真红假红——这一族没有任何测试按控制服务的私有方法名或源码文本断言（迁移前已 grep 确认 `dispatchMessageToBot`／`dispatchOneBotEvent`／`withInboundEventConversation`／`getMessageRecipientBots`／`getInboundEventConversationId` 在 `tests/` 里零出现）。前几轮判定保留的断言一条未重判。

**证据。** `evidence/baseline.ts` 让三条发送路径各跑一次（私聊文本、私聊引用回复、群文本、群图片带引用、私聊双媒体无文本、私聊合并转发），导出被测插件收到的完整会话事件与 OneBot 载荷，外加投递记录、事件方向的调试记录与场景消息。标识与 OneBot 消息序号按首次出现顺序归一化，时钟用单调假时钟固定，因此耗时与时间戳也参与比对。`evidence/01-baseline-head.json` 在 `334bd8a` 的独立 git worktree 上采集，`evidence/01-after.json` 采于本票收尾后，`diff` 无输出。

脚本第一版有一处自己的不确定性，值得记下来免得下次再踩：调试记录把正文脱敏成 `[文本已省略，N 字符]`，而 raw message 里的 OneBot 消息序号是随机消息标识按十六进制解析出的数，十进制位数会在九位与十位之间浮动，于是那个字符数每约四次运行就变一次。前两次确定性检查恰好都落在十位上，没抓到它。现在那个计数被归一化（正文本身在 `captured` 里已经逐字对过），并连跑六次确认逐字节一致。
