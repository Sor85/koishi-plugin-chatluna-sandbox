# 02 — 转发与媒体两路迁移，一条规则拦住第二份组装

**What to build:** 发合并转发、发图片这两条路也走同一个投递 module，三条路的投递行为从此真正一致；被测插件收到的事件逐字节不变。

媒体那一路手搓的 raw message 改成调共用助手函数。两者结果**逐字相同**（回复段、媒体段、文本段三段都对得上），因此这一步是纯结构性的，顺带消掉一份没有任何东西保证同步的重复。

**媒体段的字段口径不动。** 入站投递给插件的媒体段只有文件引用，而共用助手函数在带媒体时产出的段还带地址与文件名——这两者今天不一致。改它会改变被测插件收到的事件保真度，必须对着真实 OneBot 实现核过，归「OneBot 事件构造的两个方向」候选，和机器人适配器里那份读取方向的组装一起。本轮把这处差异原样保留。

合并转发的机器人操作者仍然走自身的真实 OneBot action，那一整段分支不动——它是 ADR-0076 写入偏离口径的落点，也是能力禁用与调试记录与真实通道一致的原因。

守卫随本票上线：组装入站消息事件字段的写法只允许出现在投递 module 里，谓词按「事件类型与 raw message 出现在同一个对象字面量里」这个形状判定，跑遍服务端全部源码。核过之后它今天只命中控制服务那一处，两路迁完后只命中投递 module；机器人适配器那份读取方向的组装带 raw message 但不带事件类型，命不中。**规则落地后豁免清单不增一条。**

## Comments

**两路的迁移在票 01 就完成了。** 三条发送路径原先共用同一个投递入口，改道那个入口时转发与媒体一起过去了（见票 01 的 Comments）。本票的实际工作是：媒体那路手搓的 raw message 改调 `toOneBotRawMessage`、守卫规则、ADR。

**媒体 raw message 的输出逐字相同，由基线证明而不是由一条新断言。** 手搓那份是 `[CQ:reply,id=…]` + 各媒体段 `[CQ:<类型>,file=…]` + 文本，助手函数对同一份消息段产出的正是这三段。证明方式是基线里那两条媒体用例（群图片带引用、私聊双媒体无文本）逐字节相同：`"[CQ:reply,id=<sequence-3>][CQ:image,file=sandbox-media://<media-1>]基线群图片说明"` 与 `"[CQ:record,file=sandbox-media://<media-2>][CQ:file,file=sandbox-media://<media-3>]"` 在改动前后一字不差。新写一条「两种写法输出相同」的单元测试会把已经删掉的那份写法留在测试里，那是肯定式实现细节断言。

**媒体段字段口径原样保留。** 入站投递给插件的媒体段仍然只有 `{ file }`；`toOneBotMessageSegments(content, media)` 在带媒体时产出的 `{ file, url, name }` 只出现在读取方向。本轮只换 raw message 的产出方式，不动段的字段——基线里媒体段仍然是 `"data": { "file": "sandbox-media://<media-1>" }`。

**守卫规则按对象字面量的自有属性判定。** 谓词先把每个 `{}` 的嵌套层剥掉，再看本层里是否同时出现 `post_type:` 与 `raw_message:`。因此：沙盒挂在会话上的那份 `onebot: { post_type, …, raw_message }` 命中（嵌一层也认得出）；机器人适配器里 `get_msg` 的回执带 `message_type` 与 `raw_message`、不带 `post_type`，命不中；notice 与 request 那五份带 `post_type`、不带 `raw_message`，命不中；两个键分处不同字面量也不算一次组装。整份源码里没有 `raw_message` 的文件直接短路，不付逐字面量扫描的代价。**豁免清单未增加任何条目**，「移除任一豁免后对应文件重新报错」那条元守卫仍然成立。

**规则的红灯经变异验证。** 在控制服务里临时加一个返回 `{ post_type: 'message', message_type: 'private', raw_message }` 的成员，守卫立刻报出 `src/control-service.ts 违反「只有入站投递模块能组装入站消息事件字段」：事件类型与 raw message 出现在同一个对象字面量里`，且元守卫那条同时变红。移除后恢复。

**领域词汇核过，无需新词。** 「机器人事件投递」「入站事件」「会话观察」「机器人动作记录」「OneBot 调试记录」都已在 `CONTEXT.md` 在册，本轮没有引入新概念；`inbound-delivery` 是模块名而不是新术语。

**ADR。** `docs/adr/0085-own-inbound-delivery-in-one-module.md`：seam 的形状与注入口径、共用底座为什么必须在模块里、入站事件会话窗口为什么在模块之外、notice 与 request 的组装为什么留在控制服务、守卫规则的谓词与零豁免，并写明 ADR-0076 写入偏离、ADR-0080 读取跟随与会话观察、ADR-0048 动作记录形状、ADR-0002 状态所有权一条未推翻，八个发送成员一个不动，两处刻意不碰的差异各自归哪条后续候选。

**验证命令。** `yarn typecheck`、`yarn test`（180 文件 / 1656 断言）、`yarn build` 全部通过；`evidence/02-after.json` 与 `evidence/01-baseline-head.json` 逐字节相同；`git diff --stat` 里没有客户端路径。
