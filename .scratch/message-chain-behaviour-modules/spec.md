# 消息动作链的行为下沉成模块

Status: ready-for-agent

## Problem Statement

WebQQ 工作台的消息列表与聊天区域，行为还住在组件里，因此没人能观察它。

这不是疏忽。这个仓库没有任何 DOM 测试能力——没有 jsdom、没有 happy-dom、没有组件挂载，一个测试都不曾挂载过组件，这也是一条已经记录在案的决定。于是想验证「撤回的消息不能被引用」「继承前缀那一段整体只读」「分叉点那一行显示分界」，唯一的手段就是把组件源码读进来、再断言里面出现了某一行文本。

代价是这些断言保护不了它们声称保护的东西。断言某个条件表达式在源码里出现过，证明的是「有人写过这行」，不是「这条消息真的不能被引用」。换个等价写法它就变红，而真把行为改坏了它一声不吭。同一件事在上一轮已经付过一次代价：模型请求工作台的首个用例把三百多条断言全打在源码文本上，横跨六个主题，任何一条失败都只报同一个用例名；同一区域的评审在那之后找到的多处口径漂移，那些断言一条都没抓住。

消息列表这边的状况更具体。滚动追踪的判定已经下沉了七个模块——底部阈值、尾部签名、贴底状态机、锚点补偿算术、连续消息合并、高亮与滚入视口、消息能力位——但**编排**全留在组件里：哪一行算滚动锚点、恢复分几趟施加、正在恢复时该写回待恢复状态还是当前读数、`ResizeObserver` 回调里是继续恢复还是直接置底。这些是真判定，改坏了会静默漂移，而它们一条断言都没有。聊天区域那边，三个测试用例承载一百三十多条断言，搜索的查询、分页、命中揭示、外点关闭、焦点还原全挤在一起，失败时只报一个用例名。

还有两个更小但同样静默的口子：消息时间用了隐式取运行机器时区的格式化，而同仓早已有显式时区的形状，这一处没接上；媒体标签与媒体大小的格式化在三处、两处逐字节重复，其中一份已经是模块。

## Solution

把还留在这两个组件里的行为下沉成可以单独问的模块，源码断言随之失去存在理由——先有可执行的 interface，再删断言，不是反过来。

用户看不到任何变化。消息的排列、分簇、撤回呈现、继承前缀的弱化、分叉分界、表情回应、多选、搜索、滚动位置的保存与恢复，全部与今天一字不差；唯一的例外单独成票、单独验收。

治理之后，改消息列表的人能从测试里读出「这个组件该怎么表现」，而不是「这个文件里该出现哪几行字」；改坏了行为会当场看到红灯，而换个等价写法不会。一条规则制守卫拦住下一次——组件测试文件里不再允许出现裸的肯定式源码断言，用户可见文案经显式辅助函数表达作为合法出口，尚未治理的文件登记为有主的债务而不是无声放行。

## Implementation Decisions

### 主体是下沉行为，断言清理是结果

- 顺序不可颠倒：**先有可执行的 interface，再删断言**。上一轮的规格已经把理由写死——在对应 interface 抽出来之前删断言是净损失，因为那些断言是该组件当前行为的唯一记录。
- 不引入 jsdom、happy-dom 或组件挂载测试。触碰 DOM 的行为按既有做法拆：判定进模块，DOM 机械动作留在视图里由参数注入，注入最小结构接口而不是 DOM 类型。

### 范围

- 消息列表、聊天区域、以及断言同一份组件源码的多选测试，三者对应同一条消息动作链。
- 发送控件与分析视图不在本规格内，它们各有自己的候选，其断言是那些候选的当前行为参照。
- 顺带收编两处跨文件重复：媒体标签的三份实现（其中一份已是模块）与媒体大小的两份实现，只收这两个函数，不把转发弹窗的其余行为拉进来。

### 十组行为，下沉十个模块

拥有滚动判定的既有模块已经承担了底部阈值、尾部签名、贴底状态机、锚点补偿算术、连续消息合并、高亮与滚入视口、消息能力位投影；留在视图里的是编排与一批从未下沉过的呈现判定。

- **消息呈现判定**：事件化（事件消息，或撤回且关闭撤回标记）、思考与用量随撤回标记一同隐藏、正文取值（转发卡片返回空、单媒体且正文恰为标签加文件名时去重）、引用消息与转发预览查表、消息能力位读取、继承前缀归属、分叉点分界、媒体标签与媒体大小、表情回应的双闸门判定。
- **参与者呈现投影**：名称、头像、群名片与全局昵称的回退、群身份徽标与专属头衔、群成员菜单与好友菜单的取数，以及「哪六个动作算群管理操作」那张今天内联在视图里的表。
- **滚动锚点选取**：遍历消息行取第一个底缘越过容器顶缘的那一行。这是判定不是机械动作，DOM 读取按注入拿。
- **滚动状态存取与恢复编排**：恢复的三分支（贴底置底、锚点缺失直写、锚点命中走算术）、保存时的预览态短路、以及「正在恢复时写回待恢复状态而不是当前读数」这条防覆盖边界。
- **恢复排程**：分趟施加与每层的陈旧校验；帧调度按注入取得，不再直接用全局帧接口。
- **会话切换编排**：存旧、结束恢复、取消追踪、换键、恢复或置底的完整顺序，以及容器尺寸变化时「恢复中则重排恢复，否则贴底则置底」的二选一。
- **思考面板离场**：把面板冻结在原视觉位置的判定，含按消息方向决定钉左缘还是钉右缘，以及解除宽度百分比约束以免按收缩后行宽重算。
- **指针交互分流**：多选态下头像不得阻断冒泡、气泡在捕获阶段按可转发能力位接管、整条点击排除气泡区只覆盖头像与行内空白。
- **多选与转发选择**：进入、切换、退出、可选性判定、键盘操作、确认转发。
- **合并转发对话栈**：嵌套推入与弹出、按入参加载。

### 不下沉的三块

- 区域模型装配。它是组件按既有架构决策该承担的职责，下沉它等于把组件掏空成模板。
- 六个纯转发管道。客户端守卫已明确把它们判为管道而不是动作入口；跑一遍删除测试，复杂度不会集中，只会搬家。
- 回复目标与表情选择器那两三个薄状态。

### 组件的 interface 一律不动

- props、emits、事件名与载荷逐字不变。模型的字段可以新增（由下沉后的模块产出），但不拆成分散的 props。
- 两个理由：动它要连带重开「UI 模块不读取完整工作区快照」那条守卫；更要紧的是 DOM 快照比对的前提就是界面不变，interface 同时在动，纯结构性就无从证明。

### 断言的分类口径

- 逐字沿用仓库既定的五类与判据。判据是**成本结构而不是断言形式**：肯定式实现细节断言在任何等价重构时变红却不验证行为，删；否定式的已删实现守卫只在有人把已删实现加回来时变红，那正是需要的，留；样式文本与用户文案断言不锁死实现写法，在不引入组件挂载测试的前提下是唯一手段，留。
- 五类分别是：已有行为测试覆盖同一事实（全删）、样式文本（全留）、DOM 结构与元素顺序（全留，含与样式选择器形成结构契约的类名）、实现细节契约（删肯定式、留否定式）、用户文案与展示语义（全留）。
- 消息列表实测二百三十八条：删九十六，四条转成规则制守卫，留一百三十八。可删的量集中在实现细节契约那一类的肯定式部分，其中类型声明原文那一批删掉零损失——类型检查已经强制同一件事。
- 不追求源码断言归零。归零会逼人删掉有架构决策依据的守卫。
- **删补不一对一**，但凡一条断言确实声称保护某个用户可见行为，必须先有下沉后的行为断言接上才允许删，不得留「先删干净、下一张票再补」的缺口。

### 逐条分类落在每张票的第一步

- 分类表落盘在本 feature 目录，表头写明行号对应哪个提交、当时的断言总数、以及总数变动即全表失效需重新分类；并写明必须先删除再拆分测试用例——先拆会让行号整体位移，表随即失效。
- 分类不单独成前置票。上一轮正是分类与实施之间隔了提交，行号从三百四十八漂到三百七十，只能整体重映射，还留下一条失配。

### 测试文件的形态

- 用例按主题保持现有结构，不按断言类别另分一层。一个主题天然同时包含多类断言——撤回呈现那个用例里就同时有 DOM 结构、样式文本与用户文案三种，按类别分会把主题打散，而主题才是失败时最有定位价值的信息。
- 类别与依据写成断言组上方的块注释，引用对应的架构决策编号。用例名保持中文行为描述，不塞类别代号——它会进测试报告。
- 聊天区域今天三个用例承载一百三十多条断言，按主题拆开；消息列表只有首个用例是巨型的，其余十一个已按主题分好。

### 守卫

- 新增一条规则制规则：组件测试文件不得出现裸的肯定式源码断言。用户可见文案改由显式辅助函数表达，规则认它为合法出口——这把「这条断言保护的是文案」这个意图写进代码形状，规则因此可按形状判定。
- 规则与既有四条并列，不新开文件。既有引擎的扫描根目录是硬编码的，需要提成规则上的一个字段：四条既有规则扫客户端源码，新规则扫测试目录。**不新增第三份守卫引擎**——服务端与客户端两份已经各自复制了谓词类型、规则类型、豁免类型、文件遍历、违规汇总与三条元守卫断言。
- 尚未治理的文件一次全部登记为有主豁免，否则规则一生效基建票自己就是红的。理由沿用已有判断——该文件的组件行为尚未下沉，断言是它当前行为的唯一记录，先删是净损失；负责人填对应的架构候选或后续 feature，没有对应候选的填待开候选。
- 棘轮钉「已治理文件为零」而不是断言总条数。总条数三分之二是合法断言，钉总数会误导。
- 毛玻璃相关的两条架构决策今天靠组件测试里的四条肯定式断言守着，按分类它们该删。先把它们转成规则制守卫再删——那两条的失效形态都是「不会报错、只会静默错」，直接删等于取消决策。转成规则后对全仓生效，比钉在一个组件测试里更强。
- 规则形状修订进既有的守卫决策记录，不新开一条——这不是新方向，是那条决策的实施细则与合法出口。

### 时区单独成票

- 消息时间用了隐式取运行机器时区的格式化，同仓已有显式时区的形状，这一处没接上。把时区提成显式参数是**行为变化**，与其余六张票的「界面逐像素不变」冲突。
- 因此它单独成票、排在呈现判定那张票之后、验收走行为断言（跨日、跨年、午夜、非法输入）而不是快照比对，并在票里写明它是本轮唯一的行为变化。

## Testing Decisions

好的测试断言外部可观察的行为，而不是实现写法。这个仓库已经为反面付过一次代价，也已经把判据写下来了：肯定式实现细节断言在等价重构时变红、在真实回归时沉默。本规格不新增任何一条这样的断言。

**净 seam 数：新增十个模块 seam，去掉零个。** 这是本规格与上一轮收拢型工作的区别——这里的目的就是让今天不可观察的行为变得可观察，seam 增加是意图而非代价。

### 主测试面：下沉后每个模块自身的 interface

- 纯判定的六组（消息呈现、参与者呈现、多选与转发选择、合并转发栈、滚动锚点选取、恢复排程的陈旧校验）直接以普通单元测试驱动，不需要任何环境。
- 触碰 DOM 的四组（滚动状态存取与恢复编排、会话切换编排、思考面板离场、指针交互分流）按既有做法注入最小结构接口，测试造假对象驱动。先例是 `tests/message-list-follow.test.ts`（帧调度与下一拍全部注入，五个用例逐帧驱动状态机）与 `tests/message-reveal.test.ts`（按消息标识查找、高亮与超时清理、滚入视口）。
- 编排类的断言重点在时序与边界，不在返回值：恢复中不被当前读数覆盖、陈旧排程被丢弃、容器尺寸变化时的二选一、多选下头像不阻断冒泡。

### 保留的断言仍在原测试文件

样式文本、DOM 结构与元素顺序、用户文案三类留在各自的组件测试文件里，按主题归入现有用例，上方块注释注明类别与依据。它们不是二等公民——在不引入组件挂载测试的前提下，它们是唯一手段。

### 纯结构性的证明：DOM 快照比对

- 每张票各跑一次：同一份确定性场景在下沉前后分别渲染，比对 DOM 快照。它直接证明要证明的那件事——界面没变——而不是证明某个中间值没变。
- 场景是一份大场景覆盖全部呈现分支：自有消息与继承前缀、两种撤回呈现方式、引用回复、合并转发入口、表情回应、群身份徽标与专属头衔、系统提示事件、消息分簇的三种边界（同人连发、跨时间、跨作者）、媒体消息、提及；另加两份专项脚本覆盖需要操作步骤的交互态（多选、加载更早历史）。分簇与继承前缀的缺陷恰恰出在边界叠加处，拆成小场景各测一类会漏掉叠加。
- 每张票各跑一次而不是最后统一跑一次：快照的差异只会告诉你哪里变了，不会告诉你是哪次改动干的。
- 浏览器会话与工具生成的临时目录按仓库规则在验收后清理；基线快照作为票的证据留在本 feature 目录下，不进仓库源码。

### 读取成本守卫

新增一条，只钉本轮涉及的三处不随渲染次数放大：分簇、能力位映射、引用消息查表。理由是上一轮唯一被抓到的真实回归就是这一类——两级 computed 被合成一级，导致每次按键为每一行重复归一化五个字段，行为断言全都沉默，是成本守卫当场变红抓住的。消息列表今天一条成本守卫都没有，而它是全仓最容易被读取放大伤到的地方：保留窗口内消息条数上限两千，任何「每条消息重算一次」的写法在小场景里跑得飞快、在真实场景里卡死。先例是 `tests/model-request-read-cost.test.ts` 与 `tests/preset-catalog-read-amplification.test.ts`。

### 别处变红的处置

下沉会让别的测试文件里针对同一份组件源码的断言变红。逐条区分真红与假红——函数改名导致的跟着改标识符是假红，行为口径或成本结构变化导致的是真红，停下来查——并在票的 Comments 里逐条记处置。上一轮五条变红里四条假红一条真红，那条真红如果被当成假红「跟着改一下」，读取放大就悄悄进了主干。

## Out of Scope

- **发送控件与分析视图**。它们各有自己的架构候选——发送控件是草稿与编辑器之间的桥接，分析视图是展开态与原文态。它们的源码断言是那些候选唯一的当前行为参照，本轮删掉会让那些票失去参照。本轮把它们登记为有主豁免，负责人指向对应候选。
- **其余含源码断言的测试文件**。同上，一并登记为有主豁免，不在本轮治理。
- **引入 jsdom、happy-dom 或组件挂载测试**。这是一条已经记录在案的决定，本轮不重开。
- **组件 interface 的调整**。props、emits、事件名与载荷一律不动；想调整是另一件事，治理完再单独提。
- **区域模型装配、纯转发管道与薄状态的下沉**。跑删除测试它们不集中复杂度，只搬家。
- **转发弹窗的其余行为**。只收编媒体标签与媒体大小两个重复函数，不把整个组件拉进来。
- **界面、文案、样式与交互的任何调整**。唯一的行为变化是消息时间的时区，且单独成票、单独验收。
- **源码断言归零**。三分之二的断言按仓库判据是合法的，归零会逼人删掉有架构决策依据的守卫。
- **合并那两份重复的守卫引擎**。本轮只把扫描根目录提成规则字段以免长出第三份，引擎收拢是另一条候选。

## Further Notes

- 本规格是上一轮工作明确留下的续篇。那一轮的 Out of Scope 写着「其余二十七个含源码断言的测试文件…需要先有对应候选把 interface 抽出来，否则是净损失」——本轮就是消息动作链那部分的对应候选，顺序因此必须是先抽 interface 再删断言。
- 最值得做的不是删掉多少条断言，而是四条今天只写在注释里的规则第一次成为可断言的事实：哪一行算滚动锚点、正在恢复时不被当前读数覆盖、容器尺寸变化时恢复与置底的二选一、思考面板离场钉哪一侧。这四条改坏了都不会报错，只会让界面「有点怪」。
- 落地七张票：基建一张（守卫规则、引擎加根目录字段、文案辅助函数、登记豁免、两条毛玻璃决策的守卫转规则制、修订守卫决策记录），主题五张（消息呈现投影、思考面板与点击路由、多选与转发栈、滚动定位与加载更早、聊天记录搜索），时区一张。顺序是基建、呈现投影、其余，重 DOM 编排那两张放最后——等前面几张把行为断言与快照流程磨顺了再碰全仓最容易静默改坏的地方。时区那张只需呈现投影完成。
- 每张票各跑一次完整测试、类型检查与构建，外加一次 DOM 快照比对。完整 Koishi 开发环境在插件仓库之外，每次比对都要起一遍环境并按路径清理旧进程与 worker，不是零成本——仍然每张都跑，因为统一跑一次的定位成本更高。
- 消息列表的分类基数是二百三十八条全部断言，不是「非 CSS 子集」的一百六十一条。之前流传的「全仓约八百八十条」是按 `toContain` 行数混算的，两种口径不可比，写票时以五类分类的实测数为准。
