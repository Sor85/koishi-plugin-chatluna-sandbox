# 08 — 消息时间的时区提成显式参数

**What to build:** 消息气泡上的时间在跨日、跨年那一刻显示正确，并且这件事第一次能被测。

消息时间今天用隐式取运行机器时区的方式格式化，而同一个仓库里早已有「显式时区 + 明确格式化器」的形状在用，这一处没接上。表现上的差别在开发机上撞不到——只有当运行环境时区与预期不一致，或恰好跨过午夜与年界时才会显现。

把时区提成显式参数，接上既有形状，并补齐边界断言：跨日、跨年、午夜、非法输入。

**这是本轮唯一的行为变化票。** 其余七张票的验收依据是「DOM 快照与基线逐像素一致」，而这一张会让时间文本在某些时区下变化，因此它不走快照比对，走行为断言——把它和其余票混在一起会逼人在快照 diff 里人工判断「这个差异是不是预期的」，而那正是快照流程要消掉的东西。

**Status:** resolved

- [x] 时区成为显式参数，调用方传入而不是由格式化器隐式取
- [x] 与同仓既有的显式时区格式化形状一致，不新造第二种写法
- [x] 跨日边界有断言
- [x] 跨年边界有断言
- [x] 午夜有断言

- [x] 组件的 props、emits、事件名与载荷逐字不变

## Comments

### 落地的形状

`formatSandboxTimeOfDay(value, { timeZone, locale })` 加进 `client/webqq/format-time.ts`，
与既有的 `formatSandboxDateTime` 同住一处、共用 `toEpochMs` 与缺省符号 `—`，
形状一致：`Intl.DateTimeFormat` ＋ 显式 `timeZone` ＋ 非法输入给缺省符号。

**一处有意的差别：语言也是参数。** 记录时间是机器可比对的时间戳呈现，因此固定成
`en-US` ＋ `h23` 的一种格式；气泡上的时刻是界面文案，12/24 小时制与分隔符要跟着用户环境走。
两者遵循的是同一条规矩——凡是判定依赖环境隐式提供的东西就提成参数、默认值指向真实环境
（ADR 0075 原文）。因此这里把**时区与语言两个**环境依赖都提了出来，而不是提一个留一个。

### 行为变化的边界说清楚

本票是本轮唯一的行为变化票，验收不走 DOM 快照。实际变了两件事：

1. **时区可被指名。** 不传参时按浏览器时区渲染，与今天逐字一致；传参时按指名时区解释，
   于是跨日、跨年、午夜第一次可断言。
2. **非法输入的呈现。** 此前 `new Date('').toLocaleTimeString()` 渲染成 `Invalid Date`，
   现在是缺省符号 `—`。只有采集侧写坏了时间戳才会看到，属修正而非回归。

界面文案未变这一条不只有单测：开发环境浏览器里读了前六条消息的时间元素，
改动前后**同为** `["12:13 PM","12:13 PM","12:14 PM","12:14 PM","12:15 PM","12:15 PM"]`
（该浏览器环境为 en-US ＋ 本机时区，走的正是「不传参」这条路径）。

### 六条行为断言

`tests/format-time.test.ts` 新增一个 describe（7 条断言块）：按给定时区解释时刻、跨日、跨年、
午夜（含十二小时制语言下的「上午 12:00」）、非法输入、接受时间戳与 `Date`，
以及「不给参数时与环境默认渲染逐字一致」——最后这条正是「提成参数不改变用户所见」的依据，
它对照的是同一份 `Intl` 选项，因此在任何语言与时区的机器上都成立。

### 顺带说明：格式化器缓存

保留窗口内消息条数上限两千，而气泡时间逐条渲染。格式化器按「语言 + 时区」缓存，
避免每条消息现造一个 `Intl.DateTimeFormat`。缓存键必须含时区，否则换时区会拿到上一个的结果——
这一点由跨日那三条断言（同一时刻、三个时区、三个结果）反向钉住。

### 未收进本票的一处同类写法

搜索结果列表里的 `formatSearchTime`（`client/webqq-message-search.vue`）语言是显式的
（`zh-CN`），但时区仍隐式取环境，且每次调用现造格式化器。它属搜索面板自身的呈现，
不在本票的「消息气泡时间」范围内，登记在此备查；认领搜索面板行为下沉的候选时一并收掉。

### 断言处置

`tests/webqq-message-list.test.ts`：删 0 条、加 2 条（`formatSandboxTimeOfDay(createdAt)` 接线，
以及一条否定式守卫 `not.toContain('toLocaleTimeString')`——隐式取环境的旧写法不得被加回来，
它的失效形态是「不报错，只在别的时区静默显示错的钟点」）。文件总数 190 → 192。

### 评审提出的两点，在此答复

**一、「调用方传入而不是由格式化器隐式取」是否真的做到了？** 生产接线是零参数调用
（`client/webqq-message-list.vue` 的 `formatSandboxTimeOfDay(message.createdAt)`），面板上仍按
浏览器时区渲染。这不是半成品，而是本仓库既定形状：ADR 0075 原文写着「改成 `Intl.DateTimeFormat`
加显式 `timeZone` 参数后，**不传参仍按浏览器本地时区渲染**，用户看到的结果不变，而测试可以
指名时区去断言边界」，并把规矩总结成「凡是判定依赖环境隐式提供的东西…都把它提成参数，
**默认值指向真实环境**」。同仓既有的 `formatSandboxDateTime` 也是这个用法——它唯一的生产调用点
`client/model-request-workspace.vue` 同样不传 `timeZone`。

「隐式取」被消掉的是**格式化器内部**那次环境读取：此前 `toLocaleTimeString` 把时区与语言
一起吃进去，调用方无从改变也无从断言；现在两者都是入参，谁要指名谁就传。要求生产代码显式传
`Intl.DateTimeFormat().resolvedOptions().timeZone` 只会让调用点多读一次环境、结果一字不变，
而且会与既有形状分叉——那正是验收项「不新造第二种写法」要避免的。

**二、本轮是否只有本票一处行为变化？** 措辞需要更正：**呈现口径的唯一变化在本票；票 06 另有
一处缺陷修复带来的位置变化**（加载更早后当前这一行不再跳走，该缺陷在票 05 Comments 里已记录
在案）。详见票 06 的 DOM 快照一节。
