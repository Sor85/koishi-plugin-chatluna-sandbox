# 01 — 断言守卫与治理基建

**What to build:** 组件测试文件里再写裸的肯定式源码断言会当场报错，用户可见文案有一条合法出口；尚未治理的文件全部记在账上，而不是无声放行。

新增一条规则制规则：组件测试文件不得出现裸的肯定式源码断言。用户可见文案改由一个显式辅助函数表达，规则认它为合法出口——这把「这条断言保护的是文案」这个意图写进代码形状，规则因此能按形状判定，而不必靠人记账。

既有客户端守卫引擎的扫描根目录是硬编码的，需要提成规则上的一个字段：四条既有规则扫客户端源码，新规则扫测试目录。**不得新增第三份守卫引擎**——服务端与客户端两份已经各自复制了谓词类型、规则类型、豁免类型、文件遍历、违规汇总与三条元守卫断言，再加一份就是明知故犯。

尚未治理的文件一次全部登记为有主豁免，否则规则一生效本票自己就是红的。理由沿用已有判断：该文件的组件行为尚未下沉，断言是它当前行为的唯一记录，先删是净损失。负责人填对应的架构候选或后续 feature，没有对应候选的填待开候选。棘轮钉「已治理文件为零」，不钉断言总条数——三分之二的断言按仓库判据是合法的，钉总数会误导。

毛玻璃相关的两条架构决策今天靠消息列表测试里的四条肯定式断言守着。按分类它们该删，但直接删等于取消决策——那两条的失效形态都是「不会报错、只会静默错」。先把它们转成对全仓生效的规则制守卫，再从组件测试里删。

规则形状修订进既有的守卫决策记录，不新开一条：这不是新方向，是那条决策的实施细则与合法出口。

零行为变化，不动任何组件。

**Blocked by:** None — can start immediately.

## Comments

### 「四条肯定式断言」的落点

票面写的是「毛玻璃相关的两条架构决策今天靠消息列表测试里的四条肯定式断言守着」。
`tests/webqq-message-list.test.ts` 里没有任何 `frosted` / `backdrop` 字样的断言；按注释与断言对象
认定它指的是第 60–64 行断言 `client/webqq-scrollbar.ts` 的那四条：

- `expect(scrollbarSource).toContain('showOverlay?: boolean')`
- `expect(scrollbarSource).toContain('visible && state.showOverlay')`
- `expect(scrollbarSource).toContain("sibling.matches('header, .webqq-overlay-header')")`
- `expect(scrollbarSource).toContain('const topBoundary = getScrollbarHeaderBottom(...)')`

上方注释写着「内容可以穿过表头实现毛玻璃，但轨道不能盖住表头」，正是 ADR 0071 的推论；
四条断言的对象都不是消息列表，钉在这个文件里本身就是错位。

### 转成规则的部分与下沉成模块的部分

这两条决策各有一个样式面和一个行为面，两面分别处理：

- **样式面转规则**：新增「工作区本体与一级区域不得声明 `backdrop-filter`」（ADR 0060）与
  「毛玻璃表头的模糊层必须放在 `::before` 上」（ADR 0071），扫 `client/styles` 全部样式表。
  按选择器**主语**（最后一个复合选择器）判定，`:is()` 内的逗号按括号深度跳过，
  `backdrop-filter: none` 不算违规——它恰恰是这两条决策要求的写法。两条规则当前零违规。
- **行为面下沉**：`getScrollbarHeaderBottom` / `getVisibleScrollbarRect` 抽成
  `client/webqq/scrollbar-track-bounds.ts`，按 ADR 0075 注入最小结构接口（`parentElement`、
  `children`、`matches`、`getBoundingClientRect` 四项），`tests/scrollbar-track-bounds.test.ts`
  以内存替身逐条驱动，覆盖 10 条行为断言，含「排在滚动区域后面的表头不算数」这条今天只写在
  注释里的边界。指令里只剩创建轨道、写样式与绑事件的机械动作。

这一步动了一个客户端文件，超出票面「不动任何组件」的字面措辞（该文件是指令不是组件），
但仍是纯结构性改动，界面与行为零变化。取舍已与用户确认：直接删那四条断言是净损失。
