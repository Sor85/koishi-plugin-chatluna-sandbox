# 02 — 端点集合守卫与无主端点

**What to build:** 声明、注册与消费三者的集合被钉在一起，漂移必须有人变红。

三条断言：注册的监听器集合等于契约的端点集合（两个方向都报——注册了没声明、声明了没注册）；每个端点都有消费方，消费方是客户端端口适配器里的 `send` 调用，或者显式登记为服务端自用；移除登记表里任一条目后对应端点重新报错。

登记表带必填理由，形态与客户端架构守卫的豁免清单一致：不是放行，是有主的债务。守卫读源码——端点集合与消费方名单没有别的观察面，这是 ADR-0073 明示的架构守卫例外，按规则制写谓词而不是白名单。

`chatluna-sandbox/bot-deliveries` 是本规格写作时用集合比对发现的无主端点：服务端两份声明与注册点都有它，客户端补丁没有 `send` 重载，客户端也没有任何调用。先用断言把这处不一致钉红，再按未发布阶段兼容策略决定删掉还是登记；确有保留理由时理由必填。

## Comments

### 实现记录

- 守卫落在 `tests/console-contract.test.ts`。注册集合来自假 Console 实际收集的事件名，且必须在全部可选服务（MCP、测试空间、预设）都在场时注册——缺任何一个都会让它那组端点不被注册，比对因此只在「全都在场」的形态下成立。声明集合与消费方名单读源码：interface 的键在运行时不存在，`send` 的调用点也只以字符串字面量出现，两者没有别的观察面。
- 三种漂移各一条：`在契约里声明了却没有注册监听器`、`注册了监听器却没有进契约`、`没有任何消费方，也没有登记为服务端自用`。判定收在纯函数 `findEndpointDrift` 里，因此谓词自测直接喂合成集合，不必伪造源码。
- 分组解析按大括号配平切块而不是一条正则：入参里的行内对象类型（`{ recordId: string }`）会让 `[^}]*` 提前截断。谓词按形状判定——任何叫 `Sandbox*ConsoleEvents` 的分组自动进端点集合，新增分组不必改守卫。
- 消费方扫全部客户端源码而不是只扫 `koishi-*-port.ts`。只扫端口会让这条守卫依赖「RPC 只出现在端口里」那条规则的豁免清单，两条规则各自成立更稳。
- **`bot-deliveries` 按未发布阶段兼容策略删除，理由：它今天没有任何消费方，而且已经有更好的读取面。** 客户端补丁没有它的 `send` 重载，客户端也没有任何调用；机器人事件投递的领域读取由 `SandboxControlService.getBotDeliveries` 承担，MCP 服务的两处等待逻辑直接调它，外部测试控制器则走 MCP 工具。留一个没人调的 Console 端点只是让「每个端点都有主」这句话打折。删除后登记表为空，`每条登记都写明理由` 与 `移除任一登记后重新报错` 两条成空循环，因此另有一条喂合成集合的谓词自测证明机制活着——形态与客户端架构守卫的豁免清单一致。
- 删除牵动 `console-adapter.test.ts` 三处：两处取监听器的样板，经该端点断言 `不支持旧 RPC 字段：botId` 的那条，以及断言该端点按 `recipientBotId` + `messageId` 过滤返回投递的那条。`botId` 这个字段名的拒绝没有别处覆盖（`senderId` 先命中，其余端点断的是 `userId`），因此那条断言改经 `message-history` 端点发出，覆盖没有丢。
- **正向那条断言的覆盖对象随端点一起消失，因此按未发布阶段兼容策略把死字段一并删掉。** 该端点是 `GetSandboxBotDeliveriesInput.recipientBotId` 的唯一调用方，删了端点这个过滤字段就再没有任何调用方，只剩一条到不了的分支；给它补一条领域层断言等于测试死代码。`messageId` 那个过滤字段仍有调用方（MCP 的 `wait_for_message` 补发投递事件时按它取投递），并由 `mcp-service.test.ts` 里对 `event.data.recipientBotId` 的断言实际走到。投递记录本身的 `recipientBotId` 字段不变，`message-delivery.test.ts` 与 `control-service.test.ts` 照旧断言它。
- 守卫的有效性用注入漂移实测过：注释掉 `preset-catalog` 的注册、把 `delete-test-space` 的 `send` 改成不存在的端点名，两条漂移同时被报出；还原后全绿。
