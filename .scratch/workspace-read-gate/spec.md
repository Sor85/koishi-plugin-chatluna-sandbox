# 一次读取的闸门从工作台外壳里收成模块

Status: ready-for-agent

## Problem Statement

WebQQ 工作台外壳里有二十九处一模一样的八行样板，而它们保护的两条不变量都没有任何断言。

外壳对外给出八十一个键，其中三十一个与工作区控制器同名。这三十一个几乎都是同一形状：置进行中标志、清错误文案、`await` 一次控制器调用、`catch` 里写一句中文兜底、`finally` 复位。同一句「取错误消息，取不到就用这句中文」在这一个文件里出现二十九次，进行中标志的开关出现二十四次，`(进行中, 详情进行中, 错误)` 这组状态抄了四份——调试记录、MCP 调用、模型请求、预设各一份。

样板不只是重复，它还藏着两条会静默坏掉的规则。区域读取那一族的核心是「无论成败都要复位进行中」，漏掉 `finally` 的表现是界面一直转圈、没有任何报错；操作那一族的核心是「每次操作前先清掉上一次的错误」，漏掉的表现是用户看到一条早已过期的错误文案。这两条今天都只体现在「大家都这么抄」上。

四个区域的进行中与错误状态在整个测试目录里零出现——「读详情时列表不该跟着转圈」这条从未被验证过，而它恰好是四个区域里唯一形状不一致的地方：其中三个有列表与详情两条进行中通道，预设只有一条。

再添一个读取动作的人会照抄旁边那八行。二十九处重复本来就是这么长出来的。

## Solution

把「包住一次可能失败的调用、把失败写成一句话」这件事收成模块，两条不变量随之变成可断言的事实。

用户看不到任何变化。转圈何时出现与消失、每个区域的错误文案、操作失败时发送控件上那条提示、「后一次操作的错误覆盖前一次」这个语义，全部与今天一字不差。

治理之后，往外壳里添读取动作的人写一行而不是八行；忘记复位进行中标志这类问题不会在第五个、第六个工作台上重演；一条规则拦住下一次照抄。

## User Stories

1. As a 沙盒用户, I want 四个工作台的转圈出现与消失的时机和今天一字不差, so that 一次结构性收拢不需要我重新验收界面
2. As a 沙盒用户, I want 读取失败时仍然看到针对那一步的具体文案而不是一句「操作失败」, so that 我知道哪里出了问题
3. As a 沙盒用户, I want 读某条详情时列表不跟着转圈, so that 我仍能看清列表里已经加载出来的内容
4. As a 沙盒用户, I want 读取失败后再点一次能重试, so that 一次失败不会把界面卡在错误状态
5. As a 沙盒用户, I want 撤回、贴表情、创建会话这些操作失败时错误提示出现在发送控件上, so that 提示就在我操作的地方
6. As a 沙盒用户, I want 新的一次操作把上一条过期的错误提示清掉, so that 我不会对着一条早就不成立的报错发愁
7. As a 沙盒用户, I want 四个区域的错误互不干扰, so that 预设读取失败不会让调试记录页看起来也坏了
8. As a 插件维护者, I want 「无论成败都复位进行中」这条不变量有断言, so that 忘记复位导致的一直转圈能被测出来
9. As a 插件维护者, I want 「每次操作前清掉上一次的错误」这条不变量有断言, so that 过期错误文案不再靠人点出来
10. As a 插件维护者, I want 「读详情时列表不该转圈」有断言, so that 两条进行中通道的独立性不再只是巧合
11. As a 插件维护者, I want 四个区域各自独立有断言, so that 一个区域的失败不会串到另一个
12. As a 插件维护者, I want 往外壳里添读取动作时写一行而不是八行, so that 下一个区域不必再抄一遍样板
13. As a 插件维护者, I want 兜底文案仍然留在调用点, so that 改一句用户可见的话不必跳到另一个文件
14. As a 插件维护者, I want 闸门只做「包住一次调用」这一件窄事, so that 取当前会话、问脏值守卫这类前置判定不会挤进它的 interface
15. As a 插件维护者, I want 全局单错误位「后一次覆盖前一次」的语义原样保留, so that 这次收拢不夹带行为变化
16. As a 插件维护者, I want 一条规则拦住裸的错误兜底写法, so that 二十九处重复不会重新长出来
17. As a 插件维护者, I want 规则对全部客户端源码生效而不是只盯外壳, so that 别处不会继续长出同样的样板
18. As a 插件维护者, I want 尚未迁移的那八处登记为有主的债务, so that 它们在账上而不是被规则无声放过
19. As a 插件维护者, I want 外壳的其余职责一律不动, so that 收拢是否纯结构性可以被证明
20. As a 插件维护者, I want 四个工作台模型的完整输出在收拢前后逐字节相同, so that 「行为没变」不是一句口头承诺
21. As a 插件维护者, I want 别处变红的断言逐条区分真红与假红, so that 真实回归不被当成改名顺手改掉

## Implementation Decisions

### 两个模块，因为两族的不变量不同

二十九处样板恰好分成两族，形状不同，不变量也不同：

- **区域读取闸门**：置进行中、清错误、调用、`catch` 写文案、**`finally` 复位**。它的不变量是「无论成败都要复位进行中」。四个区域各一个实例。
- **操作错误位**：清错误、调用、`catch` 写文案。**没有进行中状态，也没有 `finally`**。它的不变量是「每次操作前先清掉上一次的错误」。

不合成一个带可选进行中参数的闸门：那会让读代码的人每次都要判断这一处传没传，而两个各自只有一条不变量的模块更难用错。

### 闸门的形状

- 工厂函数，状态以反应式引用住在模块里，外壳解构出来照旧放进工作台模型。这与仓库既有的反应式模块同形——跟随控制器、滚动恢复、搜索编排、草稿宿主都是这个形状，「有状态但与 DOM 无关的行为住在反应式模块里」也已经是一条记录在案的决定。
- 区域读取闸门 ＝ 一个共享错误位 ＋ 若干命名进行中通道。调试记录、MCP 调用、模型请求各声明两条通道（列表与详情），预设声明一条。四个区域的形状差异因此变成「声明了几条通道」，而不是「少了一个引用」。
- 两条通道必须各自独立且共用一个错误位——这是今天的行为。不用一个进行中计数器代替两个布尔：计数器在并发读取时的表现与今天不同。

### 兜底文案留在调用点

- 二十九条文案里二十七条互不相同，只有「好友操作失败」与「群组操作失败」各出现两次。文案作为闸门调用的一个参数传入。
- 不收进模块查表：那会变成一张二十七行的表，改一句用户可见的话要跳到另一个文件，而表与调用点之间没有任何东西保证同步。也不退化成统一一句「操作失败」——用户会失去「哪一步失败了」这个信息。

### 闸门只做一件窄事

- 三处操作先取当前会话标识、取不到就直接返回；一处切换会话先问预设脏值守卫。这些前置判定各不相同，且都依赖外壳自己的状态，留在外壳里。
- 闸门要做的事只有一件：包住一次可能失败的调用，把失败写成一句话。

### 全局单错误位的语义不动

- 操作那一族的十七处写入共用一个全局错误位，只有一个消费方——发送控件的外部错误字段。这意味着「后一次操作的错误会覆盖前一次」，这是当前的可观察行为。
- 本轮只统一写入方式，不拆成按区域的多个错误位、也不把它挪进别处。拆或挪都会改变这个语义，是另一件事。

### 外壳其余职责一律不动

- 区域模型装配、覆盖层、证据导航、预设脏值守卫、媒体并发读取都留在原处。外壳不是转发层——把它删掉，这些东西会散回页面装配与多个模块，复杂度扩散而不是集中，因此它该留作装配模块。
- 收窄其余五十个键是另一条候选。混进来会让「闸门收拢是否纯结构性」无从证明。

### 守卫

- 新增一条规则：客户端源码里不得出现裸的「取错误消息，取不到就用一句中文」这个形状，闸门模块是唯一持有者。形状可按正则判定，与既有几条规则同形。
- 规则扫全部客户端源码而不是只盯外壳。只盯一个文件与白名单一样——别处照样长出新的样板，而这个形状最容易被复制正是因为它看起来无害。
- 外壳之外还有八处（详情栏两处，侧栏、转发目标对话框、发送控件、预设工作台、环境实体弹层、环境新建浮层各一处），本轮不迁移，按源码文件登记为有主豁免，负责人指向各自的候选。注意这些豁免的键是**源码文件**，与断言规则那批以测试文件为键的豁免不是同一批条目。
- 不迁移它们的理由：七个组件的错误位语义各不相同，有的写进本地状态、有的外发给父级，不是一次机械迁移；而且每个都要各自的基线比对。

### 两张票

- 第一张是区域读取闸门与四个区域的迁移；第二张是操作错误位、其余十七处的迁移与守卫，阻塞于第一张——守卫在区域那一族迁完之前必然是红的。
- 二十九个调用点都在同一个文件里，爆炸半径小，不需要分批迁移。
- 模块不单独成前置票：两个模块各六十行上下，纯新增没有可比对的基线，也没有任何用户可见行为，与各自的迁移放在一起才有东西可验。

## Testing Decisions

好的测试断言外部可观察的行为，而不是实现写法。这个仓库的判据已经写下来了：肯定式实现细节断言在等价重构时变红、在真实回归时沉默。本规格不新增任何一条这样的断言。

**净 seam 数：新增两个模块 seam，去掉零个。** 目的是让两条今天不可观察的不变量变得可观察。

### 主测试面

- **两个新模块自身的 interface**。它们是纯反应式模块，不触碰 DOM、不需要任何环境，普通单元测试即可驱动。先例是工作区各控制器的测试与搜索编排的测试。
- **外壳自身的 interface（既有 seam，操作那一族的回归网）**。操作那一族已经有四条穿过外壳 interface 的行为断言：真的构造外壳、真的触发失败、断言发送控件模型上的外部错误字段等于具体文案（会话不存在、名称不能为空、实例不存在、消息不存在）。它们一字不改地继续通过，就是这一族迁移的回归网。

### 区域读取那一族要补断言

四个区域的进行中与错误状态在整个测试目录里零出现，因此这一族没有回归网，必须补：

- 置位与复位：调用期间进行中为真，成功与失败两条路径都复位。
- 失败写文案：错误位等于调用点传入的那句兜底；上游给出的错误消息优先于兜底。
- 两条通道互不影响：详情通道进行中时列表通道不为真。
- 四个区域各自独立：一个区域的错误不出现在另一个区域的模型上。
- 重试：失败后再调一次，错误位被清掉。

补断言的成本很低，而收益是「读详情时列表不该转圈」这条从未被验证过的规则第一次有了红灯——它恰好是四个区域里唯一形状差异的来源。

### 纯结构性的证明

- **stash 基线比对四个工作台模型的完整输出，逐字节相同。** 这一轮的条件比前两轮好：外壳的工作台模型本来就是 interface 的一部分，进行中与错误都是模型字段，可以直接导出比对；而在 DOM 快照里它们只体现为一个转圈动画。先例是侧栏会话树那次下沉。
- **外加一次 DOM 快照**，用来兜住模板绑定被改坏的情况。
- 每张票各跑一次。浏览器会话与临时目录按仓库规则在验收后清理，基线作为票的证据留在本 feature 目录下。

### 别处变红的处置

上一轮治理过的三个测试文件都读外壳源码断言跨层接线，其中聊天区域那一条的块注释明确标着「类别：实现细节契约（肯定式）」却被保留了下来，说明当时对它有单独的理由。本轮改外壳会让这些断言可能变红，逐条区分真红与假红——标识符变化跟着改是假红，行为口径或成本结构变化是真红，停下来查——并在票的 Comments 里逐条记处置。**不重判上一轮已经判定保留的断言**，改之前先读那条块注释。

## Out of Scope

- **外壳其余五十个键的收窄**。区域模型装配、覆盖层、证据导航、预设脏值守卫、媒体并发读取都留在原处；外壳该留作装配模块，收窄它是另一条候选。
- **外壳之外那八处错误兜底的迁移**。七个组件的错误位语义各不相同，有的写进本地状态、有的外发给父级，不是一次机械迁移。本轮把它们按源码文件登记为有主豁免。
- **把全局单错误位拆成按区域的多个**，或把它挪进发送控件那块状态。两者都会改变「后一次操作的错误覆盖前一次」这个可观察语义。
- **那几处前置判定**：取当前会话标识、问预设脏值守卫。它们各不相同且依赖外壳自己的状态。
- **工作区控制器的六十二个键**。本轮只动外壳这一侧，控制器一行不改。
- **界面、文案、样式与交互的任何调整**。本轮没有行为变化，一处例外都没有。
- **上一轮保留下来的断言的重判**。那三个已治理文件里对外壳源码的断言按上一轮的判据保留，本轮无权重判。
- **引入组件挂载测试**。这是一条已经记录在案的决定。

## Further Notes

- 最值得做的不是少二十九处重复，而是两条今天只体现在「大家都这么抄」上的规则第一次成为可断言的事实：无论成败都要复位进行中、每次操作前先清掉上一次的错误。两者改坏了都不报错——一个表现为界面一直转圈，一个表现为用户对着一条早已过期的错误发愁。
- 顺带补上的那条「读详情时列表不该转圈」是四个区域里唯一形状不一致的地方——三个区域有两条进行中通道，预设只有一条。这个差异今天靠「少声明一个引用」表达，收拢后变成「声明了几条通道」，读得出来。
- 与前三轮最大的差别是证明手段更直接。前两轮验证的是渲染结果与光标位置，都要开浏览器；这一轮要验证的进行中与错误本来就是外壳 interface 上的字段，stash 基线可以直接比对完整输出。DOM 快照仍跑一次，但它是兜底而不是主证据。
- 两张票各跑一次完整测试、类型检查与构建，外加一次基线比对。
- 守卫的新规则以源码文件为键登记豁免，与断言规则那批以测试文件为键的条目不是同一批。实施时不要把两者混进同一组。
