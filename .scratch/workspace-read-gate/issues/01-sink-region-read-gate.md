# 01 — 区域读取闸门与四个工作台的迁移

**What to build:** 四个工作台的转圈与错误文案由一个闸门模块管，「无论成败都要复位进行中」这条不变量第一次有断言。

调试记录、MCP 调用、模型请求、预设今天各抄了一份 `(进行中, 详情进行中, 错误)`，读取动作各自展开成八行样板：置进行中、清错误、调用、`catch` 里写一句中文兜底、`finally` 复位。四份状态变成四个闸门实例——前三个区域各声明列表与详情两条进行中通道，预设声明一条；错误位每个区域一个，两条通道共用。

两条通道必须各自独立：读某条详情时列表不该跟着转圈。这是今天的行为，但在整个测试目录里零覆盖，而它恰好是四个区域里唯一形状不一致的地方。不用一个进行中计数器代替两个布尔——计数器在并发读取时的表现与今天不同。

兜底文案作为调用参数留在调用点。二十七条文案互不相同且都是用户可见的，收进模块查表会让改一句话要跳到另一个文件。

操作那一族的十七处这一轮不动，两族会暂时一新一旧。用户看不到任何变化。

## Comments

### 落地形状：两个模块，闸门接过错误位

- `client/webqq/error-slot.ts` — `createErrorSlot()`，守「每次调用前先清掉上一次的错误」。
  `run` 吞掉失败，`runOrThrow` 写下文案后把原始失败原样抛给调用方（`readPreset`、
  `loadModelRequestRecord`、预设变更与几处要 reject 调用者的操作需要后者）。
- `client/webqq/region-read-gate.ts` — `createRegionReadGate(errorSlot, channels)`，守
  「无论成败都要复位进行中」。

闸门**接过**一个错误位而不是自己造一个：预设区域的「定位表达式」今天没有进度通道，它要写的又正是
预设区域那个错误位。把它做成闸门上的可选通道参数就回到了规格明确否掉的形状（读代码的人每次都要
判断这一处传没传），因此改成闸门与该处共用同一个错误位——两个模块各守一条不变量的划分没有变。

### 预设区域的通道口径

规格写的是「预设只声明一条通道」，落地声明的是 `['read', 'save']` 两条。差异是口径而不是行为：
预设今天有 `presetLoading` 与 `presetSaving` 两个进行中标志，前者被读目录与读单个预设**共用**
（这正是四个区域里唯一的形状差异——另外三个区域有独立的详情通道），后者是变更通道。
因此形状差异表达为「预设没有 `detail` 通道」，仍然写在声明上，读得出来。

> 评审补记：评审认为把保存通道放进「区域读取闸门」扭曲了模块语义。这一族的成员本来就不止读取——
> 三个区域的「清理记录」也是同一个形状（置进行中、清错误、调用、失败写文案、无论成败都复位），
> 规格自己列的这一族形状也把 `runPresetMutation` 包含在内。因此保留 `save` 通道，并在模块注释里
> 写明「读取」是这一族的名字而不是它的边界；另开一个模块只为了容纳一条通道，会让同一条不变量
> 有两个持有者。

### 兜底文案在这一层其实不可达

工作区控制器已经用 `normalizeWorkspaceError(error, fallback)` 把每个操作的失败规范化成带消息的
`WorkspaceControllerError`，而它的兜底文案与外壳这二十九句**逐字相同**。因此外壳这一层的兜底在
控制器背后到不了：上游即使抛裸字符串，也会被控制器接住并换成同一句话。

本轮不动它——规格明确要求「兜底文案仍在调用点」，删掉会改变外壳 interface 的形状，也让闸门的
`fallback` 参数失去调用点。登记为后续候选：**要么**让控制器成为这批文案的唯一持有者、外壳不再传，
**要么**反过来。兜底优先级这条规则由 `tests/error-slot.test.ts` 与 `tests/region-read-gate.test.ts`
在模块层执行；外壳层断言的是「每个读取动作把上游失败写进自己那个区域」，接错区域会变红。

### 别处变红：零条

改名涉及 `debugLoading` / `debugDetailLoading` / `debugError` / `mcpCall*` / `modelRequest*` /
`presetLoading` / `presetSaving` / `presetError` / `errorMessage` 九个标识符，整个 `tests/` 目录里
对它们的引用是**零**——规格说的「四个区域的进行中与错误状态在整个测试目录里零出现」得到证实。
上一轮治理过的三个文件（消息列表、聊天区域、发送控件）对外壳源码的断言钉的是会话树投影、转发接线与
`visitKey` 递增，与本轮改动不相交，因此没有需要判真红假红的条目，也没有重判上一轮保留的断言。
