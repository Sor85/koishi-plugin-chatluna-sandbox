# 按能力把工作区端口拆开，它是最后一个大杂烩

Status: ready-for-agent

## Problem Statement

WebQQ 客户端有一道 38 个成员的端口，横跨六个互不相干的领域：场景消息读写、环境与关系操作、OneBot 调试记录、模型请求记录、预设文件、MCP 调用记录，再加一条场景变更广播。

按能力拆端口这件事在这个客户端里已经做过两次——MCP 管理面 9 个成员、AI 测试空间生命周期 7 个成员，各自都有自己的注释写明为什么不进工作区端口。工作区端口是留下来的那个大杂烩。

代价有三处：

- **每个消费方都被迫依赖整份宽 interface。** 调试记录工作台只用其中三个成员，却要面对 38 个。
- **测试也要面对同样宽的假端口。** 假端口 350 行，13 个测试文件在用；测试目录里已经有四个按区域分开的控制器测试文件（调试、MCP 调用、模型请求、预设），每一个都只需要三到七个成员，却都要准备整份。
- **加一个能力要往公共 interface 里塞方法**，所有消费方的 interface 跟着变宽。

页面装配还构造了**两份**这个端口：一份跟随当前活动空间，一份不定域。后者唯一的消费方是 AI 测试空间外壳，用它画缩略图（要能读任意空间），却白白带着 17 个与它无关的成员。

## Solution

按能力拆出四道端口：OneBot 调试记录、模型请求记录、预设文件、MCP 调用记录。场景消息读写、环境与关系操作、场景变更广播留在工作区端口。

每道新端口各配一个 Koishi 适配器与一个假适配器，假适配器共用同一个记录器。每个工作台只学自己那道端口；测试只准备自己用到的那几个方法。

用户看不到任何变化。端点名、请求载荷、隐式定域的边界、每个工作台的行为与界面，全部与今天一字不差。

## User Stories

1. As a 沙盒用户, I want 聊天、调试、模型请求、预设、MCP 调用五个界面的行为一字不变, so that 一次结构性拆分不需要我重新验收
2. As a 沙盒用户, I want 切到某个 AI 测试空间后各界面读到的仍然是那个空间的数据, so that 隐式定域没有变化
3. As a 沙盒用户, I want 模型请求记录在「全部空间」与「未归属」分类下仍然读得到, so that 切换空间不会让这些分类被当前空间覆盖
4. As a 沙盒用户, I want 预设文件仍然是全局的, so that 换空间不影响我在编辑的预设
5. As a 沙盒用户, I want MCP 调用记录仍然跨主环境与全部空间共享, so that 我能在一处复盘一轮编排
6. As a 沙盒用户, I want 空间缩略图仍然能画出任意空间, so that 空间列表的预览不受影响
7. As a 沙盒用户, I want 场景变更广播仍然扇出给全部订阅者, so that 多个页面同时打开时都能刷新
8. As a 沙盒用户, I want 界面、文案、样式与交互没有任何变化, so that 这一轮不占用我的验收时间
9. As a 插件维护者, I want 每个工作台只依赖自己那道端口, so that 读它的时候不必面对另外五个领域
10. As a 插件维护者, I want 调试工作台的测试只准备调试那三个方法, so that 我不必为一个三方法的能力搭一份 38 方法的桩
11. As a 插件维护者, I want 加一个新能力时不动别人的 interface, so that 消费方不会跟着变宽
12. As a 插件维护者, I want 改预设相关的通信时聊天与调试的测试不跟着受影响, so that 变红的范围与改动的范围相称
13. As a 插件维护者, I want 前后端端点与前端能力的对应关系按能力分组, so that 它不再是一份 38 行的平表
14. As a 插件维护者, I want 拆分依据是「输入里有没有对方的概念」而不是文件大小, so that 拆法可以被复述和检验
15. As a 插件维护者, I want 环境与关系操作留在工作区端口, so that 不出现两个都返回工作区状态的端口
16. As a 插件维护者, I want 调试记录那道端口带上同一个定域来源, so that 定域行为逐字不变
17. As a 插件维护者, I want 三道不定域的端口只需要一份实例, so that 装配不再构造两份完整的宽端口
18. As a 插件维护者, I want 不定域那份端口收窄到只剩场景那一道, so that 它不再带着 17 个与它无关的成员
19. As a 插件维护者, I want 五个假端口共用同一个记录器, so that 断言调用序列的写法不必学第二套
20. As a 插件维护者, I want 工作区控制器仍是一个 module, so that 这一轮的范围可以被证明
21. As a 插件维护者, I want 端点名与请求载荷逐字不变, so that 服务端一行都不用改
22. As a 插件维护者, I want 隐式定域的三条边界仍然有断言, so that 本轮最容易改坏的东西有红灯
23. As a 插件维护者, I want 四个工作台模型与发送控件模型的完整输出逐字节相同, so that 「行为没变」不是一句口头承诺
24. As a 插件维护者, I want 服务端一行不改并且可以用 diff 证明, so that 拆分确实只发生在客户端
25. As a 插件维护者, I want 既有那条「RPC 只许在端口适配器里」的守卫自动覆盖新增的八个文件, so that 不需要为拆分新增规则
26. As a 插件维护者, I want 不引入按成员数或文件大小判定的规则, so that 守卫不会逼出为了达标而做的拆分
27. As a 插件维护者, I want 这次拆分记进已有的那条 ADR 而不是新写一条, so that 它读起来是同一个决定的深化

## Implementation Decisions

### 四道拆出去，三组留下

- 拆出去：OneBot 调试记录 3 个、模型请求记录 4 个、预设文件 7 个、MCP 调用记录 3 个，共 17 个成员。
- 留在工作区端口：场景消息读写 17 个、环境与关系操作 3 个、场景变更广播 1 个，共 21 个。
- 环境与关系操作不拆成第五道。它返回的是同一份工作区状态，与消息读写共享场景这个概念——按既有那条 ADR 的判据（两者的输入里都没有对方的概念）它们不独立，拆开会得到两个都返回工作区状态的端口。

### 隐式定域是拆分依据的第二半

- 适配器里今天已经把这 38 个成员分成两半：场景消息、环境与关系、OneBot 调试**注入当前观察空间的标识**；模型请求、预设、MCP 调用记录、场景广播**不注入**。
- 每一组不注入的都有自己的理由，写在适配器的注释里：模型请求的未归属分类没有空间标识、切到别的空间也不该被当前观察空间覆盖；预设文件是全局 ChatLuna 资源；MCP 调用记录跨主环境与全部空间共享，筛选里的空间标识是记录字段而不是定域；广播的载荷自带空间标识。
- 因此判据在原有的「输入里有没有对方的概念」之外再加一条：**适配器要不要注入当前空间**。两条合起来把这次拆法完全确定下来，不需要任何按大小的判断。

### 调试记录那道带上同一个定域来源

- 它是四道里唯一定域的。它的工厂收同一个「解析当前空间标识」的函数，与工作区端口的工厂共用一个实参。
- 定域是适配器往请求里注入当前观察空间，不是 interface 上的概念，因此不构成「共享概念」，不影响拆分判据。
- 不因为它定域就把它留下：调试记录的输入里没有任何场景概念（只有记录标识、筛选与可选空间标识），而调试工作台是独立消费方、已有独立测试文件。留下它会让「为什么这三个在里面」变成一个没有答案的问题。

### 装配侧：不定域那份端口跟着收窄

- 页面装配今天构造两份工作区端口，一份跟随当前活动空间、一份不定域。
- 不定域那份唯一的消费方是 AI 测试空间外壳，用它画空间缩略图（必须能越过隐式定域读任意空间）。拆完之后它只需要场景那一道，从 38 个成员降到 21 个。
- 三道不定域的端口不需要第二份实例——它们的适配器根本不注入空间标识，构造一次就够。

### 假端口按能力拆，记录器共用

- 五个假端口，各自只造自己那道的桩，**共用同一个记录器**，写法不变。
- 十三个测试文件按自己用到的能力各取所需。测试目录里那四个按区域分开的控制器测试文件正好各只需要一道。

### 工作区控制器不拆

- 控制器仍是一个 module，只是构造时收五个端口而不是一个；外壳与页面装配跟着传。
- 收窄控制器的成员表是另一条候选，且已经被前一轮明确列为范围外。混进来会让「按能力拆端口是否纯结构性」无从证明。

### 守卫不新增

- 既有那条「收发 Koishi RPC 的函数只允许出现在客户端端口适配器里」按文件名模式判定持有者，新增的四个真适配器与四个假适配器自动落在模式内。
- **不加按成员数或文件大小判定的规则。** 拆分依据是能力归属，不是尺寸；一条尺寸规则会逼出为了达标而做的拆分，那与本轮的判据相反。

### ADR 只补一段，不新写

- 这是既有那条「客户端按能力拆分端口」ADR 的深化而不是翻案。补一段形状说明：哪些能力留在工作区端口、判据除了「输入里有没有对方的概念」还加上「适配器要不要注入当前空间」、以及不定域那份端口为什么只需要场景那一道。
- 显式空间标识仍然优先于隐式定域，跨空间的枚举仍归记录域目录，这两条既有决定一字不改。
- 领域词汇不需要新词，落地时核一遍。

## Testing Decisions

好的测试断言外部可观察的行为，而不是实现写法。本仓库的判据已经写下来了：肯定式实现细节断言在等价重构时变红、在真实回归时沉默。本规格不新增任何一条这样的断言。

**净新增 seam 数：四个端口 interface 加四个假适配器，但净测试面不变宽——它是把一道 38 成员的 seam 切成五道窄的。** 消费方一侧的 seam 数量不变（每个工作台原来经一道宽端口，现在经一道窄端口）。

### 主测试面

- **真适配器的既有 seam（主证据）**。已有一份针对 Koishi 工作区适配器的测试，183 行、8 个用例、19 处端点名。其中三个用例专门钉住隐式定域的边界：预设调用保持全局、模型请求记录按显式分类发送而不注入当前空间、MCP 调用记录按筛选参数发送而不注入当前空间。**这是本轮最容易改坏的东西的红灯。** 拆分后它按端口分成对应的几份，断言内容一字不改——端点名与定域行为逐条搬过去，不新增也不删减。
- **四个按区域分开的控制器测试（既有 seam，回归网）**。调试、MCP 调用、模型请求、预设各一份，它们本来就只驱动自己那一道能力。拆分后各自只准备自己那道假端口，断言一字不改。
- **工作区外壳与控制器的既有测试（既有 seam）**。场景消息、会话树、消息能力、外壳区域、操作错误位、缩略图投影那几份继续通过。
- **架构守卫（既有 seam）**。既有那条 RPC 规则自动覆盖新增文件，落地后核实零新增违规、零新增豁免。

### 不新增的断言

- 不为「某个端口只有 N 个成员」写断言：那是按尺寸判定，与本轮的拆分依据相反。
- 不为端口 interface 的成员清单写形状断言：它由真适配器测试里的端点名与各控制器测试的行为从外部证明。

### 纯结构性的证明

- **真适配器测试的端点名与三条定域断言一字不改地通过。** 主证据。
- **stash 基线比对四个工作台模型与发送控件模型的完整输出**，逐字节相同。沿用前一轮的手法：工作台模型本来就是外壳 interface 的一部分，可以直接导出比对，比 DOM 快照直接。
- **一次 DOM 快照**兜住模板绑定被改坏的情况。
- **完整测试、类型检查与构建通过。**
- **`git diff --stat` 里不出现服务端源码路径**，作为一条验收项。本轮服务端一行不改。
- 每张票各跑一次。基线作为票的证据留在本 feature 目录下。

### 别处变红的处置

改端口 interface 会让读客户端源码或按端口成员名断言的测试变红。逐条区分真红与假红——标识符变化跟着改是假红，行为口径或成本结构变化是真红，停下来查——并在票的 Comments 里逐条记处置。**不重判前几轮已经判定保留的断言。**

## Out of Scope

- **把环境与关系操作拆成第五道端口。** 它返回同一份工作区状态，与消息读写共享场景概念。
- **收窄工作区控制器的成员表。** 已被前一轮明确列为范围外，且与本轮的可证明性冲突。
- **拆分工作区外壳。** 它是装配 module，本轮只改它收几个端口。
- **服务端的任何改动。** 端点名与请求载荷逐字不变，Console 契约一行不改。
- **隐式定域口径的任何调整。** 显式空间标识优先于隐式定域，三组不定域的能力仍然不定域。
- **跨空间枚举。** 仍归记录域目录，本轮不碰。
- **按成员数或文件大小设守卫。** 与本轮判据相反。
- **界面、文案、样式与交互的任何调整。** 本轮没有行为变化，一处例外都没有。

## Further Notes

- 最值得做的不是少一份宽 interface，而是每个工作台的测试从「准备 38 个方法的桩」变成「准备三到七个」。测试目录里那四个按区域分开的控制器测试文件已经存在——四道 seam 在测试一侧早就是真的，只是端口没跟上。
- 拆法完全由两条判据确定，不需要任何主观分组：**输入里有没有对方的概念**（既有 ADR 的判据）加上**适配器要不要注入当前空间**（这次核出来的第二半）。后者今天已经写在适配器的注释里，每一组不注入的都各有理由。这也是为什么本轮不需要按大小判断，也不该引入按大小的守卫。
- 报告的 before 分组表容易被读成五道端口，但它的 after 图与判据都指向四道加一道留下。差别在于环境与关系操作：它和消息读写返回同一份工作区状态。
- 「装配构造了两份宽端口」这件事是核查时顺带发现的：不定域那份唯一的消费方是空间缩略图，却带着 17 个与它无关的成员。拆完之后它自然收窄，不需要单独一条改动。
- 本轮唯一的风险点是隐式定域，而它已经有三条断言钉着。这也是票 01 与 02 的切分依据——01 那三道完全不碰定域逻辑。
