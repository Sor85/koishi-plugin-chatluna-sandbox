# 02 — 调试记录那道拆出去，不定域那份端口跟着收窄

**What to build:** 调试工作台也只学自己那道端口，工作区端口从 38 个成员降到 21 个；切到某个 AI 测试空间后调试记录读到的仍然是那个空间的数据，一字不变。

这一道是四道里**唯一定域的**，也是本轮唯一的风险点。它的工厂收同一个「解析当前空间标识」的函数，与工作区端口的工厂共用一个实参，因此定域行为逐字不变。不因为它定域就把它留下：调试记录的输入里没有任何场景概念（只有记录标识、筛选与可选空间标识），而调试工作台是独立消费方、已有独立测试文件；留下它会让「为什么这三个还在里面」变成一个没有答案的问题。

页面装配今天构造两份工作区端口，一份跟随当前活动空间、一份不定域。**不定域那份唯一的消费方是 AI 测试空间外壳**，用它画空间缩略图（必须能越过隐式定域读任意空间）。拆完之后它只需要场景那一道，从 38 个成员降到 21 个——这是自然结果，不是额外改动。

留在工作区端口的是场景消息读写 17 个、环境与关系操作 3 个、场景变更广播 1 个。环境与关系**不拆**：它返回的是同一份工作区状态，与消息读写共享场景这个概念，拆开会得到两个都返回工作区状态的端口。

给既有那条「客户端按能力拆分端口」的 ADR 补一段形状说明，**不新写 ADR**——这是它的深化而不是翻案。

## Comments

### 落地形状

- 三件套：`onebot-debug-port.ts`（interface + `OneBotDebugPortOperation`）、`koishi-onebot-debug-port.ts`、`fake-onebot-debug-port.ts`。
- `createKoishiOneBotDebugPort(resolveSpaceId)` 与 `createKoishiWorkspacePort(resolveSpaceId)` 收同一个实参（页面装配两处都传 `() => activeSpaceId.value`），并共用新抽出的 `koishi-space-scope.ts`。隐式定域实现只有一份的理由写在该模块的注释里：「显式定域优先」是一条规则而不是两条，抄成两份之后其中一份被改动不会有任何红灯。
- 工作区端口 21 个成员：场景消息读写 17、环境与关系操作 3、场景变更广播 1。环境与关系未拆成第五道。
- 四道记录域端口的成员数：调试 3、模型请求 4、预设 7、MCP 调用记录 3。
- 不定域那份端口（`mainWorkspacePort`）随 `WorkspacePort` 一起收窄到 21 个成员，装配处的注释说明它为什么只需要场景那一道。这是拆分的自然结果，没有单独改动。
- 假端口共用 `FakePortRecorder`，注释里的计数从「三个」更新到「七个」。

### 定域的断言

新增 `tests/koishi-onebot-debug-port.test.ts` 三条，钉住这道端口的定域行为（本轮唯一的风险点，此前客户端一侧零覆盖）：

- 三个端点都附加当前活动空间的 `spaceId`；
- 调用方指名 `spaceId` 时显式定域优先，不被覆盖；
- 没有活动空间时不附加 `spaceId`。

搬迁的那三条不注入断言与 19 个端点名内容一字未改。空间缩略图跨空间读媒体的既有断言（`tests/workspace-thumbnail-projection.test.ts`「按显式 spaceId 读媒体，主环境省略 spaceId」）与场景广播「只注册一次并扇出」的既有断言均未改、均通过。
