# OneBot Sandbox 参与者与逻辑会话重构规格

Status: ready-for-agent

## Problem Statement

OneBot Sandbox 已经允许普通用户和虚拟 OneBot 机器人作为统一的当前操作者，但底层仍保留普通用户与机器人两套目录、`currentUserId` 与 `currentOperatorId` 的历史痕迹、`actorUserId` 与 `senderId` 等重复身份输入，以及以 `userId`、`botId` 描述两端的定向会话。随着机器人也能成为群主、发送消息和切换观察视角，这些字段的名称与真实语义发生偏离，导致新代码容易把机器人错误地当成需要普通用户代理的特殊情况。

当前会话结构还会为普通用户双方创建镜像私聊，并为群成员与机器人组合创建多条底层群会话。同一条群消息因此可能被重复存储或需要镜像，同一群组在机器人视角下可能出现多个入口，消息方向、好友页面、权限和 ChatLuna 状态也需要大量 `operatorIsBot` 分支才能保持一致。

插件尚未公开发布，不存在需要兼容的正式旧场景、RPC 或 MCP 合同。继续保留旧字段、迁移逻辑和双模型只会形成长期维护负担。本次重构需要直接建立以参与者、当前操作者、逻辑会话和机器人事件投递为核心的唯一领域模型，并同步更新所有调用方、测试、默认场景和未来 MCP 规格。

## Solution

沙盒场景改用带参与者种类的统一参与者目录，普通用户和虚拟 OneBot 机器人共享资料、关系、群角色、会话可见性和消息作者模型。所有真实交互命令只接受 `operatorId`，消息作者始终等于操作者；环境管理不携带操作者身份，虚拟 OneBot action 则继续使用真实机器人 `selfId`。

私聊改为任意两个参与者之间唯一的稳定逻辑会话，群聊改为每个群组唯一的逻辑会话。聊天消息在逻辑会话中只保存一次，不携带冗余机器人 ID；同一消息可以根据会话参与者和群成员动态向多个虚拟 OneBot 机器人产生独立事件投递。ChatLuna 状态使用机器人参与者 ID 与逻辑会话 ID 关联。

WebQQ、Console RPC、虚拟 OneBot 适配器和未来 MCP 共用共享测试控制模块这一主要测试接缝。所有旧字段、旧 ID 格式、镜像会话、兼容解析、localStorage 迁移和 fallback 直接删除，不提供未发布实现的兼容层。

## User Stories

1. 作为 WebQQ 用户，我希望普通用户和虚拟 OneBot 机器人来自同一个参与者目录，从而不会因页面不同而使用两套身份查找规则。
2. 作为 WebQQ 用户，我希望任意参与者都可以成为当前操作者，从而能够从用户或机器人视角观察同一模拟 QQ 环境。
3. 作为 WebQQ 用户，我希望当前操作者切换后最近会话同步变化，从而只看到该参与者当前可见的会话。
4. 作为 WebQQ 用户，我希望当前操作者切换后好友目录同步变化，从而看到该参与者自己的好友关系和好友备注。
5. 作为 WebQQ 用户，我希望当前操作者切换后群组目录同步变化，从而看到该参与者加入、申请中或未加入的群组。
6. 作为 WebQQ 用户，我希望当前操作者切换后通知同步变化，从而只处理发给该参与者或由其群角色负责的申请。
7. 作为 WebQQ 用户，我希望当前操作者切换后权限同步变化，从而群主、管理员和普通成员获得正确操作菜单。
8. 作为 WebQQ 用户，我希望当前操作者永远也是当前发送者，从而不会出现操作者与消息作者互相矛盾的状态。
9. 作为 WebQQ 用户，我希望自己的消息始终位于右侧并使用强调色，从而用户和机器人操作者获得一致视觉反馈。
10. 作为 WebQQ 用户，我希望对端消息始终位于左侧，从而消息方向只由作者与当前操作者决定。
11. 作为 WebQQ 用户，我希望机器人头像、徽标和资料仍按参与者种类展示，从而统一目录不会丢失机器人身份区分。
12. 作为 WebQQ 用户，我希望普通用户头像不会继承机器人样式，从而参与者统一不会造成视觉类型泄漏。
13. 作为 WebQQ 用户，我希望当前操作者选择只保存一个参与者 ID，从而浏览器中不存在普通用户代理状态。
14. 作为 WebQQ 用户，我希望删除当前参与者后自动选择仍存在的参与者，从而页面不会停留在无效操作者状态。
15. 作为 WebQQ 用户，我希望所有环境管理表单从同一参与者目录选择成员，从而用户和机器人都能承担群角色。
16. 作为 WebQQ 用户，我希望机器人可以在创建或编辑群组时成为群主，从而环境管理与真实群角色模型一致。
17. 作为 WebQQ 用户，我希望机器人群主被删除时其拥有的群组按统一规则处理，从而不会留下没有群主的无效群组。
18. 作为插件开发者，我希望任意两个参与者之间只有一个私聊会话，从而不同观察视角引用同一个聊天历史。
19. 作为插件开发者，我希望私聊会话 ID 与操作者方向无关，从而用户切换后会话 ID 保持稳定。
20. 作为插件开发者，我希望私聊 ID 使用排序后的参与者 ID，从而创建顺序不会产生第二条镜像会话。
21. 作为插件开发者，我希望每个群组只有一个群聊会话，从而机器人视角不会看到同一群组的多个入口。
22. 作为插件开发者，我希望群聊 ID 只由群组 ID 决定，从而成员或机器人变化不会改变历史会话标识。
23. 作为插件开发者，我希望群成员退出后群聊历史继续存在，从而关系变化不会销毁测试证据。
24. 作为插件开发者，我希望好友删除后私聊历史继续存在，从而重新建立好友关系时恢复同一会话历史。
25. 作为插件开发者，我希望失去好友关系的参与者不能继续发送私聊消息，从而保留历史不等于保留交互权限。
26. 作为插件开发者，我希望退出群组的参与者不能读取或发送群消息，从而会话访问仍服从当前成员关系。
27. 作为插件开发者，我希望重新入群后参与者重新获得同一群聊访问，从而不创建新的群聊历史分支。
28. 作为插件开发者，我希望删除参与者时清理其私聊和只有该参与者关联的数据，从而不会保留悬空引用。
29. 作为插件开发者，我希望删除群组时清理对应逻辑群聊和历史，从而显式环境删除仍能完整释放数据。
30. 作为插件开发者，我希望群消息只存储一份，从而群内机器人数量不会放大消息历史。
31. 作为插件开发者，我希望私聊消息只存储一份，从而用户双方观察同一消息对象。
32. 作为插件开发者，我希望消息只记录作者和逻辑会话，从而消息不绑定某个观察机器人。
33. 作为插件开发者，我希望同一群消息可以向所有符合条件的机器人分别派发，从而多机器人插件行为得到真实验证。
34. 作为插件开发者，我希望机器人发送群消息时不向自身派发入站事件，从而不会产生自我响应循环。
35. 作为插件开发者，我希望机器人发送群消息时其他机器人仍收到入站事件，从而多机器人环境保持真实。
36. 作为插件开发者，我希望用户向机器人私聊时只向对端机器人派发事件，从而私聊接收者明确。
37. 作为插件开发者，我希望机器人之间私聊时只向对端机器人派发事件，从而发送机器人不会收到自己的入站消息。
38. 作为插件开发者，我希望普通用户之间私聊不产生 OneBot 机器人事件，从而无机器人参与的聊天不会伪造协议事件。
39. 作为插件开发者，我希望每次机器人事件投递都标明接收机器人，从而能区分同一消息向不同机器人的投递结果。
40. 作为插件开发者，我希望所有机器人事件中的 `self_id` 仍等于机器人真实 `selfId`，从而插件能可靠获取自身 QQ ID。
41. 作为插件开发者，我希望 `get_login_info` 继续返回当前机器人 QQ ID，从而删除消息级机器人字段不会破坏协议能力。
42. 作为插件开发者，我希望机器人 action 继续以自身 `selfId` 作为操作者，从而 WebQQ 的 `operatorId` 不污染 OneBot 适配器接口。
43. 作为插件开发者，我希望机器人修改自身昵称和头像仍更新统一参与者资料，从而后续消息和列表显示最新资料。
44. 作为插件开发者，我希望机器人启用状态和实现配置仍只存在于机器人种类参与者上，从而普通用户不暴露无意义字段。
45. 作为插件开发者，我希望 NapCat 和 LLBot 行为差异继续按机器人参与者配置，从而参与者统一不会合并实现基线。
46. 作为 ChatLuna 用户，我希望思考状态按机器人参与者 ID 和逻辑会话 ID 关联，从而同一群中的多个机器人可以独立思考。
47. 作为 ChatLuna 用户，我希望 Token 用量附着到正确机器人和逻辑会话，从而切换操作者不会改变状态归属。
48. 作为 ChatLuna 用户，我希望无法确定机器人或会话归属的状态不显示，从而不会出现全局错误状态。
49. 作为 Console RPC 调用方，我希望所有交互输入统一使用 `operatorId`，从而接口名称与真实参与者语义一致。
50. 作为 Console RPC 调用方，我希望消息发送不再接受独立 `senderId`，从而无法伪造与操作者不同的作者。
51. 作为 Console RPC 调用方，我希望消息发送不再要求 `botId`，从而接收机器人由逻辑会话自动推导。
52. 作为 Console RPC 调用方，我希望环境管理命令不携带 `operatorId`，从而测试准备与真实 QQ 交互保持分离。
53. 作为 Console RPC 调用方，我希望工作区查询使用 `operatorId` 过滤可见数据，从而普通用户和机器人共享同一查询合同。
54. 作为未来 MCP 调用方，我希望每次交互显式提供 `operatorId`，从而不存在服务端隐藏当前操作者。
55. 作为未来 MCP 调用方，我希望 MCP 只允许普通用户参与者作为操作者，从而外部控制器不能冒充虚拟 OneBot 机器人。
56. 作为未来 MCP 调用方，我希望会话返回稳定的逻辑会话结构，从而切换用户视角不会得到不同会话 ID。
57. 作为未来 MCP 调用方，我希望消息结果不包含冗余 `botId`，从而消息合同与单份存储一致。
58. 作为未来 MCP 调用方，我希望 OneBot 事件结果使用 `recipientBotId`，从而可以过滤某个机器人收到的事件。
59. 作为未来 MCP 调用方，我希望消息 ID 在所有机器人事件投递中保持一致，从而可以关联聊天事实与协议事件。
60. 作为未来 MCP 调用方，我希望群聊只出现一个会话，从而消息等待不会因机器人数量返回重复事实。
61. 作为维护者，我希望普通用户和机器人使用判别联合，从而只有需要机器人能力的代码才检查参与者种类。
62. 作为维护者，我希望参与者查找只有一个领域入口，从而不再反复合并用户目录和机器人目录。
63. 作为维护者，我希望会话可见性只有一个领域规则，从而 WebQQ、OneBot 和未来 MCP 不复制判断逻辑。
64. 作为维护者，我希望机器人事件接收者只有一个推导规则，从而消息存储与事件派发不会再次耦合。
65. 作为维护者，我希望删除所有旧字段别名和 fallback，从而新代码无法继续依赖错误术语。
66. 作为维护者，我希望删除浏览器 `currentUserId` 迁移，从而本地状态只保存正式 `currentOperatorId`。
67. 作为维护者，我希望删除旧私聊和群聊 ID 解析，从而测试不会为未发布结构保留兼容路径。
68. 作为维护者，我希望默认场景直接生成新参与者和逻辑会话结构，从而启动后不会执行迁移。
69. 作为维护者，我希望场景导入导出只接受新结构，从而未发布旧 JSON 不形成长期版本负担。
70. 作为维护者，我希望类型错误直接暴露所有旧调用方，从而重构可以完整更新而不是用类型断言掩盖问题。
71. 作为测试维护者，我希望领域行为主要通过共享测试控制模块验证，从而测试关注外部结果而不是内部辅助函数。
72. 作为测试维护者，我希望 OneBot 适配器只验证协议合同，从而不会重复领域模块的全部行为测试。
73. 作为测试维护者，我希望 WebQQ 测试验证操作者切换后的可见行为，从而不依赖组件内部状态实现。
74. 作为测试维护者，我希望 Console RPC 测试验证新字段和结构，从而未来 MCP 可以复用稳定合同。
75. 作为测试维护者，我希望回归测试覆盖用户、机器人、用户间私聊、机器人间私聊和多机器人群聊，从而身份分支不会再次失衡。
76. 作为测试维护者，我希望回归测试覆盖关系删除、重新添加、退群和重新入群，从而逻辑会话生命周期明确。
77. 作为测试维护者，我希望回归测试覆盖同一消息的单份存储和多次机器人投递，从而消息与事件边界得到验证。

79. 作为测试维护者，我希望完整测试、类型检查和构建在重构结束前全部通过，从而结构修改没有遗漏调用方。
80. 作为项目维护者，我希望本次重构保持现有 WebQQ 视觉与动画不变，从而领域修复不会变成 UI 重设计。

## Implementation Decisions

- 沙盒场景使用一个统一参与者目录，参与者通过明确种类区分普通用户和虚拟 OneBot 机器人。
- 机器人实现配置、启用状态和能力覆盖只属于机器人种类参与者；机器人运行时不进入场景序列化数据。
- 所有真实参与者交互使用 `operatorId`，消息作者直接取 `operatorId`，不接受独立发送者身份。
- 环境管理是静默测试准备操作，不携带 `operatorId`，群主和成员通过提交的群成员结构明确指定。
- 虚拟 OneBot action 入口继续使用当前机器人真实 `selfId`，`get_login_info` 与事件 `self_id` 不受领域字段删除影响。
- 私聊会话由两个排序后的参与者 ID 唯一标识，参与者顺序和当前操作者不影响会话 ID。
- 群聊会话只由群组 ID 唯一标识，不再为成员与机器人组合生成底层会话。
- 会话实体不包含固定用户端或机器人端字段；私聊保存参与者对，群聊保存群组引用。
- 消息实体保存消息 ID、逻辑会话 ID、作者参与者 ID、内容、时间、回复、媒体和事件信息，不保存冗余机器人 ID。
- 消息发送命令只需要 `operatorId`、逻辑会话 ID 和消息内容或媒体，不接受 `senderId` 或 `botId`。
- 一条聊天消息只追加一次；机器人事件投递根据私聊对端或群成员动态推导，并为每个目标机器人独立派发。
- 私聊用户删除好友后保留底层逻辑会话和消息历史，但普通交互和常规工作区不可继续访问；重新成为好友后恢复同一会话。
- 群成员退群后保留群聊和历史，但该参与者失去访问；重新入群后恢复对同一群聊的访问。
- 删除参与者或群组属于显式环境删除，可以清理对应逻辑会话、消息、关系、申请和媒体引用。
- ChatLuna 思考状态与 Token 用量使用机器人参与者 ID 和逻辑会话 ID 关联，不依赖消息或会话中的机器人字段。
- WebQQ 只保存一个当前操作者 ID；最近、好友、群组、通知、权限、消息方向和发送身份都从该 ID 推导。
- WebQQ 视觉、DOM 结构、布局、动画、右键菜单和响应式行为不在本规格中重设计。
- Console RPC 所有参与者交互字段统一命名为 `operatorId`，工作区查询也使用该字段。
- 未来 MCP 交互工具使用 `operatorId`，但 MCP 适配器只接受普通用户或测试用户；机器人动作必须通过真实 OneBot action 产生。
- 未来 MCP 会话输出使用逻辑会话结构，消息输出不包含机器人 ID，OneBot 事件输出使用 `recipientBotId` 描述投递对象。
- 场景导入导出、默认场景、测试 fixture 和浏览器本地状态全部直接切换到新结构。
- 插件尚未公开发布，不实现旧字段、旧会话 ID、旧场景 JSON、旧 localStorage 或旧 RPC 的兼容、迁移和 deprecated 别名。
- 共享测试控制模块是唯一主要行为接缝；WebQQ RPC、虚拟 OneBot 和未来 MCP 是其适配器，不复制领域状态转换。
- 实施时优先让类型系统暴露旧调用方，不通过宽泛类型、可选旧字段或类型断言隐藏未完成迁移。

## Testing Decisions

- 好测试只通过公开领域操作、适配器合同和用户可见结果验证行为，不断言私有查找函数、内部数组顺序或辅助函数调用次数。
- 共享测试控制模块是主要测试接缝，覆盖参与者管理、操作者权限、逻辑会话生命周期、消息单份存储和机器人事件投递。
- 参与者测试覆盖普通用户和机器人创建、编辑、删除、群角色、群主转让、资料修改和运行时分离。
- 私聊测试覆盖用户与机器人、用户与用户、机器人与机器人三类参与者组合，并验证稳定 ID、单份历史和对端推导。
- 群聊测试覆盖一个群一个逻辑会话、多机器人接收、机器人发送不自投递和其他机器人仍接收。
- 关系测试覆盖好友审批、删除、重新添加、会话访问撤销和历史恢复。
- 群成员测试覆盖退群、踢人、重新入群、群主与管理员权限，以及历史保留。
- 消息测试验证作者等于操作者、回复与媒体引用保持有效、消息只存一份且多机器人事件共享消息 ID。
- OneBot 适配器合同测试验证 `selfId`、`get_login_info`、`self_id`、私聊/群聊 channel、消息查询、撤回和机器人 action。
- ChatLuna 测试验证同一逻辑会话中不同机器人状态相互独立，切换当前操作者不改变状态归属。
- WebQQ 测试验证用户和机器人操作者下的最近、好友、群组、通知、权限、头像和消息方向一致，不测试组件内部 ref 或 computed 名称。
- Console RPC 测试验证只接受 `operatorId` 和新逻辑会话结构，并确认旧字段不再出现在类型和运行时合同中。
- 场景测试验证默认场景和导入导出只使用新结构，不接受旧 `users`、`bots`、`userId`、会话 `botId` 或消息 `botId`。
- 回归测试沿用现有控制模块、好友关系、群权限、OneBot bridge、工作区控制器、关系目录、消息列表和 ChatLuna 状态测试的外部行为模式。
- 重构结束前运行完整单元与集成测试、类型检查、生产构建和差异检查。
- WebUI 行为受影响时使用 Ego Browser 验证 Chrome 路径，并用 Firefox 验证操作者切换、会话列表和消息方向；所有浏览器任务结束后关闭并清理临时文件。

## Out of Scope

- AI 测试空间、多场景管理、空间控制租约、用户接管和空间缩略工作台墙；这些内容由独立 Issue 19 承接，并在基础 MCP 完成后实施。
- MCP 监听器、认证、限流、幂等缓存、事件等待和空间生命周期的具体实现。
- NapCat 或 LLBot 新 action、兼容基线升级和能力矩阵扩展。
- WebQQ 视觉重设计、布局调整、新图标、流光动画或 AI 空间 FLIP 动画。
- 修改 Koishi、Satori 或 OneBot 协议本身对 `user_id`、`self_id` 和 `bot.selfId` 的正式命名。
- 为尚未发布的旧场景、旧 RPC、旧 localStorage 或旧会话 ID 提供迁移工具。
- 将机器人运行时实例序列化进沙盒场景。
- 改变服务端内存默认状态所有权或 Koishi Database 可选持久化策略。

## Further Notes

- 本规格落实 ADR-0041 和 ADR-0042，并同步遵守 ADR-0039 的统一当前操作者规则。
- `botId` 只在确实表示虚拟 OneBot 机器人参与者或机器人运行时的内部语境中保留；不得再作为逻辑会话端点或消息归属字段。
- OneBot 协议中的 `self_id` 和 Koishi Bot 的 `selfId` 是正确且必须保留的机器人身份，不属于本次删除范围。
- 环境管理与真实参与者交互继续保持不同领域路径，不能因为字段统一而产生测试准备事件。
- MCP 仍不允许外部测试控制器冒充机器人；未来 AI 测试空间中的机器人操作仍必须通过真实 OneBot action 验证。
- 首次 npm 公开发布前应直接删除旧结构而不是保留兼容层；首次公开发布后按项目正式版本兼容策略处理。
- 本规格的 Triage 状态为 `ready-for-agent`，可以直接进入拆票或实现流程。
