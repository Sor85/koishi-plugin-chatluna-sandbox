# 候选备忘：共享模型证据投影按记录身份记忆化

Status: resolved（按结构修正的方式解决，未引入缓存层）

这不是规格,是一条已核实但尚未规划的候选。记录下来是因为它的核对数据来自一次专门的事实核查,不落盘就会丢。

## 结论

按备忘里「先做结构修正、不加缓存层」的方向解决：轨迹派生现在每条记录只投影一次，
并把那份投影同时交给变量派生、请求行投影和请求组成投影。共享模型证据投影的
「不做全局缓存」声明保持不变，无需重新审视。

单次会话轨迹读取的投影次数从 `1 + 3M` 降到 `1 + M`（M 为聚合出的记录数）：
入口详情读取一次，记录循环里每条一次。变量派生从每条记录两次降到一次。

同时消除的两处读取放大：

- 列表投影不再深拷贝请求体与响应原文，数据库适配器也不再把它们取出来
  （记录行拆成 `header` / `bodies` 两列，列表查询只投影 `header`）。
- 轨迹行与分析导航的预览文本只归一化足够产出预览的前缀，不再对整段请求消息跑一次
  `\s+` 归一化。

实测（60 条 81 KB 记录、同一份确定性场景，改前对照来自 `git stash` 后的同一脚本）：

| 读取 | 改前 | 改后 |
| --- | ---: | ---: |
| 列表读取 50 条 | 10.0 ms | 0.5 ms |
| 会话轨迹 60 条请求 | 35.6 ms | 15.1 ms |

守卫测试：`tests/model-request-read-amplification.test.ts`、`tests/model-request-read-cost.test.ts`。

## 已核实的现状（解决前）

一次自动刷新周期内,同一条模型请求记录的证据被投影 **7 次**,其中 3 次解析 SSE 原文。轮询间隔为 2 秒。

刷新时发出三个读取:列表查询、详情读取、轨迹读取。列表查询不运行任何投影——协议派生已在「共享模型证据投影唯一化」那条工作里从列表路径移除。

7 次的构成:

| 来源 | 次数 | 传入的证据切片 |
| --- | ---: | --- |
| 列表查询 | 0 | 不投影 |
| 详情读取 | 1 | 只有请求体 |
| 轨迹读取 | 4 | 3 次只有请求体,1 次请求体加响应原文 |
| 分析视图 | 1 | 请求体加响应原文 |
| 工作台响应用量 computed | 1 | 只有响应原文 |

真正的重复不在「缺少缓存」,而在**轨迹派生内部**。单次轨迹读取的 4 次投影里有 3 次输入完全相同:

1. 轨迹读取入口先调用一次详情读取,那里跑一次详情投影
2. 轨迹派生的记录循环里跑一次(唯一一次可能带响应原文的)
3. 派生请求行时又自己构造一次详情并投影
4. 计算请求组成图前再构造一次详情并投影

会话模式下,设聚合出 M 条记录,总次数为 `1 + 3M`。

共享模型证据投影的唯一对外入口注释仍明确写着不做全局缓存、不深拷贝原始子树。

## 仍未处理的部分

- 客户端两次投影（分析视图与响应用量 computed）输入不同，仍各跑一次，未收敛。
- 「进行中请求每 2 秒重新读取整份会话轨迹」本身没有变化，只是每次读取更便宜了。
- 轨迹账本没有虚拟化：会话请求很多时 DOM 行数仍随事件数线性增长。
