# 01 — 共享判据与三处收紧

**What to build:** 「一条消息在某个会话里对某个操作者能做什么」成为一个可以被问的判据，服务端按它拒绝，三处与真实环境不符的宽松因此闭合。

新增 `src/message-capabilities.ts`：纯函数，入参是消息、它所在的逻辑会话、操作者与群聊时的群组，出参是撤回、贴表情、回复、创建分支、合并转发多选五项能力位。继承前缀在会话实例视图里的只读约束是其中一部分，不另开一处判断。

服务端的写入路径改为先问它：撤回的群角色阶梯从 `assertCanManageMember` 与客户端两份收成一份，错误文案保持不变——它们是外部测试控制器已经在断言的用户可见事实。三处分歧按真实环境的样子收紧：事件消息不能贴表情、不能作为分叉点，已撤回消息不能被引用。三条都是把服务端收到客户端本来的严格程度，因此界面行为不变。

判据共享，强制仍在服务端：客户端的答案只用来渲染菜单，永远可以被绕过。

**Blocked by:** 无

**Status:** resolved

## Comments

### 实现记录

- 判据落在 `src/message-capabilities.ts`：一组接收沙盒实体的纯函数，形态照 `conversation-resolution.ts`。对外两个入口，`denyMessageCapability` 给出「做不到的依据」，`readMessageCapabilities` 给出五项布尔位并由前者实现——服务端需要依据才能抛出与收敛前一致的文案，客户端只需要位，两者因此同源而不是两份判定。
- **三处收紧的实测顺序按规格执行**：先写下「事件消息贴表情被拒」「事件消息分叉被拒」「已撤回消息引用被拒」三条断言把现状钉红（连 Console 端点那条共四条红），再让服务端问判据。三条之外全量 1123 条测试没有一条因收紧变红，说明沙盒里没有依赖这三种宽松的既有行为。
- **撤回的角色阶梯从 `assertCanManageMember` 摘出，但那个函数保留。** 它服务的是群成员管理（踢人、改名片、禁言），回答的是「一个成员能对另一个成员做什么」，与「一条消息能不能被撤回」不是同一个问题。收成一处指的是撤回那条阶梯只有一份实现。摘出时保留了两个容易丢的边角：操作者或消息作者已经退群时按 `参与者不在群组中：<id>` 拒绝（原先由 `requireGroupMember` 抛出），而 `不能对自己执行撤回成员消息` 那条在撤回路径上本来就到不了（进入阶梯的前提是作者不是操作者）。
- 文案还原集中在 `describeRecallDenial` 与 `describeReactionDenial` 两个模块级函数里，按依据 switch。`已撤回消息不支持修改表情回应` 沿用原措辞；新增的三句是 `事件消息不支持表情回应`、`事件消息不能作为分叉点：<id>`、`已撤回消息不能引用回复：<id>`，措辞照既有的 `事件消息不能合并转发：<id>` 一族。
- 合并转发那条虽然本来就一致，仍改成问同一份判据（`forward` 位），文案不变。不这么做的话五项里就有一项仍是独立实现，判据「只有一份」这句话会打折。
- 「继承前缀只读」在服务端由既有的会话边界校验先行拦下（撤回要求声明的会话等于消息归属，表情回应同理），因此判据里的 `inherited-prefix` 依据在服务端到不了；它是客户端那三个入口的依据。判据仍然拥有这条规则，客户端因此不必自己再判一次。
- 「继承前缀」的定义本身从 `client/webqq/fork-boundary.ts` 上移到 `src/conversation-resolution.ts`：服务端不能引用客户端目录，而把这条单行规则在两处各写一遍正是本规格要消除的东西。`fork-boundary.ts` 与 `.vue` 改为引用共享实现，分界标记的判定没有变化。

### 追加收紧：系统提示不能被引用

用户在验收后确认「系统提示不能被引用」，因此 `reply` 位对事件消息也关闭，事件消息在五项上一条都做不到。

- 依据与另外两处事件收紧同源：真实 QQ 里戳一戳这类事件是通知而不是消息，压根没有消息编号可供引用；沙盒给它一个 ID 只是为了让 WebQQ 在时间线上如实呈现它，那个 ID 不代表它变成了可操作的对象。
- 新增文案 `事件消息不能引用回复：<id>`，与既有的 `已撤回消息不能引用回复：<id>` 一起收进 `describeReplyDenial`，措辞照 `事件消息不能合并转发` 一族。
- 覆盖两条通道：Console/外部测试控制器经 `sendMessage` 进来被拒，机器人经 OneBot `send_msg` 带 `reply` 段进来同样被拒——后者走的是同一个 `getMessageContext`，因此不需要第二处判定。
- 界面行为仍然不变：事件消息在 WebQQ 里渲染成事件行，本来就不提供右键菜单。
- ADR-0078 末段原本记录的是「不收紧」这个取舍，已按本次决定重写，并在第二段标注引用回复不属于实测出的三处分歧而是按同一依据一并收紧。
