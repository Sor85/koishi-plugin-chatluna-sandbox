# 证据记录库拥有自己的未命中判定，控制服务停止转售

Status: ready-for-agent

## Problem Statement

控制服务是沙盒服务端唯一的对外门面，73 个公开成员里有 9 个只是替证据记录库说话。

其中 7 个的实现是一行 `return this.<记录库>.<方法>(...)`——interface 和 implementation 一样宽，这是 shallow 的定义。另外 2 个只多做一件事：把「记录不存在」写成一句中文抛出去。这句判定属于记录库，写在控制服务上意味着两种记录各抄一遍。

更锐的一处是控制服务把整个模型请求记录库交了出去。十个调用点里，跨记录域读一条记录详情的两处写成「取记录域 → 取控制服务 → 取记录库 → 读记录」，穿两层去拿；另有一处按记录来路在主模拟 QQ 环境、AI 测试空间、未归属之间三层嵌套地挑记录库。而 OneBot 调试记录库从不交出去——同一件事在两种记录上封装程度不同，靠的不是决定，是先后。

「记录不存在」这句文案今天有 5 处、2 个错误类。其中未归属那一处抛的是裸 `Error` 而不是领域错误，与领域错误类自己的注释相矛盾（那个类存在的唯一理由是让 MCP 侧把「领域说不」与「实现出错」分开）。

三个主要消费方各只学 73 个成员里的 22 到 43 个，三方交集只有 5 个。没有一个消费方需要全部。

## Solution

让证据记录库拥有「这条记录在不在」这件事，控制服务不再替它说话。

用户看不到任何变化。记录列表、详情、轨迹、清理、容量摘要，以及读不到记录时的那句提示，全部与今天一字不差。外部测试控制器拿到的错误码与消息也一样。

治理之后：想弄清「记录不存在是谁判的」只有一个答案；跨记录域读一条记录不必穿两层；控制服务的公开成员表少 9 个键；一条规则拦住下一个转售成员。

## User Stories

1. As a 沙盒用户, I want 读一条读不到的模型请求记录时仍然看到「模型请求记录不存在」加上那条记录标识, so that 我知道是这条记录没了而不是界面坏了
2. As a 沙盒用户, I want 全部空间视图下读不到记录时的提示与单个空间下一字相同, so that 我不必分辨自己当时在哪个视图
3. As a 沙盒用户, I want 读不到调试记录时的提示同样具体, so that 两种证据的体验一致
4. As a 沙盒用户, I want 模型请求轨迹在主模拟 QQ 环境、AI 测试空间与未归属三种来路下都读得出来, so that 换个来路不会让轨迹视图空掉
5. As a 沙盒用户, I want 记录列表的分页、筛选与「加载更多」一字不变, so that 一次服务端收拢不需要我重新验收
6. As a 沙盒用户, I want 容量摘要与清理结果一字不变, so that 我对记录还剩多少的判断不受影响
7. As a 沙盒用户, I want 界面没有任何变化, so that 这一轮不占用我的验收时间
8. As a 外部测试控制器使用者, I want 跨记录域读不到模型请求详情时仍然拿到结构化的「记录不存在」, so that 我的脚本不必改判定
9. As a 外部测试控制器使用者, I want 一次真实的持久化故障仍然照原样抛出而不是被当成未命中, so that 故障不会伪装成「这里没有」
10. As a 外部测试控制器使用者, I want 清理类工具仍然要求显式指定记录域, so that 一个测试凭证不会一次抹掉全部证据
11. As a 插件维护者, I want 「这条记录在不在」由记录库判定, so that 加第三种证据记录时这条判定不用再抄一遍
12. As a 插件维护者, I want 单个记录域的未命中与跨记录域的未命中是两个显式不同的位置, so that 读代码时分得清「这个域里没有」与「全域都没有」
13. As a 插件维护者, I want 控制服务的公开成员表里不再有替记录库转售的成员, so that 读它的 interface 时看到的都是它自己的职责
14. As a 插件维护者, I want 跨记录域读一条记录不必穿两层, so that 记录读取路径的层数与它的实际复杂度相称
15. As a 插件维护者, I want 「按记录域标识取记录库」只有一处实现, so that 三层嵌套三元不再随来路种类增长
16. As a 插件维护者, I want 两种证据记录得到对称处理, so that 封装程度不再取决于哪一种先写
17. As a 插件维护者, I want ChatLuna 的失败回填不写在控制服务里, so that 「失败记录归档」这件事和它依赖的错误解析住在一起
18. As a 插件维护者, I want 记录库不认识 ChatLuna, so that 换掉记录存储时不必连带理解上游错误格式
19. As a 插件维护者, I want 那段关于「错误回调是同步的、收尾等待靠更新跟踪覆盖」的注释跟着逻辑一起走, so that 一条会静默坏掉的规则不会在搬迁中丢掉
20. As a 插件维护者, I want 全仓零调用的成员被删掉而不是留着, so that 公开成员表反映真实需求
21. As a 插件维护者, I want 开发预览的错误种子直接写进记录库, so that 一条仅在开发模式下生效的便利不占用对外 interface
22. As a 插件维护者, I want 一条规则拦住「一行转售」这个形状重新长出来, so that 9 个转售成员不会再攒回来
23. As a 插件维护者, I want 规则对服务端源码全量生效而不是只盯控制服务, so that 别的 module 也不能替协作者说话
24. As a 插件维护者, I want 规则按字段的声明类型判定而不是按字段名列举, so that 新增一个协作 module 时规则自动覆盖它
25. As a 插件维护者, I want 尚未处理的两处转售按成员登记为有主豁免, so that 它们在账上而不是被规则无声放过
26. As a 插件维护者, I want 豁免按成员而不是按文件匹配, so that 同一个文件里长出第三个转售成员时仍然报错
27. As a 插件维护者, I want Console RPC 契约与 MCP 工具清单逐字不变, so that 「线上 surface 没变」有一份全量的证据
28. As a 插件维护者, I want 客户端一行不改并且可以用 diff 证明, so that 这一轮不需要开浏览器验收
29. As a 插件维护者, I want 记录页、详情、容量摘要与跨记录域查找的完整输出在收拢前后逐字节相同, so that 「行为没变」不是一句口头承诺
30. As a 插件维护者, I want 控制服务其余职责一律不动, so that 收拢是否纯结构性可以被证明
31. As a 插件维护者, I want 记录域目录的既有决定一条不推翻, so that 上一轮的判定不被顺手重判

## Implementation Decisions

### 记录库拥有单个记录域的未命中，调用方拥有跨记录域的未命中

- 两个记录库各自新增一个「取不到就抛」的读取成员，与既有的「取不到返回空值」并存，沿用仓库里既有的 `require*` 命名。抛出的是领域错误，消息与今天逐字相同。
- 控制服务上那两处写着同一句判定的成员随之消失；未归属那一处的裸 `Error` 也随行消失，不是就地改类。它今天只经 Console RPC 暴露，两个错误类在那条路上都只把消息送过去，因此对外可观察行为逐字相同。
- **跨记录域未命中留在调用方**，不并进记录库。没有任何单个记录库知道「全部记录域都没有」，而记录域目录已经用返回空值表达查找未命中——这是它刻意做的取舍：原先用 `try/catch` 遍历会把「这个域里没有」与「这个域的持久化坏了」混成一件事。把跨域那句判定塞进记录库会重新引入这种混同。
- 结果是**两个持有者**：记录库拥有单域未命中，Console 那一侧拥有跨域未命中。这不是遗漏。

### 两种证据记录对称处理

- OneBot 调试记录与模型请求记录都由消费方直接持有记录库，不是只治其中一种。
- 两种记录今天的封装程度不同（一个记录库从不交出去、另一个整个交出去），差异不来自任何决定。对称处理让「找不到就抛」这条规则只有一个位置，而不是一半在记录库里一半在控制服务上。

### 记录域带上记录库，控制服务只留装配入口

- 记录域的两支都带记录库：未归属那一支今天已经带了，场景那一支补上。跨记录域读一条记录从「取记录域 → 取控制服务 → 取记录库」变成「取记录域 → 取记录库」。
- 「按记录域标识取记录库」由记录域目录提供一处，轨迹读取那段按来路三层嵌套的三元表达式塌成一次查询。
- 控制服务上取得记录库的入口保留，但只服务于插件入口的装配。
- 不动那个可辨识联合。未归属仍然只有记录库、没有沙盒场景，跨记录域查找仍然只吃场景那一支，「未归属永不参与联邦读取、必须显式指定范围」一行不改。记录域目录的架构决定只补一句形状说明，既有决定一条不推翻。

### 不建门面

- 不新增一个聚合两种记录的门面 module。那会变成第三层（消费方 → 门面 → 记录库），而两种记录的读取形状本来就不同：第二排序键不同（模型请求用记录标识、调试记录用序号），续页游标只有模型请求有——这条差异已经由记录域目录明确交给调用方声明。门面只能把差异再摊开一次。

### 顺带的删除与搬迁

- 一个全仓零调用的记录更新成员直接删掉。本仓库处于未发布阶段，不保留兼容层。
- 追加记录那个成员的唯一 src 消费方是仅在开发模式下生效的错误预览种子，改成直接调记录库，控制服务上这个键跟着消失。
- ChatLuna 失败回填（找到该会话最近一条失败记录、单行更新、把任务登记进更新跟踪）从控制服务的私有方法挪进已经拥有 ChatLuna 错误解析与「最近一条失败记录」查找的那个 module，签名接收记录库。**不进记录库**——记录库不该认识 ChatLuna。它是私有方法，搬迁不改任何 interface。
- 那段解释「ChatLuna 的错误回调是同步的，记录查找与单行更新只能在后台完成；收尾等待通过更新跟踪覆盖它，避免关机时丢掉这次归档」的注释原样跟着走。它记的是一条改坏了不报错的规则。

### 守卫：宽规则按字段声明类型判定，豁免按成员登记

- 服务端架构守卫新增一条规则：公开成员体只有一句 `this.<字段>.<方法>(...)` 即报，且该字段的声明类型是另一个 module 的类。判定读同文件里的私有字段声明，用 `Map`／`Set`／数组字面量初始化的字段不算——读自己的集合不是转售。
- 规则跑遍服务端全部源码，与既有两条同形。不按文件名列白名单：白名单只约束名单内的文件，会随文件数增长自动失效。
- 落地后命中两处（ChatLuna 状态库的两个一行委托），按**成员**登记为有主豁免，负责人指向「ChatLuna 状态库的归属」这条后续候选。
- 既有的豁免匹配以「文件 ＋ 规则」成对判定，一条豁免会放行该文件下该规则的全部违规。本规则要的是成员级粒度，因此匹配需要认到证据里的成员名，否则同一个文件里长出第三个转售成员会被静默放过。既有的「豁免按文件与规则成对匹配」那条元守卫断言随之调整，「移除任一豁免后对应文件重新报错」那条必须仍然成立。
- 规则要有正反两侧的自测：认得出一行转售（含 `async`、含带返回值与不带返回值两种），也不误报读自己集合、不误报 `return this.<字段>`（没有调用）、不误报只有一句但调用的是自由函数的成员、不误报记录库自身。

### 控制服务其余职责一律不动

- 场景写入与保留窗口、头像与媒体、群权限、关系申请、OneBot 事件投递都留在原处。按这六组职责在 implementation 里划内部 module 是另一条候选，它的爆炸半径与本轮差一个量级，混进来会让「interface 收窄是否纯结构性」无从证明。
- 测试专用的那几个成员（运行时机器人、媒体目录、以及 `send*` 与 `start*Send` 的并存）本轮不动。它们属于「发送时序」那组职责，是上面那条候选的范围。

## Testing Decisions

好的测试断言外部可观察的行为，而不是实现写法。本仓库的判据已经写下来了：肯定式实现细节断言在等价重构时变红、在真实回归时沉默。本规格不新增任何一条这样的断言。

**净新增 seam 数：零。** 本轮全部新增行为都落在既有 seam 上——两个记录库、记录域目录、ChatLuna 错误 module、Console RPC、MCP 服务、服务端架构守卫，每一个都已有自己的测试文件。这是前四轮里条件最好的一次：没有新 module，只有既有 module 的 interface 各多一个成员。

### 主测试面

- **Console RPC 的 interface（既有 seam，最高的那个）**。用户经它读记录，本轮全部对外可观察行为都在这里：详情读取、跨记录域读取、轨迹的三种来路、清理、容量摘要。这一族已经有回归网，一字不改地继续通过。
- **MCP 服务的 interface（既有 seam）**。它是唯一一处领域错误与普通错误的区别对外可观察的地方——领域拒绝保留消息、未预期异常降级并写日志。跨记录域详情读取的结构化未命中在这里断言。
- **两个记录库自身的 interface（既有 seam）**。「取不到就抛」的新成员在这里补断言。
- **记录域目录的 interface（既有 seam）**。场景那一支带上记录库、按标识取记录库这两件事在这里断言。
- **服务端架构守卫（既有 seam）**。新规则与它的正反自测、豁免的成员级匹配、元守卫都在这里。

### 要补的断言

- 取不到就抛：两种记录各断言一次，消息含记录标识，错误类是领域错误。
- 取不到返回空值与取不到就抛并存：同一条不存在的记录，一个返回空值、一个抛出，两者不互相替代。
- 跨记录域未命中与单记录域未命中是两个不同位置：跨域读不到时的消息与单域一致，但**持久化故障照原样抛出而不是被当成未命中**——这条是记录域目录刻意做的取舍，本轮改动经过它，必须有断言压住。
- 场景记录域带记录库：从记录域直接读一条记录，不经控制服务。
- 按记录域标识取记录库：主模拟 QQ 环境、AI 测试空间、未归属三种来路各断言一次。
- ChatLuna 失败回填搬迁后行为不变：给定一个上游错误与一个会话，该会话最近一条失败记录被更新，且这次更新被收尾等待覆盖。
- 守卫规则认得出一行转售（含 `async` 与两种返回形态），也不误报读自己集合、不误报没有调用的字段返回、不误报调用自由函数的单语句成员、不误报记录库自身。
- 豁免按成员匹配：同一文件同一规则下，另一个未登记的成员仍然报出。
- 既有的「移除任一豁免后对应文件重新报错」仍然成立。

### 纯结构性的证明

- **Console RPC 契约逐字不变。** 全部 RPC 声明从一份契约派生，因此契约文件不变就等于对外 surface 不变。这比逐个端点比对强，因为它是全量的。
- **MCP 工具清单与 schema 逐字不变。**
- **stash 基线比对。** 一份确定性脚本跑记录列表页、记录详情、容量摘要与跨记录域查找的完整输出，逐字节相同。沿用前几轮的手法：事实在服务端 module 的 interface 上，直接驱动导出比对，不必开浏览器。
- **`git diff --stat` 里没有客户端路径**，作为一条验收项。本轮客户端一行不改，这条比 DOM 快照强——它是全量的，而 DOM 快照只覆盖采样点。
- 每张票各跑一次完整测试、类型检查与构建。基线作为票的证据留在本 feature 目录下。

### 别处变红的处置

改控制服务的公开成员会让读它源码或按成员名断言的测试变红。逐条区分真红与假红——标识符变化跟着改是假红，行为口径或成本结构变化是真红，停下来查——并在票的 Comments 里逐条记处置。**不重判前几轮已经判定保留的断言。**

## Out of Scope

- **按六组职责在 implementation 里划内部 module。** 这是报告里的第二步，要动三千多行里的一百多个私有方法，并触及记录 OneBot 有状态动作与统一动作记录形状的两条架构决定。它单独成候选，且与「消息投递收成内部 module」那条重叠，应一起重排。
- **测试专用成员与 `send*` / `start*Send` 的并存。** 属于「发送时序」那组职责，是上面那条候选的范围。本轮收它会把成员数从 11 变成 16、并改动近五十处测试。
- **ChatLuna 状态库的归属。** 那两个一行委托本轮按成员登记为有主豁免，不迁移。
- **把跨记录域未命中并进记录库。** 会重新把「这个域里没有」与「这个域坏了」混成一件事。
- **让未归属参与联邦读取。** 记录域目录的既有决定，本轮无权重判。
- **拆分控制服务的可辨识联合，或给它加可选字段。** 上一轮明确判过：可选字段只是把判空搬进类型里。
- **界面、文案、样式与交互的任何调整。** 本轮没有行为变化，一处例外都没有。
- **引入组件挂载测试。** 已记录在案的决定。

## Further Notes

- 最值得做的不是少 9 个键，而是「这条记录在不在」这件事第一次只有一个持有者。今天它有 5 处文案、2 个错误类，其中一处的错误类还和领域错误类自己的注释相矛盾——那个矛盾不是有人写错，是这句判定没有主人的必然结果。
- 顺带被钉住的是「单域未命中」与「跨域未命中」的区别。这两件事上一轮已经在记录域目录里分开过一次（用返回空值而不是异常表达查找未命中，让持久化故障照原样抛出），本轮的改动正好经过那条路，因此要用断言压住而不是靠记得。
- 与前四轮最大的差别是不需要浏览器。前四轮验证的是渲染结果、光标位置与转圈时机，都要开浏览器或至少驱动客户端模型；这一轮全在服务端，而对外 surface 由一份 RPC 契约派生，契约不变加上 `git diff` 无客户端路径就是全量证据。
- 新增两条 ADR 内容：一条记「证据记录库拥有自己的未命中判定，控制服务不转售」，写清三件事——记录库是单域未命中的持有者而跨域未命中属于调用方、控制服务上只保留装配用的取得入口、宽规则守卫与两条按成员登记的有主豁免；另外给记录域目录那条补一句形状说明（两支都带记录库，跨记录域读记录不再经控制服务），不改它的任何既有决定。
- 领域词汇不需要新词：「证据记录」「记录域」「联邦读取」都已在册，实施时核一遍即可。
- 与「服务端持有沙盒状态」那条决定不冲突：状态仍然只有一个权威持有者，动的是 interface 的宽度。
