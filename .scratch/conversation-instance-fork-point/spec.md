# 会话实例分叉点规格

Status: ready-for-agent

## Problem Statement

创建一个会话分支时，沙盒会把分叉点及其之前的消息整段复制一份存进新实例。

沙盒对每份场景的消息有条数与序列化字节双上限，达到任一上限就从最旧的消息开始真正丢弃、不做归档。复制意味着同一段历史占用两份额度：开两个分支就占三份，原始对话的早期消息因此被提前挤掉。分支的用途恰恰是「留住原始记录作为对照」，它却在消耗原始记录的存活空间——用户越是认真地多开几条对话线复盘，越快把想保住的东西挤没。

复制还让同一条逻辑消息在场景里有了两个身份。复制体带着表情回应、ChatLuna 思考内容与 Token 用量的副本，于是同一句话在两处各有一套附属事实；用户在分支里给复制体贴的表情不会出现在原会话，反过来也一样，而它们看起来是同一条消息。

第三个后果是创建耗时随历史长度增长：分叉点越靠后，复制的消息越多，而用户的动作只是「从这里换一种问法」。

## Solution

分支只记录「我从哪条消息分出来」。历史仍然只存一份，读取时把来源会话在分叉点之前的消息与分支自有的消息拼接起来呈现。

用户能感觉到的三件事：创建分支瞬间完成，与历史长短无关；开多少条对话线都不会挤掉原始对话的早期消息；分支里分界线以上那段是与原会话共享的同一份记录，因此在分支里只读——不能撤回、不能贴表情、不会被清空，但可以引用它继续追问，这是分支最自然的用法。

只读约束的是用户在分支视图里的操作入口，不是消息本身的生命周期。原始记录后来真的变了（例如被测插件通过 OneBot 撤回了其中一条），分支里如实反映，因为它就是同一条消息。反过来，清空根会话或保留窗口淘汰会让分支分界线以上变空——和「更早的消息已不在保留窗口内」是同一种体验。

分支还可以从分支里再分出来：新分支记录的是「来源会话加分叉点」，读取时沿来源链逐段拼接，因此它能看到上一条分支里那几轮对话，而不是跳回根会话的历史。

## User Stories

1. As a 沙盒用户, I want 创建分支瞬间完成, so that 分叉点靠后、历史很长时我也不用等
2. As a 沙盒用户, I want 开多条对话线不再挤掉原始对话的早期消息, so that 我越认真复盘越不会把想保住的记录弄丢
3. As a 沙盒用户, I want 分支里能看到分叉点之前的完整上下文, so that 插件在新分支里的回答建立在同一段历史上
4. As a 沙盒用户, I want 分支里在继承的历史与本分支消息之间看到一条分界, so that 我知道哪一段是与原会话共享的
5. As a 沙盒用户, I want 继承的那段历史在视觉上稍作弱化, so that 我一眼分得清对照区与实验区
6. As a 沙盒用户, I want 在分支里引用继承的消息继续追问, so that 我可以直接在分叉点那句话上换一种问法
7. As a 沙盒用户, I want 在分支里不能撤回继承的消息, so that 我不会在对照组里误改原始记录
8. As a 沙盒用户, I want 在分支里不能给继承的消息贴表情, so that 原会话的表情回应不会被我的实验动作改写
9. As a 沙盒用户, I want 清空分支只清掉本分支的消息, so that 我可以重来一次而不动原始对话
10. As a 沙盒用户, I want 继承消息上的右键菜单不显示做不到的动作, so that 我不必靠试错才知道哪些操作被禁
11. As a 沙盒用户, I want 原会话后来撤回某条消息时分支里如实显示已撤回, so that 两边呈现的是同一个事实而不是两份快照
12. As a 沙盒用户, I want 在分支里往上翻能连续读到继承的历史, so that 加载更早消息时不会在分界处断掉
13. As a 沙盒用户, I want 刚建好的分支在侧栏显示分叉点那条消息作为预览, so that 它看起来不像一个空会话
14. As a 沙盒用户, I want 从一个分支里再创建分支时新分支能看到这个分支已有的几轮对话, so that 我可以在实验的基础上继续分叉
15. As a 沙盒用户, I want 清空根会话或保留窗口淘汰后分支分界线以上变空但分支仍在, so that 我不会因为整理原始对话而丢掉整条实验线
16. As a 沙盒用户, I want 搜索命中继承的消息时报它属于原会话, so that 搜索结果不会因为分支数量而重复膨胀
17. As a 沙盒用户, I want 已有的旧分支在改动后仍然能正常打开, so that 我不需要重置场景或迁移数据
18. As a 插件维护者, I want 被测插件在分支里能读到继承的消息, so that 它按消息 ID 取历史时不会莫名失败
19. As a 插件维护者, I want 被测插件通过原始 OneBot 撤回一条继承的消息时操作生效, so that 沙盒不对插件表现出真实环境不存在的错误
20. As a 插件维护者, I want 插件读到继承消息时拿到的私聊或群聊信息与所在会话一致, so that 群分支里的消息不会被解释成私聊
21. As a 插件维护者, I want 分支的消息分页与根会话使用同一套游标语义, so that 插件读历史的代码不需要区分会话种类
22. As a 插件维护者, I want 读取某个会话的消息列表只有一个入口, so that 拼接规则不会散到十几个调用点各自实现一遍
23. As a 插件维护者, I want 保留窗口的引用摘除不需要为拼接特殊处理, so that 淘汰逻辑保持单一策略
24. As a 插件维护者, I want 一条断言钉住「同一段历史开多个分支后消息实体总数不增长」, so that 单份消息存储不会在以后被悄悄破坏
25. As a 插件维护者, I want 分叉点作为领域术语写进领域词汇, so that 后续工作不会把它叫成起点、锚点或基线
26. As a 插件维护者, I want 一条 ADR 说明分支改为只记分叉点, so that 之前接受复制这个取舍的理由与现状同时留在记录里
27. As a 插件维护者, I want 同一条逻辑消息在场景里只有一个身份, so that 它的表情回应、思考内容与用量证据不再有两份

## Implementation Decisions

### 存储模型

- 会话实例记录「来源会话 ID」与「分叉点消息 ID」两项，不再复制消息。继承前缀是来源会话当前消息列表中分叉点及其之前的那一段。
- 只存分叉点，不额外存一份前缀消息 ID 快照。消息只追加不插入，因此「来源会话当前列表到分叉点为止」与「分叉时刻的前缀」在正常路径上等价；两者只在来源会话被清空或保留窗口淘汰时不同，而那两种情况下消息正文本身已经不存在，多存一份 ID 列表也救不回来。少一份状态就少一处可能与真相不一致的地方。
- 来源会话可以是根会话，也可以是另一个会话实例。从实例再分叉时，新实例的来源指向那个实例，解析时沿来源链逐段拼接。存储层级仍严格两层——所有实例都挂在同一个根会话下——链只在读取时展开。
- 没有分叉点的实例（当前场景里已有的复制型分支）退化为「只有自有消息」，行为正确且可用。不写迁移、不要求重置场景，符合未发布阶段兼容策略。
- 一次性替换，不做 expand–contract：拼接与复制是互斥语义，并存期间会出现「一个实例既有继承前缀又有自己的副本」这种无法推理的中间态。

### 读取

- 「读某个会话的消息列表」收成会话解析模块里的一个函数。解析结果不再对外暴露对场景数组的实时引用——那个引用是为热路径省一次复制而留的，拼接之后它无法表达合成列表。所有需要会话消息的路径改为经这个函数，拼接规则因此只有一处实现。
- 消息历史分页对拼接后的完整列表操作，游标仍是消息 ID，跨越继承前缀与自有消息的边界对调用方透明。不新增方向参数，不为前缀单设「加载继承历史」入口。
- 快照投影的「还有更早消息」判定按拼接后的列表长度计算。
- 消息搜索按消息实体自身的会话归属报告结果：命中继承前缀时报根会话。「消息只有一个会话身份」是上一轮改动刚立起来的不变量，按分支重复报告会让结果数随分支数膨胀。
- 场景消息保留窗口的引用摘除不需要改动。它已经不假设一条消息只被一个会话的消息列表引用；拼接之后前缀消息只被来源会话引用，实例的消息列表只含自有消息。

### 继承前缀的可变性

- 用户在分支视图里对继承前缀只读：不能撤回、不能贴表情、不会被清空；可以被引用。
- 撤回天然满足：它在传入会话 ID 时要求该 ID 等于消息实体的会话归属，在分支里撤回前缀会自动失败。
- 表情回应需要补一条判定：它目前只校验消息所属会话对操作者可见，不校验请求的会话是否就是消息的归属。
- 清空天然满足：它按消息实体的会话归属删除，清空分支只删自有消息。清空根会话会删掉前缀实体，其全部分支的继承历史随之变空——接受，与保留窗口淘汰属于同一类事实，不做引用计数保留，也不因为存在分支而禁止清空。
- 回复目标读取的校验从「被引用消息的会话等于当前会话」放宽为「被引用消息在当前会话里可读」，即自有消息或其继承前缀。
- 客户端消息右键在继承前缀上不显示撤回与贴表情。
- 被测插件通过原始 OneBot 撤回或贴表情作用到一条继承前缀消息时允许执行，改动如实反映进分支。只读约束的是用户在分支视图里的入口，不是消息实体的生命周期；插件寻址的是根会话的一条普通消息，拒绝会让沙盒表现出真实环境不存在的错误。
- OneBot 单条消息读取的可选会话校验同样放宽为「在请求的那个会话里可读」。输出的私聊或群聊类型与群号仍由消息实体的会话解释——实例的类型与群号继承根会话，两者结果相同，不产生可观察差异。

### 界面

- 分支里在继承前缀与自有消息之间显示一条分界标记，前缀区域视觉上弱化。分界同时解释了「上面这段是与原会话共享的同一份记录」，因此右键项变少不再像缺陷。
- 继承前缀不折叠、不默认收起：看全上下文正是复盘时要做的事。
- 侧栏实例子项的预览取拼接后的最后一条消息，刚创建的分支因此显示分叉点那条，而不是空白。

### 文档

- 领域词汇新增「分叉点」条目：会话实例记录的来源消息，它界定继承前缀的范围。
- 新增一条 ADR 说明分支改为只记分叉点，并在 ADR-0076 中标注「代价是分支要复制分叉点之前的消息」那一段被取代，不改写 ADR-0076 原文。

## Testing Decisions

好的测试从 interface 观察外部行为，不断言实现写法。按 ADR-0073，源码文本断言只在架构守卫、样式与用户可见文案三类例外中使用；数量断言不能替代逐个执行的覆盖——本规格里唯一的数量断言是「消息实体总数不随分支数增长」，它断言的是单份消息存储这条不变量本身，而不是用总数冒充行为验证。

**本规格不新增任何 seam。** 拼接是会话解析模块内部的实现变更，读取入口收成该模块的一个函数，仍在它既有的 interface 之后；其余变更都落在既有的控制服务、OneBot 表面与客户端投影三个 seam 上。

### 测试面

1. **会话解析模块的 interface（既有 seam，主要测试面）**——先例是现有的会话解析测试。覆盖：按分叉点拼接前缀与自有消息、来源是实例时沿链拼接、分叉点消息本身包含在前缀内、没有分叉点的实例只有自有消息、来源会话消息被淘汰后前缀相应缩短、拼接后的列表顺序与来源一致。
2. **控制服务的公开方法（既有 seam）**——先例是现有的控制服务测试、会话实例测试与场景消息保留测试。覆盖：创建分支不新增消息实体、同一段历史开多个分支后场景消息实体总数不随分支数增长、消息历史分页跨越分界连续返回、清空分支只删自有消息、清空根会话后分支仍存在且前缀变空、在分支里对继承前缀贴表情被拒、在分支里撤回继承前缀被拒、在分支里引用继承前缀成功、搜索命中前缀时报根会话。
3. **虚拟 OneBot 机器人的两个表面（既有 seam）**——先例是现有的消息投递测试与 OneBot 桥接测试。覆盖：插件在分支里按消息 ID 读到继承前缀、插件通过原始 OneBot 撤回继承前缀生效且分支里显示为已撤回、群分支里继承前缀的私聊或群聊信息仍是群聊、插件读历史时游标语义与根会话一致。
4. **客户端投影（既有 seam）**——先例是现有的会话树测试与消息列表相关测试。覆盖：刚创建的分支侧栏预览是分叉点那条消息、继承前缀上的右键不含撤回与贴表情、分界标记出现在正确位置。
5. **浏览器实测（一次，不是自动化 seam）**——确认分界标记在两种浏览器下的呈现一致，以及向上加载更早消息能连续跨过分界。按项目约定关闭本次验证打开的会话并清理浏览器工具产生的临时目录。

## Out of Scope

- **前后端 RPC 契约收敛成一份**。名单目前仍有三份声明，把它派生成一份并加端点集合守卫是另一个 spec 的内容。
- **侧栏树投影与展开态下沉成独立模块**。它们仍留在工作台外壳与侧栏组件里，与本规格同批规划但属于另一个 spec。
- **继承前缀可写**。不提供「在分支里改动前缀并让原会话不受影响」这种写时复制语义；需要改动原始记录时用户回到根会话操作。
- **分支之间的并排对比视图**。
- **三层及更深的存储层级**。来源链只在读取时展开，存储仍是根会话加实例两层。
- **旧复制型分支的迁移**。已有实例保持现状，不折叠成分叉点形式。
- **为分支单独设置保留配额**。实例与根会话继续共享同一份场景消息预算。

## Further Notes

- 本规格的收益是「单份消息存储」这条不变量回到 ADR-0042 的原意。上一轮为了先把会话实例打通，明确接受了复制这个代价并写进了 ADR-0076；本规格是那条记录里点名的后续工作。
- 「前缀只读」与「插件可以改动前缀」这两条容易读成矛盾。区分点是：只读是**分支视图里的操作入口**约束，防的是用户在对照组里误改原始记录；消息实体的生命周期不冻结，原始记录真的变了就该在分支里如实呈现，因为它本来就是同一条消息。
- 解析结果不再暴露实时引用的消息数组是一处需要注意的连带改动：现有热路径（消息历史与搜索）直接对那个数组取长度、找下标、切片，改成经函数读取时要确认没有调用方依赖数组对象的身份不变。
- 已核实客户端消息列表是按「当前会话的消息 ID 集合」筛选快照消息，而不是按消息实体的会话归属，因此拼接对它透明；服务端的回复目标校验是唯一明确的冲突点，已在实现决定里放宽。
