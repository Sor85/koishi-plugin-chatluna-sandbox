# 03 — 继承前缀在分支里只读

**What to build:** 分支是原始记录的对照组，因此在分支里不能改动继承来的那段历史，但可以引用它继续追问。

用户在分支里对继承前缀：不能撤回、不能贴表情、清空分支时它不受影响；可以引用它回复。客户端消息右键在继承前缀上不显示撤回与贴表情，用户不必靠试错才知道哪些操作被禁。

撤回与清空已经天然满足——两者都按消息实体的会话归属判定。表情回应要补一条判定，它目前只校验消息所属会话对操作者可见，不校验请求的会话是否就是消息的归属。回复目标读取的校验要从「被引用消息的会话等于当前会话」放宽为「被引用消息在当前会话里可读」，也就是自有消息或其继承前缀——「在分叉点那句话上换一种问法」是分支最自然的用法，禁掉它会让分界线以上完全惰性。

只读约束的是用户在分支视图里的操作入口，不是消息实体的生命周期。原始记录后来真的变了，分支里如实反映。

## Comments

### 实现记录

- 撤回与清空按规格预期天然满足，两条断言一次就绿：撤回在传入会话 ID 时要求它等于消息实体的归属，清空按消息实体的归属删除。
- `SetMessageReactionInput` 新增可选 `conversationId`。**声明时**要求它等于消息自身的归属会话，**省略时**按消息归属执行——后者是插件通道：`set_msg_emoji_like` 的处理器不带会话调用 `applyMessageReaction`，因此插件贴到继承前缀上仍然生效，沙盒不表现出真实环境不存在的错误。
- 判定只有一处，在 `setMessageReaction` **分流之前**：机器人操作者要绕一圈自身 OneBot action，而 action 表面没有「会话」这一级，判定放到写入路径就会因操作者种类而失效。`applyMessageReaction` 的参数收窄成 `Omit<SetMessageReactionInput, 'conversationId'>`，用类型说明「会话归属是请求层的边界，这条写入路径只认消息实体」，而不是接了字段却悄悄忽略。
- 被拒时的错误文案沿用撤回的 `消息不存在：<id>`：会话是操作边界，同一种拒绝在两个入口上说同一句话。
- `getMessageContext` 的回复目标校验从「归属等于当前会话」放宽为「在当前会话里可读」，即 `readConversationMessageIds` 的结果包含它。从分支里再分叉时前缀跨两段，链上任一段里的消息都算可读。反向仍然被拒：分叉点之后的原会话消息、以及分支自有的消息在根会话里都读不到。
- 客户端 `workspace-shell.setMessageReaction` 补上当前会话 ID；没有当前会话时直接返回，与 `recallMessage`、`clearConversationMessages` 同形。
- `webqq-message-list.vue` 新增 `isInheritedMessage`（消息归属会话 ≠ 当前会话），接进 `canRecallMessage`、`canReactToMessage` 与 `isReactionReadonly`。**第三处不能漏**：气泡下方已有回应条是另一个写入入口，只挡右键菜单会让用户点一下已有 emoji 就绕过只读。

### 审查后的修正

三处都由 `/code-review` 的两轴审查发现，已修：

- **写入路径那处判定是死分支。** 原本入口与 `applyMessageReaction` 各判一次，规格轴用变异实验证明删掉任一处全量 1097 条测试都全绿——两处各自都不被任何测试区分。改为单处判定 + 收窄参数类型后重跑变异实验：删掉唯一判定点，用户与机器人两条路径的用例同时变红。
- **客户端夹具的形状是投影绝不会产出的。** 原夹具同时给 `forkPoint` 与只含自有消息的 `messageIds`，而 `truncate` 明确物化拼接结果并删掉分叉点。那样测的是客户端二次展开来源链那条死路，投影一旦停止物化测试仍会绿。夹具改成投影的真实形状（`messageIds` 已物化、无 `forkPoint`）。
- **验收 5 的断言含一条数量断言与按函数声明顺序切片。** 前者正是 ADR-0073 点名的「用廉价指标冒充覆盖」，后者会因改名、内联或调序变红而抓不住口径漂移。改成三条与声明顺序无关的精确字符串断言，每条只在对应那个入口被删掉时变红。

### 留给后续票的观察

- 验收 5 唯一的守卫仍是源码文本断言。规格把它放在「客户端投影」这个既有 seam 上并以 `webqq-message-list.test.ts` 为先例，而右键权限判定目前住在 `.vue` 里，从外壳观察不到。要让它变成行为断言，得把 `canRecallMessage` / `canReactToMessage` 下沉成 `messageList` 投影里的每条消息能力位——那会连带改动本票没要求碰的群角色判定，因此留给后续 spec，不在 03 里扩面。
- 「继承前缀」「分叉点」已大量出现在代码与测试名里，但 `CONTEXT.md` 尚无条目，由 06 号票闭环。
