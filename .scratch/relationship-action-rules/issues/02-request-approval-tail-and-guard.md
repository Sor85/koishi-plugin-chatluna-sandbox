# 02 — 申请处理共用尾巴，一条规则钉住角色判定的归属

**What to build:** 好友申请与入群申请的审批，两条通道共用同一段「摘掉申请、批准则加成员或加好友、否则提交场景变更」；两条路上的拒绝文案、权限判定与通知一字不变。一条规则拦住下一次在通道入口里重新写一遍权限判定。

**只共用尾巴。** 前置判定各留在自己通道——谁有权处理、能不能代机器人处理、按什么条件查找申请。这正是两条通道**应该**不同的地方，把它们参数化会让通道差异从两段可读的代码变成一组开关。

三处已经漂移的东西原样保留：入群申请被拒时两条通道各自的文案（用户「只有群主或管理员可以处理入群申请」、机器人「机器人没有审批入群申请的权限」，前者已有断言）由拒绝原因渲染；**批准好友申请时设置备注只有机器人通道支持**，留在机器人 adapter；用户通道对群邀请那条「机器人邀请必须由机器人处理」的守卫留在用户 adapter——它表达的是操作通道这条领域约束。

第四处经核查**不是漂移**：机器人通道按 OneBot 的子类型语义查找申请（调用方必须传子类型，传错就当找不到），用户通道没有这个参数。两个通道的输入不同，不是同一规则的两种写法，本票不动它。

守卫随本票上线：群成员角色的比较只允许出现在关系规则 module 里。谓词判定操作者、行为者、目标这三个标识符名上的角色字段与字面量比较——场景校验里判断群里有没有群主、机器人适配器把角色渲染成中文名，这两处用的是另一个标识符名，天然不命中。共用消息能力规则那两处会命中，按**文件**登记为有主豁免，负责人指向 ADR-0078。

## Comments

**本票与票 01 一个提交落地，原因见票 01 的 Comments。** 本票的实际内容是：两条申请尾巴、入群申请审批那道共用的角色判定、守卫规则、ADR，以及领域词汇核对。

**尾巴只有三句，前置判定一句没有参数化。** `settleFriendRequest` 是「摘掉申请、批准则建立好友关系、提交场景变更」；`settleGroupRequest` 是「摘掉申请、批准则加入新成员并派发入群通知、否则只提交场景变更」。四处前置判定原样留在各自通道里：用户通道那两条「机器人申请／邀请必须由机器人处理」、「只能处理发给自己的好友申请／群邀请」，机器人通道那条「只能处理发给自己的群邀请」与按 OneBot 子类型语义查找申请。尾巴的入参里没有任何一个开关字段——`participantId` 与 `operatorId` 是两条通道各自算出来的值而不是分支旗标（后者的必要性见票 01 Comments 里那第五处通道差异）。

**备注做成回调而不是入参。** 尾巴收一个 `onApproved(friendship)`，机器人 adapter 用它写备注。两种替代写法都不行：给尾巴加 `remark` 参数等于把只有机器人通道支持的东西挪进了规则；让尾巴返回好友关系、由 adapter 在尾巴之后写备注会让场景变更监听器先收到一份没有备注的快照，Console 因此会闪一次无备注状态。回调写在批准分支里、提交之前，备注仍然进同一次提交。

**踩到一个可选调用的坑。** 第一版写成 `onApproved?.(addFriendship(...))`，可选调用在被调者为空时**跳过实参求值**，于是用户通道批准好友申请时根本没建立关系。既有的好友关系测试立刻变红抓住了它；规则里现在先建立再交给回调，并注明原因。

**入群申请审批的角色判定收成一个谓词，两条通道各自渲染。** `denyGroupAuthority(actor)` 就是「群主或管理员才行」这一条，本轮有三个使用点：改群名、成员管理阶梯的第一步、入群申请审批。文案在两个入口上直接成形——用户通道 `只有群主或管理员可以处理入群申请`、机器人通道 `机器人没有审批入群申请的权限`——没有为这两句各写一个 `switch`，因为那个位置的拒绝原因只有一种取值，一个单分支的渲染函数什么也没多说。

**`群申请缺少目标参与者` 挪进了邀请分支。** 收拢前它在批准分支里（`approve` 为真才判），而邀请那条守卫已经保证 `request.targetId === operatorId` 是个非空字符串，入群申请那条取的是必填的 `requesterId`——两种放法都到不了这一句。挪进邀请分支是为了让类型收窄发生在使用点旁边，行为等价，基线逐字节相同。

**守卫谓词按标识符名收窄，一处豁免。** 规则「群成员角色比较只允许出现在关系规则模块里」认三种写法：`actor|target|operator` 的角色字段与字面量相等、不等，以及字面量写在左边。四处合法命中天然避开——场景校验判断群里有没有群主用解构出的裸 `role`、删除用户与机器人时的群主检查同样是裸 `role`、按角色挑收件机器人也是裸 `role`、机器人适配器把角色渲染成中文名用 `member.role`。唯一命中的是 `src/message-capabilities.ts` 里那道撤回阶梯，按**文件**登记为有主豁免，负责人指向 ADR-0078（那条 ADR 已经判定两道阶梯各自成立、不合并；搬它会让服务端与客户端共用的纯函数模块反过来依赖关系规则）。

**规则的红灯经变异验证。** 在控制服务里临时加一个 `private mutationProbe(actor: SandboxGroupMember) { return actor.role === 'member' }`，守卫立刻报出 `src/control-service.ts 违反「群成员角色比较只允许出现在关系规则模块里」：群成员角色与字符串字面量相等或不等比较`，且「移除任一豁免后对应文件重新报错」那条元守卫同时变红（它要求移除豁免后暴露的只能是那一个文件）。移除探针后 12 条断言全绿，元守卫仍然成立，豁免清单只增这一条。

**未新增肯定式实现细节断言。** 拒绝原因联合没有形状断言，八个动作也没有新的「谁能踢人」断言——两条通道各自的既有测试（群权限 11 例、好友关系 10 例、OneBot 桥接 21 例、实现配置那一份）一字不改地通过，它们是「每条通道都真的经过了那份规则」的两侧证据。新增的断言只有守卫规则那一条正反自测。

**领域词汇核过一遍，无需新词。** `CONTEXT.md` 里「操作通道」的定义（"当前操作者执行交互时采用的领域路径；普通用户通过用户交互直接作用于模拟 QQ 环境，虚拟 OneBot 机器人通过受启用状态、实现配置和能力覆盖约束的 OneBot action 执行"）与本轮的形状完全一致，正是这个 module 的名字来源；「机器人动作」「机器人事件投递」也都在册。`relationship-actions` 是模块名而不是新术语。`_Avoid_` 清单里没有本轮用到的词。

**ADR。** `docs/adr/0087-own-relationship-action-rules-in-one-module.md`：规则的唯一持有者与两条通道退成 adapter、拒绝以可辨识原因表达并由通道渲染文案（沿用 ADR-0078 的形状）、申请审批只共用尾巴及其理由、备注为什么是回调、守卫谓词与那一处按文件登记的豁免、为什么必须是 module 而不是私有方法（文件级持有者判定会把整个文件放行）。写明不推翻：领域词汇里的「操作通道」、ADR-0002 的服务端状态所有权、ADR-0076 的写入偏离（机器人只能经自身 OneBot action）、ADR-0078 的共用消息能力规则，以及 ADR-0008／0039 的关系审批与当前操作者约束。第五处经核查不是漂移那件事也写进去了。
