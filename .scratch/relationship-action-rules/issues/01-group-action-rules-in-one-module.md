# 01 — 群操作的规则收成一个 module，两条通道各自调它

**What to build:** 从 WebQQ 踢人、设管理员、改群名、改群名片、退群，和被测插件经自身 OneBot action 做同样五件事，从此走的是同一份规则——而两条路上的每一句拒绝文案、每一条群通知的载荷与时序，与今天一字不差。

这五个动作今天是两份逐字重复，差异只有返回值形状与通知里操作者标识的取值来源。另外三个动作（转让群主、设专属头衔、禁言）**已经共用**私有方法，本票把它们一起搬进新 module——否则同一族规则会分居两处。

**拒绝不再由规则直接写成中文。** 规则返回一个可辨识的拒绝原因，两条通道各自渲染文案。这不是新形状：共用消息能力规则已经这么做，控制服务里三个渲染函数把同一个拒绝原因渲染成撤回、贴表情、回复三套不同文案。本票沿用它，因此两条通道的文案逐字保留而角色判定只剩一份。

module 按最小结构化 interface 注入协作者（提交场景变更、派发群通知），**不注入宿主类型**，**不持有第二份沙盒场景**——只接收群对象与成员的引用。通道差异表达在 adapter 里，不表达绕道：机器人仍然只能经自身 OneBot action，受启用状态、实现配置与能力覆盖约束。

申请处理与守卫本轮不动，留给票 02。

## Comments

**票 02 的申请尾巴与守卫和本票一起落地，一个提交。** 票面写着「申请处理与守卫本轮不动，留给票 02」，但两张票共用同一个 module 与同一份协作者 interface：`denyGroupAuthority` 这个导出只为入群申请审批而存在，`removeRelationshipRequest`／`addFriendship`／`addApprovedGroupMember` 三个协作者也只有申请尾巴用得到。只做本票等于先把 module 造成一份只填了一半的协作者集合，票 02 再把同一份 interface 改一遍，中间那个状态没有任何人会读到。仓库里入站投递那一轮同样是两张票一个提交（`b59464e`），因此沿用它。

**八个动作收进 `src/relationship-actions.ts`，控制服务里不再有第二份。** 五份逐字重复（退群、改群名、设管理员、踢人、改群名片）收成五个方法，三个已经共用私有方法的（转让群主、设专属头衔、禁言）原样搬进同一个 module。控制服务里 `assertCanManageMember`、`setGroupMemberTitle`、`setGroupMemberMute`、`transferGroupOwner` 四个私有方法删除；`MAX_GROUP_MUTE_SECONDS` 跟着禁言规则搬走。两条通道的入口各自只剩「取群、取成员、调规则、把拒绝原因渲染成文案、返回自己那种形状」。

**动作名做成一张两条通道共用的表。** 八个动作的拒绝措辞在两条通道上今天逐字相同，因此一个渲染函数加一张动作名表就够；`describeGroupActionDenial(denial, 'kick')` 这样调用，动作名不在两条通道里各抄一遍。表里 `leave: '退出群组'` 今天不会被插值（退群只有一个不带动作名的原因），留着只为让渲染函数的签名是总的。文案真正不同的那一处（入群申请审批）不进这张表，见票 02。

**群名为空与头衔超长两条校验跟着规则走。** 它们必须在角色判定**之后**执行——普通成员传空群名时该看到的是「只有群主或管理员可以修改群名称」而不是「群名称不能为空」——所以不能由 adapter 先校验再把值传进来。两条因此成为拒绝原因（`group-name-empty`、`title-too-long`），措辞逐字保留。`validateOptionalName` 搬走后在控制服务里没有别的调用点，按未发布阶段兼容策略直接删除；`validateName` 留下，它还服务用户、机器人与群组的创建。

**`不能对自己执行…` 这条原因今天走不到。** 阶梯顺序决定了自己对自己必先命中前两条（同一个成员角色相同：普通成员命中权限不足，管理员命中「管理员不能管理群主或其他管理员」，群主命中「目标是群主」）。收拢前后完全一样，基线里「用户通道 踢人 拒绝：管理员踢自己」返回的正是第二句。原样保留并在规则里注明，理由是阶梯将来放宽时它仍要挡住「对自己执行」。

**顺手核出第五处通道差异，判定为输入不同、不动它。** 批准群邀请时入群通知的 `operator_id`：用户通道给的是受邀人自己（守卫已经保证 `request.targetId === operatorId`），机器人通道给的是邀请人（`request.requesterId`）。两条通道对「谁是这次入群的操作者」的答案不同，因此共用尾巴收 `operatorId` 作为入参，由各自通道算出来——而不是在尾巴里按 `subType` 分支。规格列的四处漂移之外还有这一处，记下来免得下一轮有人把它当债务。

**别处变红：零条。** 全量 180 个测试文件、1658 条断言一次通过。迁移前已 grep 确认 `assertCanManageMember`／`setGroupMemberTitle`／`setGroupMemberMute`／`transferGroupOwner`／`validateOptionalName`／`MAX_GROUP_MUTE_SECONDS` 在 `tests/` 里零出现，也没有任何测试读控制服务的源码文本。前几轮判定保留的断言一条未重判。

**证据。** `evidence/baseline.ts` 驱动两条**真实通道**跑 87 个用例：八个群动作加禁言在用户通道与机器人通道上各跑一遍（含全部拒绝分支）、两类申请审批与两类邀请审批在两条通道上各跑一遍、以及只有用户通道有的申请入群、邀请、群内与私聊戳一戳、设置好友备注、删除好友。每个用例记录执行前后**完整场景快照的 sha256 摘要**、两份快照之间**逐叶子的差异**、这次操作派发出去的**每一个标准 Koishi 事件与原始 OneBot 载荷的完整 JSON**、以及返回值或错误文案。摘要覆盖整份快照，任何一处场景差异都会让它变；差异清单只是让「变了什么」可读。标识按首次出现顺序归一化，时钟用单调假时钟，禁言到期时间与事件时间戳因此也参与比对——一次调用顺序的改变会立刻表现为数字不同。`evidence/01-baseline-head.json` 在 `137f04d` 的独立 git worktree 上采集，`evidence/01-after.json` 采于本票收尾后，`diff` 无输出。

脚本自己有两处不确定性，值得记下来免得下次再踩：内置头像按未占用集合随机挑选、池子用完后还会重复，因此引用值既不稳定也不能靠出现顺序配对（头像与关系规则无关，只保留「有没有头像」这一位）；另一处是事件数组交出引用后被窗口之外的准备工作继续追加，改成复制才对得上。两处都是先连跑三次才暴露出来的。

**验证命令。** `npx tsc -p tsconfig.json --noEmit`、`yarn typecheck`、`yarn test`（180 文件 / 1658 断言）、`yarn build` 全部通过；`git diff --stat` 只有 `src/control-service.ts` 与 `tests/server-architecture.test.ts`，客户端零改动。
