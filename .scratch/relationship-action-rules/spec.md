# 关系操作的规则只有一份，两条操作通道退成 adapter

Status: ready-for-agent

## Problem Statement

同一条群权限规则在沙盒里写了两遍：一遍给普通用户走的用户交互，一遍给虚拟 OneBot 机器人走的 action。

八个群动作里，退群、改群名、设管理员、踢人、改群名片这五个是**两份逐字重复**——同样的角色判定、同样的状态变更、同样的通知时序，差异只有返回值形状与通知里操作者标识的取值来源。另外三个（转让群主、设专属头衔、禁言）**已经共用**了私有方法，所以「共用一份规则」这条路在这个文件里已经走过三次，形状是现成的，只是没走完。

申请处理同样有两份：找到申请、按类型判权限、摘掉申请、批准则加成员或加好友。

两份拷贝已经漂移了，而且漂移是用户能看见的：

- 入群申请被拒时，用户通道说「只有群主或管理员可以处理入群申请」，机器人通道说「机器人没有审批入群申请的权限」。
- 好友申请找不到时，用户通道说「关系申请不存在」，机器人通道说「好友申请不存在」。
- 批准好友申请时顺手设置备注，**只有机器人通道支持**。
- 用户通道对群邀请多一条「机器人邀请必须由机器人处理」的守卫。

修一个群权限问题今天要改两处。漏掉一处的表现是「从 WebQQ 操作正常、机器人操作却不对」——两条路都通，只是规则不一样，没有任何东西会报错。加第九个群动作时会再写两遍。

## Solution

把关系操作的领域规则收成一个 module，两条操作通道退成 adapter：用户通道直接调它，机器人通道经自身 OneBot action 落到同一份规则上。

**已经漂移的那四处原样保留。** 拒绝不再由规则直接写成中文，而是返回一个可辨识的拒绝原因，由通道各自渲染文案——两处已有断言的文案因此逐字不变，而角色判定只剩一份。备注留在机器人 adapter，邀请守卫留在用户 adapter。

用户看不到任何变化。两条通道的每一个动作、每一句拒绝文案、每一条群通知的载荷与时序，全部与今天一字不差。

治理之后：修一处群权限两条路同时好；加一个动作写一遍；一条规则拦住下一次各写两遍。

## User Stories

1. As a 沙盒用户, I want 从 WebQQ 踢人、设管理员、改群名、改群名片、退群的行为一字不变, so that 一次结构性收拢不需要我重新验收
2. As a 沙盒用户, I want 权限不足时看到的拒绝文案一字不变, so that 我不必重新学哪句话对应哪种拒绝
3. As a 沙盒用户, I want 处理入群申请与群邀请的权限判定不变, so that 谁能审批仍然符合我的预期
4. As a 沙盒用户, I want 「机器人邀请必须由机器人处理」这条守卫仍然生效, so that 我不会代机器人做它该自己做的决定
5. As a 沙盒用户, I want 每个群操作派发出去的群通知载荷与时序不变, so that 被测插件收到的事件与今天一致
6. As a 沙盒用户, I want 群主不能直接退群、不能修改群主权限这些边界不变, so that 场景不会进入没有群主的状态
7. As a 沙盒用户, I want 申请、邀请、戳一戳这些只有用户通道有的动作不受影响, so that WebQQ 的交互面没有变化
8. As a 被测插件开发者, I want 机器人经自身 OneBot action 执行群操作的行为一字不变, so that 我的插件不必改
9. As a 被测插件开发者, I want 机器人操作仍然受启用状态、实现配置与能力覆盖约束, so that 沙盒仍然像真实环境
10. As a 被测插件开发者, I want 机器人审批好友申请时仍然能顺手设置备注, so that 我的插件用到的那个参数还在
11. As a 被测插件开发者, I want 机器人通道的拒绝文案一字不变, so that 我按文案断言的测试不必改
12. As a 被测插件开发者, I want 机器人通道仍然按 OneBot 的子类型语义查找申请, so that 传错子类型时仍然得到「申请不存在」而不是被静默处理
13. As a 被测插件开发者, I want 调试记录里机器人动作的形状不变, so that 我仍能复盘一次操作
14. As a 插件维护者, I want 一条群权限规则只有一份实现, so that 修一处两条路同时好
15. As a 插件维护者, I want 加一个新的群动作只写一遍, so that 不会漏掉另一条通道
16. As a 插件维护者, I want 已经共用的那三个动作和新收进来的一起住在同一个 module 里, so that 规则不分居两处
17. As a 插件维护者, I want 拒绝以可辨识原因表达而不是直接写成中文, so that 同一条判定能被两条通道渲染成各自的文案
18. As a 插件维护者, I want 这个形状与仓库里既有的消息能力拒绝一致, so that 读代码的人不需要学新东西
19. As a 插件维护者, I want 申请处理只共用尾巴, so that 前置判定仍然显式表达两条通道本该不同的地方
20. As a 插件维护者, I want 通道差异表达在 adapter 里而不是绕过规则, so that 「操作通道」这条领域约束不被削弱
21. As a 插件维护者, I want 新 module 不持有第二份沙盒场景, so that 服务端状态所有权不变
22. As a 插件维护者, I want 群成员角色的比较由一条规则钉在 module 里, so that 下一个人不会在通道入口里重新写一遍权限判定
23. As a 插件维护者, I want 那条规则不误报场景校验与角色名渲染, so that 守卫的信号不被稀释
24. As a 插件维护者, I want 共用消息能力规则那两处按文件登记为有主豁免, so that 它们在账上而不是被无声放过
25. As a 插件维护者, I want 两条通道各自的既有测试一字不改地通过, so that 回归网来自真实通道而不是新造的断言
26. As a 插件维护者, I want 每个动作前后的场景快照与群通知载荷逐字节相同, so that 「行为没变」不是一句口头承诺
27. As a 插件维护者, I want 客户端一行不改并且可以用 diff 证明, so that 这一轮不需要开浏览器
28. As a 插件维护者, I want 这道归属写进 ADR, so that 下一个人知道关系规则该住在哪里

## Implementation Decisions

### 重复的实际范围：五处逐字重复，三处已经共用

- 八个群动作里，退群、改群名、设管理员、踢人、改群名片是两份逐字重复；转让群主、设专属头衔、禁言已经共用私有方法。报告说的「四个公开入口加两个申请处理器各自实现相近的规则」是高估——这条路已经走过三次，本轮把它走完。
- 申请、邀请、戳一戳、用户侧的申请审批只有用户通道有，不涉及重复。

### 要 module 而不是继续用私有方法

- 依据是守卫。仓库既有的架构守卫都按「写法形状 ＋ 持有者文件」判定；规则留在控制服务的私有方法里，持有者就是控制服务整个文件，而违规也在同一个文件里——文件级持有者判定会把整个文件放行，规则等于不存在。**想要守卫，就必须要 module。**
- 通过删除测试：删掉它，八个动作的规则会散回两个通道入口，正是今天的状态。它在集中而不是搬家。
- 注入两到三个协作者（提交场景变更、派发群通知、申请与好友关系集合），与入站投递 module 同口径：注入最小结构化 interface，不注入宿主类型。**module 不持有第二份沙盒场景**，只接收引用，ADR-0002 不动。
- 已经共用的那三个方法一起搬进去，否则同一族规则会分居两处。

### 拒绝以可辨识原因表达，通道渲染文案

- 规则不再直接抛中文，而是返回一个可辨识的拒绝原因；两条通道各自把原因渲染成自己的文案。
- 这不是新形状：共用消息能力规则已经这么做——它返回一个拒绝原因联合，而控制服务里有三个渲染函数把同一个原因渲染成撤回、贴表情、回复三套不同文案。本轮沿用它。
- 收益是那两处**已有断言**的文案（「只有群主或管理员可以处理入群申请」与「机器人没有审批入群申请的权限」）逐字保留，而角色判定只剩一份。传字符串也能做到，但那会让规则收一个只为拼文案存在的参数。

### 已经漂移的四处原样保留

- 两处拒绝文案：由上面的原因渲染保留。
- 批准好友申请时设置备注：**只有机器人通道支持**，留在机器人 adapter。给用户通道加这个参数是新功能而不是重构。
- 用户通道对群邀请那条「机器人邀请必须由机器人处理」的守卫：留在用户 adapter。它表达的正是「操作通道」这条领域约束——机器人的决定必须由机器人自己经 OneBot action 作出。
- 第五处不算漂移：机器人通道按 OneBot 的子类型语义查找申请（调用方必须传子类型，传错就当找不到），用户通道没有这个参数。两个通道的**输入不同**，不是同一规则的两种写法。

### 申请处理只共用尾巴

- 共用的是尾巴：摘掉申请、批准则加成员或加好友、否则提交场景变更。
- 前置判定各留在自己通道——谁有权处理、能不能代机器人处理、按什么条件查找申请。这正是两条通道**应该**不同的地方；把它们参数化会让通道差异从两段可读的代码变成一组开关，读的人每次都要回头查那个开关传了什么。

### 守卫：谓词按标识符名收窄

- 新增一条规则：群成员角色的比较只允许出现在关系规则 module 里。谓词判定 `actor` / `target` / `operator` 这三个名字上的角色字段与字面量比较。
- 今天服务端有 18 处角色比较，按用途分四类：两份逐字重复的权限判定 8 处（收成 4）、已经共用的 4 处（原样搬入）、入群申请审批权限 2 处（收成 1）、以及**三处不是权限判定的**——场景校验里判断群里有没有群主、机器人适配器把角色渲染成中文名，加上共用消息能力规则那两处。
- 前两类不是权限判定的那两处用的是另一个标识符名，因此谓词天然不命中，不需要豁免。共用消息能力规则那两处用的是同样的标识符名，会命中，按文件登记为有主豁免，负责人指向 ADR-0078——那两处角色比较是消息能力规则自己的职责。
- 这与工具注册表那条规则同一个手法：按标识符名收窄谓词避开合法命中，而不是靠豁免去兜。

### ADR

- 写一条：关系操作的领域规则由一个 module 唯一持有；两条操作通道退成 adapter，用户通道直接调、机器人通道经自身 OneBot action 落到同一份规则上；拒绝以可辨识原因表达、由通道渲染文案；申请处理只共用尾巴及其理由；群成员角色比较由一条规则钉在 module 里，共用消息能力规则按文件登记为有主豁免。
- 写明不推翻：领域词汇里的「操作通道」（adapter 表达差异，不表达绕道）、ADR-0002 的服务端状态所有权、ADR-0076 的写入偏离（机器人只能经自身 OneBot action）、ADR-0078 的共用消息能力规则。
- 领域词汇不需要新词：「操作通道」已在册且定义准确，正是这个 module 的名字来源。落地时核一遍。

## Testing Decisions

好的测试断言外部可观察的行为，而不是实现写法。本仓库的判据已经写下来了：肯定式实现细节断言在等价重构时变红、在真实回归时沉默。本规格不新增任何一条这样的断言。

**净新增 seam 数：零。** 两条操作通道各自的既有 seam 就是这一族的全部测试面，而且它们恰好是**真实通道**——这一点比新造一个 module seam 更重要。

### 主测试面

- **用户通道的既有 seam**。执行好友操作与群操作那两个入口，测试目录里各有约 40 处引用，分布在七到九个文件里。其中群权限那一份（263 行、11 个用例）与好友关系那一份（245 行、10 个用例）是这一族的核心，含权限拒绝的具体文案。
- **机器人通道的既有 seam**：机器人自身的 OneBot action。落地点那四个成员在测试里**零直接调用**，但它们经机器人运行时的 action 被 OneBot 桥接那一份（986 行、21 个用例）与实现配置那一份覆盖，含「只有群主可以设置专属头衔」这类权限拒绝，以及能力禁用的拒绝。
- 两份都**一字不改**地继续通过。这是本轮的回归网，且两份分别从真实通道驱动——它们不是同一条断言的两份拷贝，而是「每条通道都真的经过了那份规则」这条接线的两侧证据。
- **服务端架构守卫（既有 seam）**。新规则与它的正反自测在这里。

### 不新增的断言

- 不为新 module 单独写一套「谁能踢人」的断言去替换上面两份。规则合并之后两条通道共用一份实现，但两份通道测试仍然各自证明**那条通道确实走了这份规则**——这正是今天会漂移的地方，不能用一份 module 断言替掉。
- 不为拒绝原因联合写形状断言：那是肯定式实现细节断言，等价重构时变红。它由两条通道渲染出的具体文案从外部证明。

### 纯结构性的证明

- **两条通道各自的既有测试一字不改地通过。** 主证据。
- **stash 基线比对每个动作执行前后的沙盒场景快照，以及派发出去的群通知载荷完整 JSON**，逐字节相同。八个群动作 ＋ 两类申请处理 ＋ 两条通道各跑一次。
- **完整测试、类型检查与构建通过。**
- **`git diff --stat` 里没有客户端路径。** 本轮客户端一行不改。不开浏览器。
- 每张票各跑一次。基线作为票的证据留在本 feature 目录下。

### 别处变红的处置

改控制服务会让读它源码或按私有方法名断言的测试变红。逐条区分真红与假红——标识符变化跟着改是假红，行为口径或成本结构变化是真红，停下来查——并在票的 Comments 里逐条记处置。**不重判前几轮已经判定保留的断言。**

## Out of Scope

- **统一那两处拒绝文案。** 两处都有断言，统一它们要改断言，而改断言正是最容易把真红当假红顺手改掉的动作。文案由拒绝原因渲染，逐字保留。
- **给用户通道加「批准好友申请时设置备注」。** 那是新功能而不是重构。
- **把用户通道那条「机器人邀请必须由机器人处理」的守卫下沉进规则。** 它表达的是操作通道这条领域约束，属于 adapter。
- **让两个通道按同一条件查找申请。** 机器人通道多的子类型匹配是 OneBot 协议自身语义，两个通道的输入不同。
- **控制服务上那四个机器人通道落地成员的收窄。** 它们是 OneBot action 的落地点，返回 OneBot 回执形状，本轮只把规则搬走、不动它们的 interface。
- **按剩下几组职责继续划控制服务内部 module。** 场景写入与保留窗口、头像与媒体、发送时序、公共 notice 派发本轮不动。
- **界面、文案、样式与交互的任何调整。** 本轮没有行为变化，一处例外都没有。

## Further Notes

- 最值得做的不是少五份拷贝，而是「两条通道的规则会不会漂移」这件事第一次有了红灯。它今天的失败形态是「从 WebQQ 操作正常、机器人操作却不对」——两条路都通，只是规则不一样，没有任何东西会报错。
- 而且它**已经漂移过四次**了。四处里三处是文案与参数（本轮原样保留），但它们证明了漂移不是假设。第五处经核查不是漂移而是两个通道的输入不同，这个区分本身值得写下来，免得下一轮有人把它当债务去「修」。
- 「共用一份规则」这条路在这个文件里已经走过三次（转让群主、设专属头衔、禁言），形状是现成的。本轮的新东西只有两样：把它走完，以及把它搬到一个能被守卫钉住的位置。
- 拒绝以原因表达而不是直接抛中文，这个形状仓库里已有先例——共用消息能力规则返回拒绝原因，控制服务里三个渲染函数把同一个原因渲染成三套文案。本轮遇到的正是同一个问题（同一条判定、两套文案），因此不发明新写法。
- 机器人通道的 seam 是 OneBot action 而不是那四个落地成员。这一点决定了本轮不需要为机器人通道新增任何测试面：真实通道已经被覆盖，而那才是应该被覆盖的东西。
