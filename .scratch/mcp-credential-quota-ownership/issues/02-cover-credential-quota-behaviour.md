# 02 — 补齐测试凭证配额的行为测试

**What to build:** 外部测试控制器超出自己的调用频率或并发上限时,能拿到明确的拒绝与结构化重试时间——这件事第一次有测试证明。

已核实的覆盖缺口:测试凭证的四档频率上限中,状态修改、等待与媒体上传三档在任何测试里都没有被设置过;并发超限对应的错误码在整个仓库零处触发。也就是说 ADR-0025 承诺的「按测试凭证分别限制查询、状态修改、等待和媒体上传的频率与并发,超限返回结构化重试时间」当前只有查询那一档被间接覆盖,其余全部未验证。

这张票要证明的是外部测试控制器视角的行为:达到某一档上限后下一次调用被拒绝、拒绝携带可用于重试的等待时间、不同凭证的额度互不影响、不同档位的额度互不串用、并发上限在超出时拒绝而不是排队。频率与并发两类需要不同的驱动方式——频率靠推进时间,并发靠让多个调用同时在飞。

**Blocked by:** None — can start immediately(与 01 互不阻塞;01 只移动字段声明,不改变配额执行位置)

**Status:** ready-for-agent

- [ ] 状态修改档达到频率上限后,下一次状态修改调用被拒绝
- [ ] 等待档达到频率上限后,下一次等待调用被拒绝
- [ ] 媒体上传档达到频率上限后,下一次上传调用被拒绝
- [ ] 查询档达到频率上限后,下一次查询调用被拒绝
- [ ] 超限拒绝携带结构化的重试等待时间
- [ ] 各档额度互不串用:一档耗尽不影响其他档
- [ ] 不同测试凭证的额度互相独立
- [ ] 时间推进后额度恢复,调用重新被接受
- [ ] 并发变更超出上限时被拒绝,且拒绝使用并发超限对应的错误码而不是频率超限的
- [ ] 并发等待超出上限时被拒绝
- [ ] 并发上传超出上限时被拒绝
- [ ] 并发调用结束后额度释放,后续调用重新被接受
- [ ] 频率类用推进时间驱动,并发类用多个同时在飞的调用驱动,不用等待真实时长
- [ ] 断言的是外部测试控制器可观察的结果——是否被拒绝、错误码、重试时间——不断言内部计数器状态
- [ ] 单元测试、类型检查与构建全绿
