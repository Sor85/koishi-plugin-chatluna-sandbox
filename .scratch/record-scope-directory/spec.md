# 跨记录域联邦读取收成一个 module

Status: ready-for-agent

## Problem Statement

「主模拟 QQ 环境加上全部 AI 测试空间」这件事没有任何 module 拥有它。

八处代码各自重新推导一遍：Console 的调试记录列表、调试记录详情、调试记录清理、模型请求列表、模型请求详情，测试控制端点的模型请求列表，以及插件装配里的预设运行时目标解析、模型请求采集器候选、用量事件关联的记录库集合。每一处都自己枚举一遍测试空间，每一处都自己判一次「测试空间服务可能不存在」——十一处判空，而插件入口的正常路径与降级路径都传真实例，这个判空保护的是一个从未发生的情况。

同一个想法有两份实现。模型请求那份是导出的合并函数，调试记录那份是内联在 Console 里的一段代码，两者逐步同形：按时间排序、相同时用第二排序键破平、切到每页条数、容量四字段相加、最早游标取最小。「先查主环境，失败就 catch 着遍历空间」也写了两遍。

两份实现已经开始漂移，而且没人会发现。调试记录联邦前会等全部成员就绪，注释写明「避免把仍在加载误报成空历史」；模型请求联邦一处都不等。测试控制端点有模型请求的联邦列表，却没有联邦详情，外部测试控制器拿到一个记录标识必须先知道它属于哪个 AI 测试空间。「先主后遍历」用 try/catch 表达，把「这个记录域里没有这条记录」和「这个记录域的持久化坏了」混成同一件事：一次真实故障会被当成未命中静默跳过，用户看到的是「记录不存在」。

联邦这一层几乎没有测试。活着的联邦用例只有三个，覆盖排序方向、四种范围取值与清理覆盖面；每页条数截断、是否还有更多、最早游标、容量累加这四件事在联邦层一条断言都没有。单个记录库的分页断言是齐的，但它们证明不了聚合。

## Solution

「谁是全部记录域」变成一个可以单独问的 module，「跨记录域读一次」变成它的三种行为。

用户看不到变化，只有一处例外：外部测试控制器多一个跨记录域的模型请求详情读取。今天散在调用点的四条规则升级成 module 拥有的事实——记录域的清单顺序、未归属不参与联邦、读取前等待全部成员就绪、未命中用空值而不是异常表达。

下一个要做「跨全部记录域看一遍」的人只写查询条件，不必再想着遍历 AI 测试空间；一条架构守卫拦住照抄旧写法的下一次。

## User Stories

1. As a 沙盒用户, I want 调试记录页的联邦视图排列与今天完全一样, so that 一次结构性收拢不需要我重新验收界面
2. As a 沙盒用户, I want 模型请求页在「全部」范围下的排列与今天完全一样, so that 我的复盘习惯不被打断
3. As a 沙盒用户, I want 模型请求页在「全部」范围下的「加载更多」继续可用, so that 我能翻到更早的记录
4. As a 沙盒用户, I want 数据库模式下刚重启时联邦视图不返回空列表, so that 我不会以为记录丢了
5. As a 沙盒用户, I want 调试记录的一键清理继续覆盖运行中的 AI 测试空间, so that 我不必先逐个接管空间
6. As a 沙盒用户, I want 联邦视图里每条记录仍然标着它来自主环境还是哪个空间, so that 我知道这条证据在哪产生
7. As a 外部测试控制器, I want 拿着记录标识就能读到模型请求详情, so that 我不必先知道它属于哪个空间
8. As a 外部测试控制器, I want 清理类工具继续要求显式指定范围, so that 我不会一次抹掉主环境与全部空间的证据
9. As a 外部测试控制器, I want 未归属的模型请求仍然只能显式指定才读到, so that 无法安全归属的请求不会混进某个空间的结论里
10. As a 外部测试控制器, I want 两种协议表述在这次改动后仍然落到同一次工具调用, so that 权限、配额、幂等与记录不出现第二套
11. As a 插件维护者, I want 联邦口径只有一份, so that 改排序或容量统计时两种记录同时生效
12. As a 插件维护者, I want 记录域的清单顺序是接口的一部分, so that 「先查主环境」不必由每个读取方各自声明
13. As a 插件维护者, I want 未归属不参与联邦这条规则由一个 module 拥有, so that 每个调用点不必各写一次过滤
14. As a 插件维护者, I want 一个记录域的持久化故障照原样抛出, so that 它不再伪装成「记录不存在」
15. As a 插件维护者, I want 判空只在构造记录域目录时发生一次, so that 之后的代码里再也见不到它
16. As a 插件维护者, I want 联邦层的截断、还有更多、最早游标与容量累加各有断言, so that 改合并逻辑时立刻看到红灯
17. As a 插件维护者, I want 「读取前等待全部成员就绪」这条不变量有断言, so that 它不再只是一句注释
18. As a 插件维护者, I want 两种记录页的差异只以第二排序键与续页游标两个参数表达, so that 新增一种记录不必改这个 module
19. As a 插件维护者, I want 续页游标只在第二排序键跨记录域可比时给出, so that 我不会误以为调试记录也能跨空间翻页
20. As a 插件维护者, I want 插件装配里三处枚举也走同一个 module, so that 「谁是全部记录域」不留第二个答案
21. As a 插件维护者, I want 公开的合并函数不再导出, so that 没有一条绕过这个 module 的路
22. As a 插件维护者, I want 一条守卫拦住重新枚举 AI 测试空间的写法, so that 这次收拢不在下一个功能里被抄回去
23. As a 插件维护者, I want 「记录域」与「联邦读取」写进领域词汇, so that 下一个人知道这两个概念存在
24. As a 插件维护者, I want 联邦到哪里为止有一条架构决策记录, so that 测试控制端点刻意的能力不对等不被当成漏洞去修

## Implementation Decisions

### 记录域目录是一个独立的服务端 module

- 新建一个 module 持有沙盒控制服务、AI 测试空间服务与未归属模型请求库三者，对外只回答「谁是全部记录域」以及三种跨记录域行为。不把这件事加进 AI 测试空间服务：那个名字与「AI 测试空间」这一领域词绑定，而主模拟 QQ 环境明确不是测试空间，塞进去会污染词汇。
- 服务端专用。客户端始终带显式空间标识定域，联邦是服务端把多个记录域揉成一页之后才发给前端的，前端没有「全部记录域」这个概念。因此该 module 可以自由依赖 Koishi 运行时，不受「被客户端一同引用的领域模块不依赖 Koishi 运行时」那条守卫约束。
- 单文件，放在服务端源码顶层。仓库只为多文件子系统建目录。

### 记录域用可辨识联合表达，而不是可选字段

- 记录域分两类：拥有沙盒场景的（主模拟 QQ 环境与各 AI 测试空间，都有控制服务）与未归属的（只有模型请求库，没有场景）。
- 用可辨识联合而不是一个可选的控制服务字段：后者只是把判空从调用点搬进类型，每个消费方仍要写一次判空，等于换个地方保留同一个坑。

### interface 是高阶的，而不是按记录种类枚举

- 五个成员：列出全部记录域、只列出拥有场景的那些、联邦读取一页、按顺序查找第一个命中、逐个记录域各执行一次并把结果按顺序还给调用方。
- 不按记录种类给方法。记录种类会增长，按种类枚举会让这个 module 每加一种记录就变宽一次，正是要摆脱的形状。

### 判空在构造时吸收一次

- AI 测试空间服务与未归属记录库在构造入参里保持可选，缺席就是清单里少一个成员，而不是清单里有个空洞。
- 两个消费方（Console 注册与测试控制服务）各自在入口把三个输入包成一份记录域目录，而不是由插件入口创建一份传下去。两处包装从同样三个输入派生，不存在第二个数据源，因此内容不可能漂移；换成插件入口统一创建会改动两个函数的签名，代价是二十多处测试调用点，不成比例。

### 清单顺序是接口的一部分

- 顺序固定为主模拟 QQ 环境、各 AI 测试空间按创建序、未归属在末尾。「先查主环境再逐个找」这一语义由该顺序表达，查找不再额外收「从哪开始」的参数。
- 未归属排在末尾，读起来就是「它不参与联邦」。

### 未归属永不参与联邦

- 联邦读取与逐个执行都只遍历拥有场景的记录域。这条规则由该 module 拥有，而不是由每个调用点各写一次过滤。
- 未归属仍可经「列出全部记录域」拿到，供显式指定范围的读取路径使用。

### 可被联邦的一页只要求四个字段

- 记录数组、是否还有更多、当前最早游标、容量摘要。这四个字段在 OneBot 调试记录页与模型请求记录页上同名同义，容量摘要的四个子项也一致，因此合并可以直接相加。
- 两种页的实质差异只有两处，都由调用方以参数声明，而不是写进该 module：
  - **第二排序键**：时间相同时的破平函数。模型请求用记录标识，调试记录用序号。
  - **续页游标**：只在第二排序键跨记录域全局可比时提供。模型请求的时间与标识组合全局可比，WebQQ 的「加载更多」正在使用；调试记录的序号是每个记录域各自独立的计数，跨记录域比较没有意义，因此调试记录的联邦页没有续页游标，精确游标分页必须带显式空间标识。这不是疏漏，是规则。
- 每页条数的上限由调用方按自己的记录种类先夹紧再传入。两种记录的上限不同，由该 module 统一夹会把其中一种的上限强加给另一种。

### 未命中用空值表达，故障照原样抛出

- 查找的未命中返回空值。原先用 try/catch 遍历，把「没有这条记录」与「持久化坏了」混成一件事；改动后一个记录域的故障不再被当成未命中静默跳过。
- 这是行为变化：某个记录域读取失败时，调用方会拿到那个故障，而不是「记录不存在」。

### 读取前等待全部成员就绪

- 联邦读取与查找在读取前等全部成员的场景就绪。记录库自身的读取路径已经各自等过自己的就绪，这里额外等到的是场景就绪与场景待写队列。
- 此前只有调试记录那条路等、模型请求那条完全不等。两条路统一向保守的方向对齐：多等一次已就绪的 Promise 成本接近零，漏等的后果是静默返回空列表。

### 来源标注的数据归 module，形状归调用点

- 该 module 提供标注所需的数据——记录域标识、名字、是不是主环境；投影成哪种来源形状留在调用点。
- 来源形状属于 Console 契约与测试控制端点各自的出参。Console 的端点出参由契约唯一声明，让枚举 module 去产出契约形状等于把出参声明搬出契约。

### 权限策略留在调用点

- 逐个记录域执行只负责遍历。「这个操作要不要先接管空间」是注册时的策略，留在调用点显式书写；藏进遍历 module 会让读代码的人以为该操作天然不需要接管。

### 测试控制端点保持单个记录域的门禁

- 清理类工具继续要求显式指定范围。联邦清理意味着一个测试凭证一次抹掉主模拟 QQ 环境与全部 AI 测试空间的证据，这个能力不给外部测试控制器。
- 只补齐模型请求详情的跨记录域读取：它无副作用，记录标识本身唯一，要求调用方先知道记录属于哪个空间说不通。补齐后查找有两个真实调用方，而不是一个。
- 这处能力不对等是刻意的，写进架构决策记录。

### 公开的合并函数不再导出

- 合并逻辑收进该 module 内部。留着公开导出等于留一条绕过 module 的路，而它今天恰好被两个即将改走 module 的调用点直接使用。

### 插件装配的三处枚举同批收拢

- 预设运行时目标解析、模型请求采集器候选、用量事件关联的记录库集合都改用「列出记录域」。这三处与读取扇出共享的恰好是「谁是全部记录域」这一件事；只收一半，旧写法会留在装配里被下一个人照抄。

### 领域词汇与架构决策

- 领域词汇新增「记录域」与「联邦读取」两条。代码里已经在用「范围标识」这个词，而它的取值恰好就是主环境、某个空间、未归属三种；领域词只是给一个已经在用但没被命名的概念补上名字。
- 新开一条架构决策记录，记录联邦读取的归属、续页游标规则、等待就绪这条不变量，以及测试控制端点刻意保持的能力不对等。

## Testing Decisions

好的测试断言外部可观察的行为，而不是实现写法。本仓库已经为此付过代价：模型请求工作台曾有三百多条打在源码文本上的断言，一次性删掉一百二十八条，理由是它们在任何等价重构时变红、对真实行为回归保持沉默。这次收拢不新增任何源码文本断言。

**净 seam 数不变：去掉一个，新增一个。**

### 主测试面：两个既有入口 seam（主要判据）

1. **Console 端点监听器**——测试手工捕获注册的监听器后直接调用。`tests/console-debug-records.test.ts` 的联邦用例与 `tests/console-model-requests.test.ts` 的分范围用例落在这里。
2. **测试控制服务的工具调用入口**——两种协议表述共用的唯一入口。`tests/mcp-model-requests.test.ts` 的分范围用例落在这里。

这次收拢是纯结构性重构，因此主判据是**这三个用例一字不改地继续通过**。它们已经覆盖联邦排序方向、四种范围取值、未归属的正文隐藏与清理拒绝、清理覆盖全部空间。需要改断言才能过，就说明口径变了，停下来查。

### 新增测试面：记录域目录自身的 interface

只用来断言今天在入口 seam 上没有覆盖、且从入口构造成本过高的那几件事：

- 每页条数截断与「是否还有更多」的两种来源（切掉了东西 / 任一记录域自己还有更多）
- 容量四字段逐项相加
- 最早游标取全部记录域里最小的那个，全都没有时不编造
- 续页游标只在调用方声明且确有下一页时产出；未声明时结果里根本没有这一项
- 第二排序键为数字时按数值比较，而不是按字符串（字符串序下十会排在九之前）
- 清单顺序、缺席成员不留空洞、联邦不遍历未归属
- 读取前等到全部成员就绪
- 查找命中后不再继续读、命中时带回记录域、全部未命中返回空值、读取抛错时原样抛出

从 Console 入口断言容量累加需要真的把两个记录域各塞到容量上限，代价高且脆弱；在这个 seam 上一行即可。先例是仓库里已有的单记录库分页用例（`tests/model-request-records.test.ts` 与 `tests/onebot-debug-records.test.ts`），形状可直接沿用——它们证明的是单库，这里证明聚合。

### 去掉的 seam

公开导出的合并函数今天被两个调用点直接使用却没有任何直接测试。收进 module 内部后它不再是一个可被独立调用的面。

### 架构守卫

新增一条规则制守卫，谓词按写法形状判定：枚举 AI 测试空间与按标识取控制服务出现在同一段表达式里即报，记录域目录自身是规则的持有者。纯粹列出空间清单给用户看（Console 的空间列表端点与测试控制端点的列表工具）不命中；带显式空间标识的单空间解析也不命中。

先例是仓库现有的两套规则制守卫：会话集合那条同样按写法形状判定，并刻意不误报领域类型里的字段声明与投影回填。不用白名单——白名单只约束名单内的文件，会随文件数增长自动失效。豁免清单保持为空：这次收拢之后不应存在需要登记的违规。

## Out of Scope

- **测试控制端点的联邦清理与联邦调试列表**。清理的显式范围要求是刻意的门禁，不是遗漏；调试记录的联邦列表同样不补。本规格只补模型请求详情一处读取。
- **把 Console 的联邦清理收窄成必须指定范围**。那是用户自己的界面，门禁理由不适用，收窄会打断现有的一键清理。
- **统一两种记录页的第二排序键**。把调试记录的序号改成记录标识会动到它的持久化游标语义，为了对称去改存储不划算。
- **把每页条数上限统一到该 module**。两种记录的上限不同，统一会把其中一种的上限强加给另一种。
- **让客户端也拿到联邦概念**。客户端始终带显式空间标识，本规格不为一个假需求给该 module 加上禁依赖 Koishi 运行时的约束。
- **控制服务其余职责的拆分**。它仍然是一个七十多个公开成员的 module，转售证据记录库、消息投递、群权限、关系申请都各有摩擦，但都不在本规格内。
- **测试控制服务的工具分派收拢**。它的工具执行是一条四十分支的长条件链，与本规格无关。
- **未归属记录的归属推断**。无法安全归属的请求继续留在未归属，本规格不改变归属判定。

## Further Notes

- 这次收拢最值得做的不是少几行重复，而是三条今天只写在注释里或根本没写的规则第一次成为可断言的事实：记录域的清单顺序、读取前等待全部成员就绪、以及「未命中」与「故障」是两件事。第三条今天是一个静默缺陷——一个 AI 测试空间的持久化故障会让用户看到「记录不存在」。
- 判断这次收拢是否纯结构性，用 stash 基线的办法：同一份确定性场景（主环境加两个 AI 测试空间，各有调试记录与模型请求，含未归属记录）分别在收拢后与基线上导出联邦列表、联邦详情与清理结果，逐字节比对，而不是只看界面。
- 落地分三步，每步各跑一次完整测试与构建：① 建 module、补单测、写领域词与架构决策，不动任何调用点；② 五个 Console 调用点与测试控制端点的模型请求列表改走 module，删掉合并函数的公开导出；③ 插件装配三处、补齐测试控制端点的模型请求详情、加架构守卫。第 ② 步是纯结构性重构，三个既有联邦用例是它的回归网；第 ③ 步含一处功能新增，与重构分开才能定位问题。
