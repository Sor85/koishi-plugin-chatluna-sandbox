# 05 — 测试控制端点补齐跨记录域的模型请求详情

**What to build:** 外部测试控制器拿着一个模型请求记录标识就能读到详情，不必先知道它属于哪个 AI 测试空间。

测试控制端点今天有模型请求的联邦列表，却只能按显式范围读详情——调用方从「全部」列表里拿到一条记录，想看它的完整请求体与响应体，还得自己回头判断它属于哪个记录域。补齐后「全部」范围的详情读取按记录域目录的顺序查找，命中即返回，并带上来源标注。

未命中与故障仍然分开：全部记录域都没有这条记录时返回结构化的「记录不存在」，某个记录域的持久化故障照原样抛出并映射成对应的稳定错误码。

清理类工具**不**跟着放开，继续要求显式指定范围。联邦清理意味着一个测试凭证一次抹掉主模拟 QQ 环境与全部 AI 测试空间的证据，这个能力不给外部测试控制器。调试记录的联邦列表同样不补。这处能力不对等是刻意的，已写进架构决策记录。

这是本轮唯一的功能新增，因此与前面几张纯重构票分开——测试红了时能立刻分清是收拢改了行为还是新行为不对。

## Comments

- `get_model_request_record` 的 scope 枚举补上 `all`，工具描述同步说明它按记录 ID 跨记录域查找。
- 「全部」分支刻意留在原有 catch 之外：那个 catch 把任何异常都记成 `record_not_found`，故障会因此伪装成未命中。现在未命中显式抛结构化 `record_not_found`，故障交给 `normalizeToolError` 按 ADR-0027 归类成 `internal_error`。
- 来源标注按本端点自己的入参词汇给出（`{ scope, spaceId, name }`），调用方可以原样传回任何单记录域工具。
- 四个新用例落在 `service.callTool` 这个既有 seam 上；反向验证（去掉「全部」分支）时其中三个变红。
